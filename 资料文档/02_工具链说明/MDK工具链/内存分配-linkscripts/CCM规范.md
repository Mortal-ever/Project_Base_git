### 1. CCM 到底是什么？（硬件本质）

**CCM（Core Coupled Memory）** 是 STM32F4 内部一块 **64KB 的 SRAM**。

- **物理位置**：挂在 CPU 的 **D-Bus（数据总线）** 上，**不在 AHB 总线矩阵(外设总线)**内。
- **速度特性**：与 CPU 内核直连，**零等待周期**，且**不会因为 CPU 和 DMA 同时访问普通 SRAM 而产生总线仲裁延迟**。
- **访问权限**：**只有 CPU（Cortex-M4 内核）能访问它**。所有 DMA 控制器（ETH、UART、SPI、SDIO、USB）**物理上根本看不见 CCM 的地址（0x10000000~0x1000FFFF）**。



| 规则                  | 说明                                                         | 违反后果                                                     |
| :-------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **绝对禁止 DMA 访问** | 任何外设的 DMA 缓冲区（ETH Tx/Rx、UART DMA、SDIO 缓存）**绝不能**放在 CCM。 | **HardFault**（总线错误）或静默数据错乱（DMA 读到 0xFFFFFFFF）。 |
| **启动时可能未清零**  | CCM 在复位后内容随机。若使用 `UNINIT` 属性，系统启动时**不会**清 0。 | 依赖初始值 0 的全局变量会出问题，必须显式赋值或 `memset`。   |
| **调试器可正常访问**  | JTAG/SWD 可以读写 CCM，不影响在线调试（Keil Watch 可查看）。 | 无副作用。                                                   |
| **仅 CPU 负载受益**   | 只有 CPU 频繁读写的变量（任务栈、协议控制块、加密上下文）才值得放 CCM；纯数据搬运（如帧缓存）放普通 SRAM。 | 放错不会死机，但浪费了 64KB 高速资源。                       |

### 2.map代码段解释

在编译器眼中，你的 C 代码中的变量被分成了几类“段（Section）”，链接器根据这些段来分配地址。

| 段名称        | 存放内容                                                     | 初始值在哪里？               | 运行时位置                               |
| :------------ | :----------------------------------------------------------- | :--------------------------- | :--------------------------------------- |
| **`.text`**   | 程序代码（指令）、常量（`const`）、只读数据                  | **Flash（0x08000000）**      | **Flash**（直接在 Flash 中执行，不搬移） |
| **`.rodata`** | 只读常量（如 `"Hello"` 字符串、`const int`）                 | **Flash（跟着 .text）**      | **Flash** 或 RAM（取决于配置）           |
| **`.data`**   | **已初始化**的非零全局变量/静态变量<br>（例如 `int flag = 1;`） | Flash 中有备份值             | **RAM**（启动时从 Flash 拷贝过来）       |
| **`.bss`**    | **未初始化**或初始化为 **0** 的全局/静态变量<br>（例如 `int count;` 或 `static int num = 0;`） | **没有备份值**（只记录长度） | **RAM**（启动时由启动代码清零）          |

### 3. 在你的工程中，是谁在“维护这些规则”？（隐形规范）

你不需要在代码里到处检查“这块内存是不是 CCM”，因为你的工程通过**链接脚本（`.sct`）**和**架构分层**，已经建立了一套强制的“物理隔离护栏”：

#### 规范 ①：链接脚本（`.sct`）的“白名单”机制
你的脚本明确规定了只有 **`app_task_manager.o`** 中的 `CCM_HEAP` 段才能进入 CCM：

```text
RW_CCM 0x10000000 UNINIT 0x00010000  {
    app_task_manager.o (CCM_HEAP)   // 只有这个文件的这个段能进 CCM
}
RW_IRAM1 0x20000000 0x0001C000  {
    .ANY (+RW +ZI)                 // 其他所有 .c 文件默认进普通 SRAM
}
```
**效果**：
- 你在 `app_task_manager.c` 中定义的 `ucHeap[]`（FreeRTOS 堆）和任务栈（如果使用静态栈）——**进入 CCM**。
- 你在 `app_comm_log.c` 中定义的 `static uint8_t aucTxBuffer[256]`——**因为不在白名单，自动落入普通 SRAM（你 map 里看到的 `0x20005984`）**。

#### 规范 ②：架构文档的“反 DMA 铁律”
在你的 `工程技术栈与分层结构说明.md` 第 2.1 节中明确写道：
> *“业务应用任务不直接调用 HAL_UART_Transmit；只有日志 UART 后端等平台适配文件可以调用。”*

而在 `当前Modbus架构与使用说明.md` 第 9 节中，特别强调了 LOG 模块的设计：
> *“LOG 任务栈中的格式化文本不会直接传给 DMA；后端先复制到 `AppCommLogUartContext_t.aucTxBuffer[]`。”*

**这意味着**：即使任务栈（在 CCM）里拼好了日志字符串，最终发送给 UART 的 DMA 缓冲区（`aucTxBuffer`）被强制定义为 **`static`（普通 SRAM）**。这个“复制中转”的动作，就是工程架构强行加的**安全护栏**，防止 CCM 数据被 DMA 搬运。

#### 规范 ③：LwIP 内存池的“默认安全区”
LwIP 的 PBUF 池（`memp_memory_PBUF_POOL_base`）定义在 LwIP 源码的 `.c` 文件中，没有被指定到 `CCM_HEAP` 段。因此它自动落在 `RW_IRAM1`（普通 SRAM），ETH DMA 可以安全访问。

### 4. 回到你的问题：静态 vs 动态，哪个能放 CCM？

| 内存类型                        | 能否放 CCM     | 在你的工程里**实际**放在哪                                   | 依据                  |
| :------------------------------ | :------------- | :----------------------------------------------------------- | :-------------------- |
| **函数内局部变量**（非静态）    | ✅ 能（在栈上） | **CCM**（因为任务栈从 `ucHeap` 分配，而 `ucHeap` 在 CCM）    | 链接脚本白名单        |
| **全局 / 函数内 `static` 变量** | ✅ 能（加属性） | **默认普通 SRAM**（除非手动加 `__attribute__((section("CCM_HEAP")))`） | `.ANY` 规则落入 IRAM1 |
| **`pvPortMalloc` 动态申请**     | ✅ 能（从堆取） | **CCM**（因为 `ucHeap` 在 CCM）                              | 链接脚本白名单        |

#### 规则 ①：`UNINIT` 的“免清零”特权

你在 CCM 区加了 `UNINIT` 关键字。这向链接器传达了一个信号：**这个区域的变量，启动时不要进行 `.data` 拷贝，也不要进行 `.bss` 清零**。

- 为什么这么做？因为 **CCM 是 `UNINIT`**，所以启动代码里的 `__main` 会**跳过**对 `0x10000000` 区域的清零操作。
- 为什么能这么做？因为你在 `app_task_manager.o` 中放置的是 **`ucHeap`（FreeRTOS 堆）**。FreeRTOS 在初始化堆时（`pvPortMalloc` 第一次调用），内部会自己去管理 `ucHeap` 的起始状态，**不依赖于硬件启动清零**。如果强行让启动代码去清零这 64KB CCM，反而浪费了 CPU 的启动时间。

#### 规则 ②：为什么常规 `.data` / `.bss` 不在 CCM？

你的脚本中，**没有**把常规的 `*(.data)` 或 `*(.bss)` 放进 `RW_CCM` 区域，而是用 `.ANY (+RW +ZI)` 把它们全部丢进了 `RW_IRAM1`（普通 SRAM）。

- 这是**故意为之**的防御性设计。如果程序员在某个 `.c` 文件中定义了一个 `static int dma_buffer[1024] = {0};`，这个数组默认就是 `.bss`（或 `.data`）。
- 因为链接器把它分配到了 `RW_IRAM1`（普通 SRAM），它就能被 DMA 访问。
- **绝对不要把常规的 `static` 变量直接放到 `CCM`**，否则它的初始值无法被 `__main` 正确处理（因为 `UNINIT` 跳过了初始化），你会得到一个随机垃圾值作为“初始值 0”。

**关键结论**：你的工程通过 **`.sct` 白名单 + 分层强制中转（LOG 拷贝）+ LwIP 默认池**，形成了一套**“CPU 数据走 CCM，DMA 数据走 SRAM”**的自动隔离机制。你不需要在代码里操心地址检查，只需要遵守一条铁律：**凡是交给外设 DMA 搬运的缓冲区，务必定义成 `static` 或全局变量（让链接器丢进 SRAM）**。其余的 CPU 密集数据，放心扔给 `pvPortMalloc` 或局部变量，它们会自然落在 CCM 里享受高速。。

### 5. 后续 HTTPS 开发如何套用这套规则？

- **mbedTLS 上下文**（`ssl_context`、`entropy`）：**使用 `pvPortMalloc` 申请** → 自动落入 CCM，握手加解密速度起飞。
- **网络发送/接收大块数据**（如 JSON 响应）：定义 **`static uint8_t tx_buffer[4096]`** → 自动落入普通 SRAM，传给 LwIP 的 `netconn_write` 时，ETH DMA 搬运安全。
- **千万不要做**：在任务函数里定义 `uint8_t dma_rx_buf[1024]` 局部数组传给 UART DMA——因为局部数组在栈上（CCM），DMA 访问必挂。**必须用 `static` 或全局数组（SRAM）**。

### 6. 启动时的“幕后搬运工”（这是理解 CCM 的关键）

在进入你的 `main()` 函数之前，STM32 的启动文件（`startup_stm32f407xx.s`）调用 `__main`（C 库初始化函数），它会执行两个至关重要的动作：

1. **加载 `.data`**：将 Flash 中固件里存储的 `.data` 初始值，**复制**到 RAM 中对应的 `.data` 区域。
2. **清零 `.bss`**：将 RAM 中 `.bss` 区域的所有字节**全部写 0**。

**核心结论**：`.data` 和 `.bss` 的初始值维护是由 **CPU 内核（Cortex-M4）** 在启动阶段通过**纯软件循环（或编译器优化的内存拷贝）** 完成的，**不涉及任何 DMA**。

### 7. 针对“Map 文件”的深度阅读技巧

你的 `MDK-ARM/MilkTea.map` 文件会显示所有段的最终归宿。当你看 Map 文件时，重点关注以下几类符号：

- **`Image$$RW_IRAM1$$ZI$$Limit`**：启动代码清零 .bss 的结束地址。
- **`Image$$RW_CCM$$ZI$$Base`**：CCM 区域的基地址（因为 UNINIT，启动代码不会碰它）。

你会发现：
- **`s_axPendingEntries = 0x200056EC`**：它落在 `RW_IRAM1` 范围（0x20000000~0x2001C000），所以它的 `.bss`（未初始化）会被启动代码清零。你没有对它做显式赋值，但它默认是 0，这就是启动代码的功劳。
- **`ucHeap`（在 CCM）**：它虽然也是 `.bss` 性质，但因为 `UNINIT`，启动代码跳过清零。FreeRTOS 的 `heap_4.c` 在初始化时会通过 `pxEnd` 指针和链表结构来“标记”这块内存，并不要求它本身是全 0 的。

### 5. 结合 CCM 的使用规范（针对你当前工程）

基于以上底层原理，你的工程必须严格遵守以下两条“铁律”：

| 变量类型                                                     | 推荐放置位置                       | 底层段                                                       | 原因分析                                                     |
| :----------------------------------------------------------- | :--------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **DMA 缓冲区**（UART/SDIO/SPI 收发数组）                     | **必须**在 `RW_IRAM1`（普通 SRAM） | 全局/静态变量（`.bss` 或 `.data`）                           | 普通 SRAM 是 `UNINIT` 的，启动代码会清零或赋初值，且 DMA 总线矩阵可见。 |
| **CPU 频繁访问的控制块**（TCB、Queue、LwIP 的 `netconn`、mbedTLS 上下文） | **推荐**在 `RW_CCM`                | 通过 `pvPortMalloc`（从 `ucHeap` 获取） 或 **`__attribute__((section("CCM_HEAP")))`** 定义的任务栈 | CCM 零等待，且 CPU 独占访问；启动时无需初始化，交给 `pvPortMalloc` 内部管理即可。 |

### 6. 总结一句

- **`.data` / `.bss` 是启动搬运的基础单位**，由启动代码的 CPU 软件处理。
- **CCM 加 `UNINIT` 是在告诉启动代码“别碰我，我自己会管”**，这正是为你把 `ucHeap` 丢进去做铺垫。
- **工程规范**：你想让 CPU 独享高速的内存（任务控制块、动态对象），丢进 CCM；你想让 DMA 安全访问的内存（数组、静态缓冲区），必须留在普通 SRAM。严谨的链接脚本设计，已经帮你在编译阶段就做好了这场“物理隔离”。
