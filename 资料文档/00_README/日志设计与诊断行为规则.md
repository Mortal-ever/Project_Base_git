# 日志设计与诊断行为规则

## 目的

日志的目标是让开发者和自动化分析工具能够快速定位问题。日志格式不固定，
STM32、ESP、Linux 或其他 target 可以使用各自合适的格式；本规则只约束信息
完整性、可读性和输出行为。

## 必须满足的行为

1. 关键日志应能回答：哪个模块或设备、执行什么动作、处于什么阶段、结果如何，
   以及可定位的设备号、寄存器、地址或错误码。
2. source 前缀不能代替具体对象。`BUS_COMMAND_FAILED` 必须同时给出设备名称、
   设备 ID 和操作结果，不能要求阅读源码才能判断对象。
3. 正常周期轮询不应持续打印日志。只有状态变化、异常、超时、恢复或明确开启
   的调试模式才允许输出。
4. IO 状态日志采用边沿触发。首次采样只建立基线，之后仅在状态改变时输出，
   并包含点位名称、旧值和新值。
5. 初始化失败不得被重试循环持续刷屏。重试可以继续，但同一失败阶段只提示一次；
   设备恢复或阶段改变后，允许重新提示。
6. 日志文本必须让开发者直接理解，不得为了统一而强制套用无意义的字段模板。
   结构化字段、文本消息或二者组合均可使用。
7. 设备名、IO 名称、动作名和寄存器名应来自稳定的 target 配置，避免同一对象在
   多个源文件中出现不同名称。
8. 运行时字符串必须符合目标工具链要求。ARMCC V5.06 与 GCC 共用的源码优先
   使用 ASCII 名称；中文对照放在文档或上位机资料中。
9. 修改日志名称不得改变设备 ID、动作 ID、寄存器地址、协议值或错误码。

## 最小验收场景

新增或修改日志后，至少检查：正常成功、设备失败、超时、恢复，以及无状态变化
的重复轮询。每个场景都应能从日志中判断是否需要继续排查硬件、协议、流程或配置。

## 审查问题

- 不看源码能否确认具体失败设备？
- 能否区分初始化失败、单次命令失败和超时？
- 能否解释日志是否由重试或周期任务触发？
- 日志是否包含动作和阶段，而不只是一个错误码？
- GCC 与目标编译器是否能以相同含义编译？
- 是否避免了无必要的 RAM、动态分配和高频串口输出？
