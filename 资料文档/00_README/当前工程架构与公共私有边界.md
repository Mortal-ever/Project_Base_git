# 当前工程架构与公共/私有边界（定稿）

> 版本：1.0  
> 日期：2026-08-29  
> 适用范围：当前仓库、当前 Coffee2 target。MilkTea 本轮不参与架构设计、构建或兼容性判断。

仓库中残留的 `Application/UserAPP/MilkTeaApp` 文件属于待后续独立重写的遗留资料，
当前不进入 GCC preset、Keil target 或公共层验证；它们不能反向定义本架构。

这份文档是当前源码结构的架构入口。旧的“五层迁移”“DeviceProtocol 转发”
方案只保留作历史证据；若与本文件冲突，以本文件、源码和工程配置为准。

## 1. 一句话结论

公共层不是 Coffee2 专属。任何未来 target 都可以按需 include/link
`Application/Common`、`Transport`、`ProtocolStack/ModbusPort`、`New_Party/nanoMODBUS`
和 `DeviceLibrary`；Coffee2 只是当前唯一已经组合出来的产品。F200 虽使用厂商自有
协议、不是 Modbus，仍是无产品语义的公共设备库驱动。

当前不保留 `Application/DeviceProtocol`。原目录中的文件只是把产品命令转成设备库
调用的薄转发层，且夹带 Coffee2 的动作枚举、状态镜像或站点点表；它们不形成可复用
的独立能力，已删除。

## 2. 稳定的四层结构

```text
L1  平台/生成层
    CubeMX_Base/Core、Drivers、Middlewares、LWIP
    （HAL、FreeRTOS、lwIP、启动、外设初始化；生成物只由 CubeMX 维护）
          ▲
L2  公共基础层
    Common、Transport、ProtocolStack/ModbusPort、New_Party/nanoMODBUS
    （日志/OTA/TCP 会话/诊断、字节传输、Modbus 端口、协议栈）
          ▲
L3  公共设备库
    DeviceLibrary
    （Dobot、F200、杯盖、糖浆、制冰、秤、电能表、IO 等设备原生驱动）
          ▲
L4  target 私有应用层
    UserAPP/<Target>
    （业务、命令、队列、任务、设备选型、ID/route/串口/IP 绑定、状态和协议语义）
```

依赖方向固定为：

```text
Target App  ->  DeviceLibrary  ->  ModbusPort  ->  Transport  ->  L1 平台
Target App  ->  Common/Transport/ProtocolStack
```

公共层禁止反向依赖任何 `UserAPP/<Target>`。唯一受控例外是启动组合根
`Application/Common/CommonTargets.h`：它只被生成的 `freertos.c` 包含，依据
`USE_<TARGET>` 宏选择私有 manager；它不是公共业务 API，也不把 Coffee2 业务
暴露给其他 target。

## 3. 公共层定义：任何 target 均可复用

“公共”表示代码不包含产品名称、产品寄存器、订单语义、固定物理总线绑定或某个
target 的状态对象；它可以被另一个 target 单独编译和链接。公共目标在
`Application/CMakeLists.txt` 中位于 `if(PRODUCT_NAME ...)` 之前定义，Keil 中位于
独立公共虚拟组。

### 3.1 公共目录和目标

| 目录 | GCC 公共目标 | 作用 |
| --- | --- | --- |
| `Application/Common/Diagnostics` | `app_diagnostics` | 崩溃/断言诊断 |
| `Application/Common/Log` | `app_log` | 通用日志输出 |
| `Application/Common/LwipAlert` | `app_lwip_alert` | lwIP 资源告警 |
| `Application/Common/Ota` | `app_ota` | 通用 Flash/HTTP OTA 基础能力 |
| `Application/Common/TcpClientSession` | `app_tcp_client_session` | 无任务、无队列的 TCP 会话状态 |
| `Application/Transport` | `app_transport` | UART/TCP 字节传输 |
| `Application/ProtocolStack/ModbusPort` | `app_modbus_port` | Modbus 端口适配 |
| `Application/New_Party/nanoMODBUS` | `nanomodbus` | 第三方 Modbus 栈 |
| `Application/DeviceLibrary/Robot/Dobot` | `device_dobot` | Dobot 原生设备驱动和点表数据结构 |
| `Application/DeviceLibrary/CoffeeMachine` | `device_f200`、`device_coffee_o`、`device_coffee_x`、`device_coffee_m50` | F200 自有协议驱动；O/X/M50 为 Modbus RTU 设备驱动 |
| `Application/DeviceLibrary/CupLidController/ShengShu` | `device_cup_lid` | 晟枢杯/盖驱动 |
| `Application/DeviceLibrary/SyrupMachine/CurrentModbus` | `device_syrup` | 糖浆机 Modbus 驱动 |
| `Application/DeviceLibrary/IceMachine/CurrentModbus` | `device_ice` | 制冰机 Modbus 驱动 |
| `Application/DeviceLibrary/Scale/BSQ_DG_V2` | `device_scale` | 称重设备驱动 |
| `Application/DeviceLibrary/PowerMeter/DDSU666` | `device_power_meter` | 电能表驱动 |
| `Application/DeviceLibrary/IoModule/ModbusDigitalIo` | `device_io` | 数字 IO 驱动 |

`DeviceLibrary/Inc/device_library.h` 和各设备目录中的头文件是公共契约。驱动只
接收调用方提供的设备上下文/传输参数并返回设备结果；它不创建 target 任务、队列，
不写 Coffee2 image，不解释上位机寄存器。

`DeviceLibrary/CoffeeMachine/coffee_machine_O.*`、`coffee_machine_X.*` 和
`coffee_machine_m50.*` 是按型号拆分的公共 Modbus RTU 驱动。O/X 分别读取 16/24
个状态寄存器，并提供制作、暂停/恢复、关机/重启、清洗、取消和故障复位；M50
按 Coffee1 已验证的 16 寄存器和 0x2000/0x200C/0x200D/0x200E 控制集合实现。
三者均在公共 CMake 目标和 Keil 公共 DeviceLibrary 组中独立列出，任何 target
可以按需选择，不包含 Coffee2 业务绑定。
`ProtocolStack/Modbus` 目录仍是 legacy，不在当前正式构建链中。

公共诊断核心不 include 任一 target 的日志端口。`app_crash_diag.c` 只调用弱公共
`lAppCrashDiagWrite()`；当前 Coffee2 在自己的 `coffee2_crash_log_port.c` 中提供强
绑定，其他 target 可以提供不同输出实现或保留默认空实现。

`MDK-ARM/STM32F407_Base.uvoptx`、`uvguix.*` 和旧 Objects 日志是 Keil 的调试/UI
缓存，可能保留历史 target 或已删除文件名；它们不决定编译输入。当前构建清单和
虚拟目录以 `STM32F407_Base.uvprojx` 为准，若需清理 UI 缓存可由 Keil 重新生成。

### 3.2 另一个 target 如何使用公共层

未来只需在其 target 分支中声明私有 app，并选择公共目标；不需要复制公共驱动，也
不需要创建 `DeviceProtocol`：

```cmake
add_library(other_app OBJECT
    UserAPP/OtherApp/WorkFlow/other_workflow.c
    UserAPP/OtherApp/Bus/other_bus.c
)
target_include_directories(other_app PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/UserAPP/OtherApp/...
)
target_link_libraries(other_app PRIVATE
    product_interfaces      # Common/Transport/DeviceLibrary 头文件契约
    device_f200             # 需要 F200 时选择
    device_scale            # 需要秤时选择
    app_modbus_port         # 只有 Modbus 设备才选择
)
```

Keil 采用相同原则：公共组保留一次，target 的 `IncludeInBuild` 决定选择哪些
设备库源文件；不需要的设备可以排除，不会进入链接。公共组本身不包含任何
`UserAPP/Coffee2App` 路径。

## 4. 私有层定义：每个 target 自己拥有

私有代码只放在 `Application/UserAPP/<Target>`，只由该 target 编译。当前 Coffee2
私有目录如下：

```text
Application/UserAPP/Coffee2App/
├─ Config/              业务常量、协议/设备选择、任务配置
├─ Comm_Log/            Coffee2 source、重定向和崩溃日志桥接
├─ Device/              Coffee2 设备绑定及 coffee2_device_image 状态投影
├─ IO_State/            Coffee2 IO 语义
├─ Modbus_Rtu_Bus/      Coffee2 总线 owner、命令执行、取消和结果提交
├─ Modbus_Tcp_Server/   上位机寄存器/服务器语义
├─ Ota/                 coffee2_ota.c/.h 私有 OTA 流程编排
├─ Robot_Tcp/           机器人 TCP owner、Coffee2 动作点表和状态机
├─ Task_Manager/        Coffee2 任务/队列创建
└─ WorkFlow/            Coffee2 订单业务流程
```

`coffee2_device_image.*` 现在物理位于 `UserAPP/Coffee2App/Device`，是 Coffee2
私有状态，不是公共设备模型；它记录业务可见状态，不能被公共驱动 include。
`coffee2_rtu_bus.*` 也是 Coffee2 私有总线 owner，虽然目录名包含 Modbus，仍不
代表公共协议层。

## 5. 命令体系决策

命令是业务输入，不是设备库职责。每个 target 自己定义：

- 命令枚举/参数布局（例如 Coffee2 的 `Coffee2Action_e`、`Coffee2Command_t`）；
- 队列、超时、重试、取消、order/transaction 关联；
- 命令到设备库 API 的映射；
- 结果到该 target 状态/image/寄存器的投影。

不建立公共运行时 `CommandManager`、Router 或 Adapter。多个 target 的命令形状
相似时，可以复制一个私有模板后修改；复制的是业务编排，不复制 DeviceLibrary
驱动。这样避免为了“统一接口”把产品语义塞回公共层。

当前 Coffee2 的 RTU owner 直接调用 `device_f200`、`device_cup_lid`、`device_syrup`、
`device_ice`、`device_scale`、`device_power_meter`、`device_io`；Robot owner
直接使用 `device_dobot` 的公共配置/解析数据结构。原 `Application/DeviceProtocol`
转发文件和 `Application/Common/Command/app_command.h` 已删除。

## 6. GCC 与 Keil 的组合规则

### GCC

- `product_interfaces` 只导出公共头文件路径和平台接口，绝不导出 Coffee2 私有路径。
- `app_*` 与 `device_*` 公共目标在产品分支外声明，任何未来 target 都可选择链接。
- `coffee2_app` 只加入 Coffee2 源文件，并用 `PRIVATE` include path 指向自己的子目录。
- `PRODUCT_LINK_TARGETS` 是当前产品的最终组合清单；未来 target 增加自己的 app
  和清单即可，不改公共驱动源码。
- 当前 `CMakePresets.json` 仅暴露 Coffee2 Debug/Release；新增 target 时应新增其
  私有 app 分支和 preset，不把未重写的 MilkTea 重新接回当前构建。
- 生成的 `freertos.c` 是唯一需要看到 `coffee2_manager.h` 的启动组合根；GCC 仅把
  `Task_Manager` 路径作为最终产品 executable 的 `PRIVATE` include，不传播给公共目标。
- 当前 `GCC-ARM/CMakeLists.txt` 的 CubeMX 源根仍指向已签入的
  `CubeMX_Base` 生成输出；维护输入登记为 `CubeMX_Base/CubeMX_Genarate/CMAKE`
  和 `.../MDK`，不得直接编辑生成输出或 `.ioc`。

### Keil

当前 `MDK-ARM/STM32F407_Base.uvprojx` 只保留一个 `Coffee2` target，虚拟目录为：

```text
Application/Common
Application/Coffee2App
Application/DeviceLibrary
Application/Transport
Application/ProtocolStack/ModbusPort
Application/New_Party/nanoMODBUS
```

生成的 HAL/FreeRTOS/lwIP、CMSIS、BSP 组保持在工程原有位置。`Application/Coffee2App`
包含 Coffee2 私有源（含 `coffee2_device_image.c` 和 `coffee2_ota.c`）；公共设备源
只在 `Application/DeviceLibrary` 出现一次；没有 `DeviceProtocol` 组，也没有旧 OTA
私有源。Keil 的 `IncludePath` 是 target 级属性，因此 Coffee2 编译命令会同时列出
公共目录和 Coffee2 私有目录；这不改变源码边界，公共源码仍禁止 include 任一
`UserAPP` 头文件。未来 target 可以复用公共组，新增自己的 `Application/<Target>App`
组，通过 `IncludeInBuild` 选择设备，而不是修改公共代码来适配业务。

## 7. 禁止事项与维护入口

1. 公共代码不得 include `UserAPP`，不得引用 Coffee2 命令、寄存器、image 或物理
   UART/IP 绑定；`CommonTargets.h` 仅作为启动组合根例外。
2. 不要重新建立 `DeviceProtocol` 目录来包装设备库；只有当未来出现真正跨产品、
   与具体设备无关的协议栈能力时，才在 L2 评审后新增公共模块。
3. 不编辑 `CubeMX_Base/F407Base.ioc`。CubeMX 配置维护使用
   `CubeMX_Base/CubeMX_Genarate/CMAKE/F407Base_CMAKE.ioc` 和
   `CubeMX_Base/CubeMX_Genarate/MDK/F407Base_MDK.ioc`，生成输出中的 USER CODE
   变更必须按专门流程处理。
4. 任何新增/移动/删除文件必须追加根目录 `CHANGES.md`；构建和硬件烧录状态必须
   用 `CONFIRMED/HISTORICAL/UNKNOWN/OUT_OF_SCOPE` 标注。
