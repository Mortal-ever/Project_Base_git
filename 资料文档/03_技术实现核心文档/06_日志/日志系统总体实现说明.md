## 1. 日志系统实际分层

Coffee2 日志分为**两层**，经独立 Product 适配层访问公共核心。CONFIRMED。

| 层 | 目录 | 文件 | 归属 |
| --- | --- | --- | --- |
| 公共日志核心 | `Application/Common/Log` | `app_log.c/.h` | 公共层，target-neutral |
| Coffee2 日志适配 | `Application/UserAPP/Coffee2App/Comm_Log` | `coffee2_log.c/.h`、`coffee2_crash_log_port.c`、`coffee2_retarget.c`、`app_comm_log_port.h` | Coffee2 私有层 |

### 1.1 输出端口与通道

- 日志输出端口：**USART1**（`huart1`）。CONFIRMED，见 `coffee2_log.c`：`xUartConfig.pxUart = &huart1`。
- 创建 Transport：`xTransportUartCreate()`，通道名 `"coffee2_log_uart"`（`coffee2_log.c:80-82`）。
- 静态上下文：`s_xCoffee2LogChannel`（通道）+ `s_xCoffee2LogTransport`（UART 后端，置于普通 SRAM 供 DMA 使用）。CONFIRMED。

### 1.2 队列、缓存与任务

| 项 | 值 | 来源 |
| --- | --- | --- |
| 日志 ring 长度 | `APP_LOG_RING_LENGTH = 32` 条 | `app_log.c:25` |
| 事件文本长度 | `APP_LOG_TEXT_LENGTH = 72` 字节（含终止符） | `app_log.c:27` |
| 字段名长度 | `APP_LOG_FIELD_LENGTH = 24` 字节 | `app_log.c:29` |
| 单行输出长度 | `APP_LOG_LINE_LENGTH = 160` 字节 | `app_log.c:31` |
| 覆盖策略 | overwrite-oldest（满则覆盖最旧） | `app_log.c:299-311` |
| 唤醒机制 | 静态二进制信号量 `s_xLogSignal` 合并生产者唤醒 | `app_log.c:74` |
| 日志任务 | `vCoffee2LogTask` → `vAppLogTask` | `coffee2_log.c:174`、`app_log.c:391` |
| 任务创建 | `coffee2_manager.c:315`，`"C2Log"`，栈 256，优先级 idle+2 | CONFIRMED |

### 1.3 日志等级

`APP_LOG_LEVEL_INFO(0) / WARNING(1) / ERROR(2)`，共 3 级，**无 DEBUG 级**。CONFIRMED，`app_log.h:45-50`。Coffee2 层 `COFFEE2_LOG_LEVEL_*` 为同一数值的别名（`coffee2_log.h:44-49`）。

### 1.4 日志 source

Coffee2 定义 18 个 source（`coffee2_log.h:56-76`），映射为稳定文本前缀（`coffee2_log.c:25-45`）。见本文件第 4 节。

### 1.5 接口家族

- 文本/结构化/格式化接口：见本文第 3 节。
- printf 风格：`xCoffee2LogPrintfOrder()`，内部 `vsnprintf` 到 72 字节栈缓冲（`coffee2_log.c:147-165`）。
- 启动期日志：`lCoffee2LogEarlyWrite()` → `lAppLogEarlyWrite()`（调度器前轮询输出）。
- 运行期日志：`xCoffee2LogWrite*` 系列 → `xAppLogWrite*`（进 ring）。
- 崩溃日志：`coffee2_crash_log_port.c` 的 `lAppCrashDiagWrite()` 强绑定，见《崩溃死机日志机制说明》。

## 2. Coffee2 当前日志调用链

```text
Coffee2 业务模块 (Workflow/Robot/Bus/Server/IO/OTA)
   -> Coffee2 日志适配层 (coffee2_log.c: xCoffee2LogWrite* / Printf / Field)
   -> Common Log (app_log.c: xAppLogWrite*)
   -> 静态 ring (s_axLogRing[32], APP_CCM_DATA)
   -> 二进制信号量唤醒 (s_xLogSignal)
   -> 日志任务 (vCoffee2LogTask -> vAppLogTask)
   -> Transport UART (USART1, transport_uart)
   -> UART 输出
```

对每一级的行为（CONFIRMED）：

| 级 | 文件/函数 | 数据结构 | 调用线程 | 是否阻塞 | 允许 ISR | 失败行为 | 是否丢日志 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 业务层调用 | `coffee2_log.c` | — | 各业务任务 | 否 | **否**（头文件 `@warning Do not call from interrupt`） | 返回错误码 | 由上层忽略 |
| 公共写入 | `app_log.c` `xAppLogWriteOrder/Field` | `AppLogEntry_t` 入 ring | 任务上下文 | 否 | 否 | `APP_LOG_RESULT_NOT_READY/INVALID_ARG` | 满时覆盖最旧 |
| 消费 | `vAppLogTask` `app_log.c:391` | 从 ring 取 `AppLogEntry_t` | C2Log 任务 | 部分（send 有 100ms 超时） | — | send 失败置 `ulTransmitFailureCount` | send 失败丢弃该条 |
| 输出 | `transport_uart` USART1 | TransportChannel | C2Log 任务 | 部分 | — | 重试退避 100~1000ms | 见上 |

> 说明：生产端不动态分配、不阻塞；唯一可能"丢日志"发生在 ring 满（覆盖最旧）或 Transport 发送失败（计数 + 丢弃）。CONFIRMED。

## 5. 日志行为约束（当前工程经验）

依据 `日志设计与诊断行为规则.md` 与源码实际，CONFIRMED 的约束：

1. 日志不要求所有平台统一格式（Coffee2 用 `[<seq>LEVEL][Task:Module] EVENT result=N field=V` 风格）。
2. 当前 Coffee2 使用英文 ASCII 事件/字段名，避免 ARMCC V5.06 与 GCC 的编码差异。
3. 关键日志必须能回答：哪个模块/设备、动作、阶段、结果、错误上下文。
4. 不能只打 `result=-4`；需给设备名/ID/寄存器/动作。
5. 周期轮询不持续打正常日志；仅状态变化/异常/超时/恢复/调试模式输出。
6. IO 日志边沿触发，首次仅建基线。
7. 初始化失败不被重试无限刷屏（同阶段只提示一次）。
8. 文本/结构化/混合均可，不为统一而降低可读性。
9. 考虑 Flash/RAM/CPU/串口带宽；ISR 不调用阻塞日志。

## 6. 当前日志问题审查

> 每个问题含：文件、函数、触发条件、当前输出、诊断影响、严重度、是否需要源码修改。

### A. 初始化/指令失败重复打印（P1，已处理）
- 文件：`coffee2_workflow.c`（`vCoffee2WorkflowTask` 初始化循环）。
- 触发：机器初始化步骤失败（如 `MACHINE_INIT_BLOCKED result=-1007`）。
- 当前：`lLastInitError` 去重，错误值不变时不重复打 `MACHINE_INIT_BLOCKED`（CONFIRMED，`coffee2_workflow.c:407-414`）。
- 诊断影响：初始化阻塞有去重；底层 `BUS_COMMAND_FAILED` 仍可能按状态变化出现。
- 是否需修改：去重已实现，非必须。

### B. `BUS_COMMAND_FAILED`（P1，已部分处理）
- 文件：`coffee2_rtu_bus.c`（`prvLogCommandFailure`）。
- 触发：Modbus/设备命令失败。
- 当前：仅当 `lLastResult` 与本次结果不同时输出（去重），事件含 `device` ID 字段（CONFIRMED，`coffee2_rtu_bus.c:567-580`）。
- 诊断影响：能区分设备 ID；个别日志仅数字 ID，需结合 source 前缀定位。
- 是否需修改：可选。

### C. 设备号与设备名不一致/缺失（P1，可选）
- 触发：`BUS_COMMAND_FAILED` 用 `device=N` 数字 ID。
- 当前：source 前缀已提供英文模块名（如 `IoOutput`），device 字段提供数字 ID。
- 诊断影响：前缀 + device 组合已可定位；数字 ID 单独不直观。
- 是否需修改：可选（建议在无前缀日志补充名称）。

### D. IO 状态变化点位定位（P2，依赖编译状态）
- 触发：IO 状态变化。
- 当前：`coffee2_io.c` 使用 `COFFEE2_IO_NAME_*` 英文点位名（部分构建存在编译告警，见 CONFLICT）。
- 是否需修改：视编译告警而定。

### E. Modbus 失败上下文（P2，可选增强）
- 触发：Modbus 超时/异常。
- 当前：`BUS_COMMAND_FAILED result=-4 device=N` 含 device 但未直接含功能码/寄存器。
- 是否需修改：可选增强。

### F. 机器人动作名（P2，已提供）
- 触发：机器人动作。
- 当前：日志事件含 action 数值（如 `ROBOT_ACTION_START=114`）。动作名 map 由 `coffee2_robot_tcp.c` 解析。
- 是否需修改：可选。

### G. OTA 阶段/原因（P2，已提供）
- 触发：OTA 各阶段。
- 当前：`coffee2_ota_*.c` 输出 `OTA_HTTP_*`、`OTA_FLASH_*` 等事件（CONFIRMED）。
- 是否需修改：可选。

### H. ARMCC V5.06 编码风险 / GCC-Keil 一致性（P0，需核）
- 已确认 Coffee2 日志事件名采用 ASCII，规避中文字符串差异。CONFIRMED。
- `coffee2_crash_log_port.c` 内注释含中文（不影响字符串），建议保持代码内注释 ASCII 化。
