# 奶茶机死机日志管理与排障说明

> 适用工程：MilkTea STM32F407 + FreeRTOS + Keil MDK V5.06
>
> 当前实现日期：2026-07-23
>
> 输出介质：日志模块已注册的 UART；当前默认是 USART1

## 1. 功能边界

死机日志是普通 LOG 任务之外的一条独立应急通道，用于系统已经不能继续调度时输出：

1. Cortex-M4 最近一次异常寄存器快照和 SCB 故障寄存器。
2. FreeRTOS 已登记任务的句柄、名称、优先级、栈范围和栈高水位。

当前接管以下致命入口：

| 入口 | `reason` | 说明 |
| --- | --- | --- |
| HardFault | `HARD_FAULT(1)` | 强制升级或无法分类的硬件异常 |
| MemManage | `MEM_MANAGE(2)` | MPU/内存管理异常 |
| BusFault | `BUS_FAULT(3)` | 总线访问异常 |
| UsageFault | `USAGE_FAULT(4)` | 非法指令、非法状态、除零等 |
| FreeRTOS 栈溢出钩子 | `STACK_OVERFLOW(5)` | `configCHECK_FOR_STACK_OVERFLOW=2` 检测到任务栈越界 |
| FreeRTOS 内存分配失败钩子 | `MALLOC_FAILED(6)` | `pvPortMalloc()` 无法满足申请 |
| `configASSERT` | `ASSERT(7)` | 内核或工程断言失败 |

这条通道不进入结构化日志队列，不等待 LOG 任务，不使用任务通知、信号量、动态内存、
`printf`、HAL Tick 或 FreeRTOS API。

## 2. 运行流程

```text
异常或 FreeRTOS 致命钩子
  -> ARMCC 汇编入口立即关闭中断
  -> 保存 R4~R11、MSP、PSP
  -> 异常时选择硬件压栈使用的 MSP/PSP
  -> 切换到 MSP，避免继续使用可能损坏的任务栈
  -> C 层冻结一次日志文本
     -> 第一部分：核心寄存器和 SCB 快照
     -> 第二部分：任务句柄和现场计算的栈高水位
  -> 清除已注册日志 UART 的 DMAT 请求
  -> 直接轮询 UART TXE/TC 输出
  -> DWT CYCCNT 等待 10 秒
  -> 重发同一份冻结文本，永久循环
```

第一次输出不等待 10 秒。10 秒只位于本次输出完成与下一次重发之间。

## 3. 为什么任务栈水位在死机现场采样

正常运行期间没有周期扫描任务栈，也没有在 LOG 任务每次运行时调用
`uxTaskGetSystemState()`或`uxTaskGetStackHighWaterMark()`。

当前开销只有：

- 任务创建时复制一次句柄、名称、栈上下界和优先级。
- 任务删除时把对应记录标记为无效。
- 每次任务切换时执行一次当前任务句柄指针赋值。
- 每个 FreeRTOS TCB 因`configRECORD_STACK_HIGH_ADDRESS=1`增加一个栈末端指针。

真正的 0xA5 栈填充值扫描只发生在系统已经进入死机处理之后。因此不会给 LOG 任务增加
周期负担，也不会在正常业务期间扫描 CCM。

## 4. CCM 与栈范围保护

FreeRTOS heap 当前位于 CCM，动态创建的 TCB 和任务栈也会来自 CCM。CPU可以读取 CCM，
所以死机现场允许扫描以下两个完整地址区间：

| 内存 | 允许范围 |
| --- | --- |
| CCM | `0x10000000` ~ `0x1000FFFF` |
| SRAM | `0x20000000` ~ `0x2001FFFF` |

每条任务记录还必须同时满足：

- 栈低地址不大于栈高地址。
- 两个地址都是 4 字节对齐。
- 完整栈范围不跨越 CCM/SRAM 边界。
- 单任务栈不超过`APP_CRASH_MAX_STACK_BYTES`，默认 16 KB。

任何一项失败都不会继续解引用该范围，日志输出`hwm=INVALID_RANGE`。这样可以避免损坏的
TCB或任务记录在死机处理过程中制造第二次异常。

高水位字段表示任务运行历史中最少剩余的连续未使用栈空间：

```text
hwm_words=123 hwm_bytes=492
```

数值越小越危险；`hwm_words=0`表示已经没有可确认的安全余量，应立即增加栈或减少局部
大数组和深层调用。

## 5. 第一部分：寄存器快照

典型输出：

```text
[CRASH][CAPTURE] source=EXCEPTION
[CRASH][BEGIN] reason=HARD_FAULT code=1 current_handle=0x10001234
[CRASH][CORE] EXC_RETURN=0xFFFFFFFD FRAME_SP=0x10001820
[CRASH][CORE] R0=0x00000000 R1=0x20001000 R2=0x00000004 R3=0x00000000
[CRASH][CORE] R12=0x00000000 LR=0x08004567 PC=0x08001235 XPSR=0x21000000
[CRASH][CORE] R4=0x00000000 R5=0x00000000 R6=0x00000000 R7=0x00000000
[CRASH][CORE] R8=0x00000000 R9=0x00000000 R10=0x00000000 R11=0x00000000
[CRASH][STACK] MSP=0x2001FF00 PSP=0x10001820 CONTROL=0x00000002 PRIMASK=0x00000001 BASEPRI=0x00000000 FAULTMASK=0x00000000
[CRASH][SCB] CFSR=0x00008200 HFSR=0x40000000 DFSR=0x00000000 AFSR=0x00000000
[CRASH][SCB] MMFAR=0xE000ED34 BFAR=0xDEADBEEF SHCSR=0x00070008 ICSR=0x00400803
[CRASH][DECODE] FORCED PRECISERR BFARVALID
```

字段解释：

| 字段 | 用途 |
| --- | --- |
| `current_handle` | 最近一次被调度进入运行态的任务句柄 |
| `EXC_RETURN` | 判断异常前使用 MSP/PSP、是否存在浮点扩展帧 |
| `FRAME_SP` | Cortex-M 硬件异常帧起始地址 |
| `R0~R3/R12` | 异常发生时由硬件保存的通用寄存器 |
| `LR` | 异常发生点的返回地址 |
| `PC` | 最重要的故障指令地址，可在 map/listing 中定位 |
| `XPSR` | Thumb 状态、异常号和条件标志 |
| `R4~R11` | 汇编入口进入 C 之前保存的被调用者寄存器 |
| `MSP/PSP` | 进入处理器时两个栈指针的快照 |
| `CFSR/HFSR` | MemManage、BusFault、UsageFault 和强制升级原因 |
| `MMFAR/BFAR` | 地址有效位成立时的非法内存/总线访问地址 |

`[CRASH][DECODE]`只给出常用位的快速提示，最终判断仍以原始 SCB 数值和 Cortex-M4
手册为准。

## 6. 第二部分：FreeRTOS 任务健康

典型输出：

```text
[CRASH][RTOS] registered_tasks=7 registration_drops=0
[CRASH][TASK] name=LOG handle=0x10000110 current=0 priority=3 stack_low=0x10000160 stack_high=0x1000055C hwm_words=92 hwm_bytes=368
[CRASH][TASK] name=MilkTeaApp handle=0x10002000 current=1 priority=2 stack_low=0x10002050 stack_high=0x1000304C hwm_words=301 hwm_bytes=1204
[CRASH][END] repeat_seconds=10
```

字段解释：

| 字段 | 含义 |
| --- | --- |
| `registered_tasks` | 当前有效任务记录数，包括 FreeRTOS Idle/Timer 任务 |
| `registration_drops` | 任务数超过固定记录容量而未登记的次数，正常应为 0 |
| `name` | 任务创建时复制的独立名称，不在死机时读取 TCB 名称 |
| `handle` | FreeRTOS 任务句柄，也就是 TCB 地址 |
| `current` | `1`表示最近一次切入运行的任务，优先检查该任务 |
| `priority` | 创建时记录的任务优先级 |
| `stack_low/high` | 创建时记录的完整栈边界 |
| `hwm_words/bytes` | 死机现场扫描 0xA5 得到的历史最小剩余空间 |

若任务运行期动态修改过优先级，当前日志中的`priority`仍是创建时值；任务句柄、栈边界和
高水位不受此限制。

## 7. 串口输出规则

死机输出只使用`xAppCommLogPortRegister()`已经登记的日志 UART。当前登记点仍是：

```c
static UART_HandleTypeDef * const s_pxLogUart = &huart1;
```

切换到其他串口后，普通日志和死机日志会一起跟随该注册点，不需要在 Diagnostics
模块再次配置串口号。

死机路径不调用统一 Transport 的正常发送接口，因为正常接口依赖互斥锁、DMA完成中断和
任务调度。它直接使用同一注册上下文中的 UART 寄存器：

1. 清除`USART_CR3_DMAT`，停止新的 DMA 请求。
2. 有界等待 TXE，逐字节写 DR。
3. 有界等待 TC，确认最后一个停止位发送完毕。
4. 等待期间按配置刷新 IWDG。

即使 CubeMX 给该 UART 配置了 TX DMA，死机日志仍统一使用轮询阻塞发送。

限制：

- 若死机发生在日志 UART 注册完成之前，没有可用的注册串口，无法输出。
- 若 UART 时钟、GPIO、发送器或外部收发器已经损坏，软件不能保证送达。
- 当`APP_COMM_LOG_UART_OUTPUT_ENABLE=0`时，死机串口输出也关闭。
- HTTP后端不参与死机输出，因为 lwIP 和调度器在现场不再可信。

## 8. DWT 延时与看门狗

唯一延时源是 Cortex-M4 的 DWT `CYCCNT`，不使用`HAL_Delay()`、`osDelay()`、
`vTaskDelay()`或 FreeRTOS Tick。

默认每 100 ms 完成一个短等待区间并执行一次看门狗刷新，累计 10 秒后重发：

```c
#define APP_CRASH_REPEAT_SECONDS                10U
#define APP_CRASH_WATCHDOG_REFRESH_HZ           10U
```

STM32F4 的 IWDG 启动后不能由软件关闭，因此最终策略是“继续喂狗”，不是尝试关闭它。
当前工程没有启动 IWDG，所以默认：

```c
#define APP_CRASH_IWDG_REFRESH_ENABLE            0U
```

未来 CubeMX 或启动代码启用 IWDG 时，必须同步改为`1U`并进行板级验证。刷新函数只直接
写`IWDG->KR=0xAAAA`，不调用 HAL。当前实现不支持 WWDG。

## 12. 排障顺序

收到死机日志后按以下顺序：

1. 保存从`[CRASH][CAPTURE]`到`[CRASH][END]`的完整一轮，不要只截最后几行。
2. 看`reason`和`[CRASH][DECODE]`确定大类。
3. 用`PC`和`LR`在同版本`MilkTea.map`或 Keil Disassembly 定位函数。
4. CFSR 中地址有效位成立时检查`BFAR`或`MMFAR`。
5. 找`current=1`任务，检查它的栈水位和最近普通业务日志。
6. 检查所有任务的`hwm_words`，优先处理接近 0 或`INVALID_RANGE`。
7. 若`registration_drops`非 0，增大`APP_CRASH_MAX_TASKS`并重新构建。
8. 必须保留产生日志的 HEX、AXF、map 和源码版本，其他构建的地址不能直接套用。

## 13. 板级验证建议

发布前至少完成：

1. 正常启动和业务日志不受影响。
2. 在受控测试版本触发`configASSERT(0)`，确认第一轮立即输出且每 10 秒重发。
3. 在受控测试版本触发非法地址访问，确认`PC/CFSR/BFAR`有效。
4. 人为缩小测试任务栈，确认栈溢出钩子能打印对应句柄和名称。
5. 切换日志注册到无 TX DMA 的 UART，确认普通日志和死机日志同时迁移。
6. 若启用 IWDG，确认连续观察一分钟不会复位。
7. 若关闭 UART 输出宏，确认正常业务不崩溃，并接受“没有死机串口日志”的结果。

测试触发代码不能保留在量产路径中。

## 14. 当前临时CCM边界故障注入

为了验证本套死机日志，当前LOG任务已经临时启用：

```c
#define APP_COMM_LOG_CCM_FAULT_INJECTION_ENABLE    1U
```

LOG任务处理完自己的`[LOG][OUTPUT] BACKEND`启动日志后，会向`0x10010000`写入一个
32位测试值。STM32F407的CCM有效范围止于`0x1000FFFF`，因此该地址是CCM末端之外的
第一个地址，CPU访问应触发BusFault；当前未单独使能BusFault时通常升级为HardFault。

预期串口顺序：

```text
[...][I][LOG][OUTPUT] BACKEND ...
[CRASH][CAPTURE] source=EXCEPTION
[CRASH][BEGIN] reason=HARD_FAULT ...
...
[CRASH][END] repeat_seconds=10
```

完整死机文本会每10秒重复一次。测试完成后必须把宏改为`0U`；量产前还应删除
`app_comm_log.c`中带有`TEMPORARY CCM FAULT INJECTION TEST`注释的调用块和
`prvInjectCcmBoundaryFault()`函数。
