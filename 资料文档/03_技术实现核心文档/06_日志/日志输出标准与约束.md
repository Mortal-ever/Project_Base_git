# 日志输出标准与约束

> 适用范围：Project_Base 当前 STM32/Coffee2，以及后续接入同一公共日志核心的
> Coffee3Close 等 target。  
> 文档性质：输出行为规范；源码调用链和内存/任务实现见《日志系统总体实现说明.md》。  
> 状态：CURRENT / NORMATIVE（规范）；Coffee3 的 source 表在代码接入前仍属于 PROPOSED。  
> 编写日期：2026-09-07

## 1. 这份标准解决什么问题

日志的目的不是“把事件编码成一串固定字段”，而是让开发者和自动化分析工具在不
翻源码的情况下回答：

1. 哪个 target、任务、总线或设备在输出；
2. 对哪个对象执行了什么动作，处于什么阶段；
3. 结果是成功、等待、失败、超时、恢复还是被业务门禁拒绝；
4. 需要继续排查时，能拿到设备 ID、订单号、IO 宏名、寄存器、错误码或超时信息。

因此，本工程同时约束**稳定的来源前缀**和**可读的正文**，但不强迫所有正文使用
`EVENT result=... field=...` 模板。正文可以是自然语言、宏名、少量键值，或者两者
的组合，只要信息完整且长度受控。

## 2. 与当前源码实现的对应关系（CONFIRMED）

### 2.1 公共核心负责什么

`Application/Common/Log/app_log.c/.h` 是 target-neutral 的异步日志核心：

- `AppLogSourceDescriptor_t` 保存静态 `pcTaskName` 和 `pcModuleName`；
- `xAppLogInit()` 接收 target 私有 source 表和可选 Transport；
- `xAppLogWrite*()` 把有界记录写入静态 ring，不动态分配；
- `vAppLogTask()` 是唯一输出消费者；
- ring 长度为 32 条，正文最大 72 字节，最终输出行最大 160 字节；
- `xAppLogWriteTextOrder()` 专门用于不追加 `result`/`field` 的人类可读正文；
- `xAppLogWriteField*()` 用于确实需要标准化结果和字段的诊断记录；
- 日志写入接口是任务上下文接口，禁止在 ISR 中调用。

实现依据：`app_log.c:25-31, 239-320, 391-435, 461-499`，
`app_log.h:52-74, 108-200`。

### 2.2 Coffee2 适配层负责什么

`Application/UserAPP/Coffee2App/Comm_Log/coffee2_log.c/.h` 负责：

- 定义 Coffee2 的 source ID 与稳定文本映射；
- 创建 USART1 日志 Transport；
- 将 Coffee2 API 转换到公共 `AppLog` API；
- 提供 `xCoffee2LogPrintfOrder()` 的有界 printf 风格入口；
- 创建 `C2Log` 消费任务并把输出交给公共核心。

适配层不能把事件名称临时拼到 source 前缀中。新增 source 必须新增静态表项和对应
枚举，不能在正文写一个看似 source 的动态名称。

### 2.3 当前行格式是如何生成的

公共核心当前按以下顺序拼接一行（`app_log.c:469-499`）：

```text
[ORDER_HEX4LEVEL][TASK:MODULE] BODY[ result=SIGNED][ FIELD=SIGNED]\r\n
```

例如：

```text
[0000INFO][C2Workflow:Workflow] order=123 content complete; continue final placement
[F123WARN][C2Bus5:IoInput] IO_INPUT_MODULE_16CH_COMMAND_FAILED result=-4 device=9
```

字段含义：

| 片段 | 规则 |
| --- | --- |
| `ORDER_HEX4` | 记录关联的 16 位订单/调试命名空间；`0000` 是系统日志，`F123` 可表示调试命名空间；它不是时间戳。 |
| `LEVEL` | 当前实现只有 `INFO`、`WARN`、`ERROR` 三级。 |
| `TASK` | source 表中固定的任务/总线/服务归属，例如 `C2Bus5`。 |
| `MODULE` | source 表中固定的设备类别或模块，例如 `IoInput`。 |
| `BODY` | 运行时正文，必须表达具体对象、动作、阶段和结果。 |
| `result/field` | 只有调用结构化 API 时由核心追加；不是每条日志的强制后缀。 |

其他 target 可以有不同的传输封装，但必须保留等价的稳定来源分类和可定位正文。
对于当前 STM32/Coffee2/Coffee3 适配，直接遵守上面的方括号格式。

## 3. source 前缀标准

### 3.1 source 是“代码归属”，不是“业务事件”

source 必须来自 target 的静态 source 表，表示负责产生这条日志的任务、总线或
模块。订单、出餐口、X4、门、客户取餐、初始化失败等属于**事件对象或事件阶段**，
应写在正文，不能临时变成 source。

错误示例（禁止）：

```text
[0000INFO][C3Outlet:Pickup] Outlet 1 empty for 30 s
[0000WARN][C3Water:OrderGate] X4 unavailable
[0000INFO][C3IoInput:Door] Order 123 placed at outlet 1
```

上面三个标签没有经过 target source 表注册，并且把业务对象/事件阶段伪装成代码
来源。它们会使分析者误以为存在 `C3Outlet`、`C3Water` 或 `C3IoInput` 任务。

正确示例（source 稳定，事件放正文）：

```text
[0000INFO][C3Workflow:Workflow] order=123 content complete; continue final placement
[0000INFO][C3Robot:MBTcpClient] order=123 placement complete; target=OUTLET_1
[0000WARN][C3Workflow:Workflow] order=123 complete; X4 unavailable; reject next order
[0000INFO][C3Bus5:IoInput] outlet=1 empty for 30 s; publish customer-take state
[0000INFO][C3Server:MBTcpServer] customer-take ACK received; release outlet=1
```

如果实际动作由其他已注册 source 所有，应使用实际 owner；不能为了让正文好看而
新建动态前缀。`C3Bus5:IoInput` 只有在 C3 source 表正式注册后才能进入固件。

### 3.2 source 命名规则

source 文本使用 ASCII、短、稳定且可 grep 的名字：

1. `TASK` 以 target 前缀开头（当前 Coffee2 为 `C2`，Coffee3 规划为 `C3`）；
2. 总线使用 `C2Bus2`、`C2Bus5` 等固定编号；业务任务使用 `C2Workflow`、
   `C2Server`、`C2Robot` 等固定名称；
3. `MODULE` 使用设备类别或服务类别，如 `MBRtu`、`IoInput`、`IoOutput`、
   `Workflow`、`MBTcpClient`；
4. 一个 source 表项对应一个稳定 owner，不随订单号、设备 ID、动作名变化；
5. 新增 source 必须同时更新 target 私有枚举、静态表和 target 日志说明文档；
6. 公共 `app_log` 核心不保存 Coffee2/Coffee3 名称，也不引用 UserAPP 头文件。

### 3.3 当前 Coffee2 source 基线（CONFIRMED）

以下映射来自 `coffee2_log.c:25-45`，是当前工程的实际基线：

| Source ID/用途 | TASK | MODULE |
| --- | --- | --- |
| SYSTEM | `C2Main` | `System` |
| SERVER | `C2Server` | `MBTcpServer` |
| WORKFLOW | `C2Workflow` | `Workflow` |
| ROBOT | `C2Robot` | `MBTcpClient` |
| BUS2/BUS3/BUS4/BUS5 | `C2Bus2`…`C2Bus5` | `MBRtu` |
| IO | `C2Workflow` | `IO` |
| COFFEE/CUP/SYRUP/LID | `C2Bus2`/`C2Bus3` | 对应设备名 |
| ICE/WEIGH | `C2Bus4` | 对应设备名 |
| ENERGY_METER | `C2Bus3` | `EnergyMeter` |
| IO_INPUT | `C2Bus5` | `IoInput` |
| IO_OUTPUT | `C2Bus5` | `IoOutput` |

Coffee3 不得直接复制事件名作为 source；应在其私有适配层建立自己的静态表。表项
尚未进入 Coffee3 源码前，文档中的 `C3...` 仅是 PROPOSED 设计名称。

## 4. 正文内容标准

### 4.1 最小信息集

正文至少包含下列信息中的必要集合：

| 日志类型 | 必须回答的问题 | 推荐正文元素 |
| --- | --- | --- |
| 设备命令失败 | 哪个设备、什么动作、为何失败 | `device=<name/id> action=<action> result=<code> stage=<stage>` |
| 超时 | 等待谁、等了多久、下一步是什么 | `device=<...> action=<...> timeout=<ms>; next=<...>` |
| 初始化 | 哪个阶段未完成、是否锁定 | `init stage=<...> failed; locked=<0/1>; action=...` |
| IO 边沿 | 哪个点位由什么变成什么 | `point=<MACRO> old=<0/1> new=<0/1>` |
| 业务状态 | 哪个订单在哪一步 | `order=<id> stage=<...>; next=<...>` |
| ACK | 确认消费了什么，是否释放资源 | `order=<id> ack=<...> consumed; release=<resource>` |
| 恢复 | 哪个对象从故障恢复 | `device=<...> recovered; state=<...>` |

正文不应只输出 `result=-4`、`step=64785` 或 `device=9`。数字必须和动作、阶段
或稳定的 source 结合；无法取得名称时至少保留 source、设备 ID、功能码/寄存器或
动作 ID。

### 4.2 可读正文优先于无意义模板

以下两种写法都允许，按诊断场景选择：

```text
[0000ERROR][C2Workflow:Workflow] order=123 final placement failed; target=OUTLET_1 result=-4
[0000WARN][C2Bus5:IoInput] IO_INPUT_MODULE_16CH_COMMAND_FAILED result=-4 device=9
```

不要求所有正常信息都加 `result=0`。成功、状态变化和下一步动作优先使用自然
语言；需要机器解析时再补 `key=value`。不要为了统一而输出无法解释的
`EVENT result=<int> field=<...>` 空壳。

### 4.3 ASCII 和工具链兼容

当前 ARMCC V5.06 与 GCC 共用源码，运行时日志正文和点位标识默认使用 ASCII：

- IO 点位使用 Coffee2/Coffee3 私有英文宏名，例如 `DI1_OUTLET_DOOR_UPPER_LIMIT`、
  `X4_PURE_WATER_BUCKET1_LOW_LEVEL`、`Y1_WATER_HEATER_RELAY`；
- 中文含义写入业务文档、对照表或上位机资料；
- 若 target 经过独立编码验证并允许 UTF-8，可在 target 适配层扩展，但不能破坏
  ARMCC/GCC 共用源码和现有串口解析；
- 任何正文仍受公共核心 72 字节限制，超长描述必须压缩为稳定短语和关键字段。

## 5. 日志级别

| 级别 | 使用条件 | 不应使用的场景 |
| --- | --- | --- |
| `INFO` | 正常开始/完成、状态边沿、ACK 消费、恢复、下一步动作 | 每次周期轮询、无变化的重复快照 |
| `WARN` | 可恢复异常、传感器异常、降级、禁止新单、重试或人工关注 | 把所有正常等待都当告警 |
| `ERROR` | 当前订单/初始化/安全动作真实失败、超时导致流程停止、不可安全继续 | 预期中的一次重试或普通设备轮询失败 |

级别描述影响，不描述设备类别。设备类别由 source 和正文决定；不要使用
`C3Outlet`、`C3Water` 等事件标签来“强化”级别含义。

## 6. 输出时机、去重与周期任务

### 6.1 允许输出的边界

周期任务可以持续刷新状态，但日志只在以下时机输出：

- 动作开始、完成、失败、超时；
- IO/设备状态第一次建立基线后的边沿变化；
- 离线、重新上线、故障码变化或恢复；
- 业务阶段变化（例如内容完成、最终放杯、门开始下降、客户取餐确认）；
- 明确开启的维护/调试命令的一次请求和一次结果。

首次采样只建立 IO 基线，不能把所有初始值当作“变化”。正常无变化的 50 ms/200 ms
刷新禁止持续打印。

### 6.2 初始化失败去重

初始化流程可以按业务需要重试，但同一设备、同一阶段、同一错误只输出一次；只有
错误变化、进入新阶段、设备恢复或人工复位重新开始时才允许再次输出。这样可以
保留真实失败事实，同时避免 `WORKFLOW_STEP_START/DONE/DEVICE_FAILED` 每个周期刷屏。

### 6.3 失败与恢复成对

设备离线/超时应记录失败上下文；恢复后再输出一条恢复日志。恢复日志不得伪造之前
未发生的成功动作，也不得清除业务状态中的未确认事件。

## 7. 订单、IO 和设备日志的具体要求

### 7.1 订单链路

Coffee3 订单可能同时存在“制作订单”和“出餐口等待客户订单”。当两者可能并存时，
正文必须带 `order=<id>`；如果一个出餐口事件与另一个线上订单并行，额外带
`outlet_order=<id>`，禁止只写“订单完成”造成串单误判。

推荐阶段词：`accepted`、`making`、`content complete`、`final placement`、
`outlet waiting`、`customer-take confirmed`、`released`、`rejected`。

### 7.2 IO 边沿

IO 变化日志应使用 target 私有英文宏名，并同时带旧值/新值：

```text
[0000INFO][C2Workflow:IO] point=DI1_OUTLET_DOOR_UPPER_LIMIT old=0 new=1
[0000INFO][C2Bus5:IoInput] point=X4_PURE_WATER_BUCKET1_LOW_LEVEL old=1 new=0
[0000INFO][C2Bus5:IoOutput] point=Y1_WATER_HEATER_RELAY old=0 new=1
```

首次读取没有 `old` 值时只建立基线；通信失效时输出一次失联/恢复，不把未知值伪造
成 0。输出调试命令要区分“请求接收”和“设备确认完成”。

### 7.3 Modbus/设备失败

最小可用示例：

```text
[0000WARN][C2Bus5:IoInput] IO_INPUT_MODULE_16CH_COMMAND_FAILED result=-4 device=9
[0000WARN][C2Bus5:IoInput] RTU_DEVICE_OFFLINE result=-4 device=9
```

如果同一 source 下有多个设备或多个寄存器，必须补 `device_name`、`unit`、
`function`、`address` 或 `action` 中至少一个，不能只给数字错误码。

## 8. Coffee3Close 第五版示例的修正规则

第五版业务文档中 `C3Outlet`、`C3Water`、`C3IoInput` 的示例应按以下原则解释和
修改：

| 原写法的问题 | 修正 |
| --- | --- |
| `C3Outlet:Pickup` 把出餐口/取餐事件当 source | 使用已注册的 owner，例如 `C3Bus5:IoInput` 或 `C3Server:MBTcpServer`，事件放正文 |
| `C3Water:OrderGate` 把缺水门禁当 source | 使用 `C3Workflow:Workflow`，正文写 `X4 unavailable; reject next order` |
| `C3IoInput:Door` 未体现实际总线/模块 owner | 使用实际已注册 IO source；若由机器人执行动作，使用 `C3Robot:MBTcpClient` |

建议的第五版示例：

```text
[0000INFO][C3Workflow:Workflow] order=123 content complete; continue final placement
[0000INFO][C3Robot:MBTcpClient] order=123 placement complete; target=OUTLET_1
[0000WARN][C3Workflow:Workflow] order=123 complete; X4 unavailable; reject next order
[0000INFO][C3Bus5:IoInput] outlet=1 empty for 30 s; publish customer-take state
[0000INFO][C3Server:MBTcpServer] customer-take ACK received; release outlet=1
```

这些 `C3...` 前缀只有在 Coffee3 私有 source 表完成注册后才可进入固件；本节不
宣称 Coffee3 源码已经接入。

## 9. Target 接入清单

每个 target 接入公共日志核心时，必须完成以下事项：

1. 在 target 私有目录定义 source ID 枚举和只读 `AppLogSourceDescriptor_t` 表；
2. 为每个 source 写清 TASK、MODULE、owner 和允许记录的事件范围；
3. 配置自己的 Transport；DMA 缓冲放在 DMA 可访问 SRAM，不能放 CCM；
4. 创建唯一日志消费者任务并调用 `vAppLogTask()`，不创建多个竞争消费者；
5. 对业务文本使用 `xAppLogWriteTextOrder()`，对确实需要解析的字段使用
   `xAppLogWriteField*()`；
6. 把 IO 名称、设备名和寄存器名集中在 target 配置，不在多个业务文件各写一份；
7. 对周期刷新、初始化重试和恢复事件实现边沿/状态去重；
8. 编译时检查 ARMCC V5.06 和 GCC 均可接受的 ASCII 运行时字符串、C90/C99 语法；
9. 为每个 target 维护单独的日志说明文档，列出 source 表、关键事件、级别和示例；
10. 不把 target 私有 source、业务枚举或寄存器语义反向放入公共核心。

## 10. 变更验收清单

新增或修改日志前后，必须至少验证：

- 正常开始、完成和下一步动作能读懂；
- 设备失败包含稳定 source、设备对象/ID、动作或阶段和错误码；
- 超时与普通失败可区分，并且有等待对象和后续动作；
- IO 首次采样不刷屏，状态变化包含宏名和 old/new；
- 初始化同一错误不会被重试周期刷屏；
- 离线和恢复各有一次清晰记录；
- 订单日志能区分制作、最终放杯、出餐口等待和客户取餐 ACK；
- 不出现未注册的 `C3Outlet`、`C3Water`、`C3IoInput` 等动态 source；
- 运行时正文不超过实现上限，ARMCC V5.06 与 GCC 使用相同含义；
- 只读检查 `git diff`、UTF-8/末尾换行、source 表和文档链接，未获授权不烧录。
