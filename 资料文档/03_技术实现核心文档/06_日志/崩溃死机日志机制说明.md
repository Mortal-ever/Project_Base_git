## 3. 崩溃输出路径

CONFIRMED。

- **路径**：崩溃文本冻结 → `lAppCrashDiagWrite()` → Coffee2 强绑定 `lAppCommLogPortCrashWrite()`（`coffee2_crash_log_port.c:18`）→ **LL-USART 轮询 huart1**。
- **依赖调度**：否。崩溃路径调度器无关，不依赖任务。
- **是否可能在 HardFault 中再次异常**：有防护——`s_ucCrashActive` 防重入、任务栈范围校验、UART 自旋 `APP_CRASH_UART_SPIN_LIMIT`。
- **是否依赖 DMA/中断**：否。崩溃前 `CLEAR_BIT(CR3, DMAT)` 清 DMA 传输，轮询 TXE/TC。
- **是否可能卡住看门狗**：`vAppCrashDiagWatchdogRefresh()` 默认关闭（`APP_CRASH_IWDG_REFRESH_ENABLE=0`）。若实际使能则会在崩溃循环刷新 IWDG。
- **下次启动读取上次崩溃**：NOT_IMPLEMENTED。崩溃文本只在当前崩溃现场重复输出，不写入 Flash/Backup SRAM（UNKNOWN 需核）。
- **固定长度/校验/版本**：文本缓冲 `APP_CRASH_TEXT_BUFFER_SIZE=4096`、报告含 `CRASH_*` 标记与重复周期 `REPEAT_SECONDS`；无显式校验字段（UNKNOWN）。

## 7. 源码带读：从崩溃捕捉到串口输出的完整实现

### 7.0 实现全景：四个层次各自的职责边界
```
层次          文件                      职责                        使用的 CPU 资源
────────────────────────────────────────────────────────────────────────────────
L1 汇编包装  app_crash_fault_*.S       保现场、选栈、传参           R0-R2(参数)、R3(临时)
L2 C 入口    app_crash_diag.c:         防重入、冻结一次报告         s_ucCrashActive
             vAppCrashDiag*Entry
L3 报告构建  prvBuild*Text 一族        顺序拼接文本到单静态缓冲     s_aucCrashText[4096]
L4 输出循环  prvCrashRun               无限重放 + 喂狗 + DWT 延时   DWT->CYCCNT, UART
```
关键结论先行（对应第 3 章状态表的澄清）：
| 问题                     | 结论                             | 依据                                                         |
| ------------------------ | -------------------------------- | ------------------------------------------------------------ |
| 有无环形缓冲区？         | **无，也不需要**                 | 只有一块 `static uint8_t s_aucCrashText[4096]`，报告构建完成后内容冻结不变，循环里重放的是同一份字节流，没有"边写边读"的并发需求 |
| 有无双缓冲？             | **无，也不需要**                 | 构建期（`prvBuildXxxText`）与输出期（`prvCrashRun`）在时间上严格串行：先全部构建完，再进入输出循环；中断已被 `CPSID I` / `__disable_irq()` 关闭，不存在读者写者竞争 |
| 串口输出是阻塞还是 DMA？ | **纯轮询阻塞式**，DMA 被显式关闭 | Coffee2 端口 `lAppCommLogPortCrashWrite()`（`coffee2_crash_log_port.c:18`）在崩溃路径上 `CLEAR_BIT(CR3, DMAT)` 后逐字节等 TXE/TC；每字节有 `APP_CRASH_UART_SPIN_LIMIT=1000000` 次自旋上限防止永久卡死 |
| 输出顺序如何编排？       | **一次性顺序拼接，无动态调度**   | 报告按固定段落顺序写入单缓冲（见 7.3），输出时从 `s_aucCrashText[0]` 到 `s_usCrashTextLength` 线性发出 |

### 7.1 L1 汇编包装层——为什么必须是汇编，以及每条指令的依据
#### 7.1.1 为什么崩溃入口必须用汇编
三个硬性原因，均由 ARMv7-M 架构决定：
1. **异常入口时的寄存器状态未按 C ABI 保存**。异常发生时硬件只自动压栈 R0-R3/R12/LR/PC/xPSR（基本帧）到当前活动栈，R4-R11 处于"崩溃瞬间的值"状态。C 编译器按 AAPCS 只会保存它自己用到的 callee-saved 寄存器，无法保证完整捕获 R4-R11 的崩溃值——只有汇编能在这二者之间插手。
2. **需要读特殊寄存器 MSP/PSP/CONTROL**。C 代码无法在栈切换前读到"崩溃瞬间的 PSP 原值"（进入 C 函数后 prologue 可能已改变栈视图）。
3. **需要主动切换栈**。栈溢出钩子触发时任务栈（PSP）已不可信，必须切回 MSP 才能安全执行 C 诊断代码。
#### 7.1.2 异常路径逐条指令拆解（`AppCrashFaultCommon`）
以 GCC 版为例（ARMCC 版逐条等价）：
```asm
AppCrashFaultCommon:
    cpsid i                          ; [依据] 立即冻结所有可屏蔽异常。
                                     ; 防止后续保存寄存器过程中被更高优先级
                                     ; 异常打断造成现场污染。等价 C 的 __disable_irq()，
                                     ; 但必须在任何 C 代码之前执行，只能放汇编。
    ldr  r3, =g_aulAppCrashSavedRegisters
                                     ; [依据] 文字池加载 C 全局数组的绝对地址。
                                     ; r3 是 AAPCS 中的 scratch 寄存器，可自由使用。
    stmia r3!, {r4-r11}              ; [依据] StM Increment After，把 8 个
                                     ; callee-saved 寄存器按 R4→R11 顺序写入
                                     ; g_aulAppCrashSavedRegisters[0..7]，
                                     ; r3 自动前移 8 字。此顺序与 C 端
                                     ; prvAppendSavedRegisters() 的下标约定一致。
    mrs  r4, msp                     ; [依据] MRS 是唯一读 MSP/PSP 的指令。
    mrs  r5, psp                     ; 注意此时 MSP 已是"硬件压栈后"的值，
                                     ; PSP 若异常前在用任务栈则仍是崩溃瞬间值。
    stmia r3!, {r4-r5}               ; → g_aulAppCrashSavedRegisters[8]=MSP, [9]=PSP
    tst  lr, #4                      ; [依据] EXC_RETURN 的 bit2 (0x4) 由硬件在
                                     ; 异常入口设置：0=异常前用 MSP，1=异常前用 PSP。
                                     ; 这是"崩溃点在哪个栈上"的架构级判据。
    ite  eq
    mrseq r0, msp                    ; LR[2]==0 → 硬件帧在 MSP 栈上
    mrsne r0, psp                    ; LR[2]==1 → 硬件帧在 PSP（任务栈）上
                                     ; → R0 = 第一个 C 参数 pulFaultStack
    mov  r1, lr                      ; R1 = 第二个参数 ulExcReturn（含 bit4 信息，
                                     ; C 层用它判别 FPU 扩展帧，见 7.3.2）
    b    vAppCrashDiagFaultEntry     ; [依据] 尾跳转而非 BL：不压返回地址，
                                     ; 栈上不新增任何帧，诊断函数"永不返回"的
                                     ; 契约在汇编层就已成立。
```
入口分发器用 `MOVS R2, #N` 把原因码放进 R2（第三个 C 参数 `ulReason`），与 `app_crash_diag.h` 中 `AppCrashReason_e` 枚举严格对应：
| 汇编入口                        | R2   | 枚举                              |
| ------------------------------- | ---- | --------------------------------- |
| `AppHardFault_Handler`          | 1    | `APP_CRASH_REASON_HARD_FAULT`     |
| `AppMemManage_Handler`          | 2    | `APP_CRASH_REASON_MEM_MANAGE`     |
| `AppBusFault_Handler`           | 3    | `APP_CRASH_REASON_BUS_FAULT`      |
| `AppUsageFault_Handler`         | 4    | `APP_CRASH_REASON_USAGE_FAULT`    |
| `vApplicationStackOverflowHook` | 5    | `APP_CRASH_REASON_STACK_OVERFLOW` |
| `vApplicationMallocFailedHook`  | 6    | `APP_CRASH_REASON_MALLOC_FAILED`  |
| `vAppCrashDiagAssertEntry`      | 7    | `APP_CRASH_REASON_ASSERT`         |
> **文档勘误**：第 1 章状态表中 `malloc failed hook` 标注 NOT_IMPLEMENTED——根据当前汇编源码，`vApplicationStackOverflowHook` / `vApplicationMallocFailedHook` **均已 EXPORT 为强符号**（两个 .S 文件都存在），该行应升级为 **CONFIRMED**。
#### 7.1.3 RTOS 钩子路径的栈切换依据（`AppCrashRtosCommon`）
```asm
    mrs  r3, control
    bic  r3, r3, #2                  ; 清 CONTROL.SPSEL(bit1)：0=线程模式使用 MSP
    msr  control, r3
    isb                              ; [依据] ARMv7-M 要求修改 CONTROL 后必须
                                     ; ISB，否则后续取指/栈访问可能仍按旧视图执行。
    b    vAppCrashDiagRtosEntry
```
**原理**：`configCHECK_FOR_STACK_OVERFLOW=2` 的溢出钩子触发时，任务栈指针 PSP 指向的区域已被判定损坏（或越界到非法地址）。若继续在 PSP 上执行 C 函数，函数 prologue 的 push 会立刻二次故障。切到 MSP（独立的中断主栈，STM32 上通常 1-2KB 且不在崩溃现场）保证诊断代码有确定安全的执行栈。Malloc 钩子同理但更保守——汇编显式 `MOVS R0,#0 / MOVS R1,#0` 把 `(pvTaskHandle, pcTaskName)` 置 NULL，C 端一律走"未知任务"分支。
#### 7.1.4 双工具链等价性要点
| 概念                                                         | ARMCC (`.s`)                     | GCC (`.S`)                                      | 易错点                                                       |
| ------------------------------------------------------------ | -------------------------------- | ----------------------------------------------- | ------------------------------------------------------------ |
| 段声明                                                       | `AREA \|.text\|, CODE, READONLY` | `.section .text.AppCrashFault, "ax", %progbits` | GCC 段名带函数名利于 `-ffunction-sections` + gc-sections     |
| Thumb 标记                                                   | 文件级 `THUMB`                   | 每个函数前 `.thumb_func`                        | **GCC 必须逐函数标注**，否则链接器把符号当 ARM 态，`BLX` 会切 T=0 直接 UsageFault(INVSTATE) |
| 对齐                                                         | `PRESERVE8`                      | `.align 2`                                      | AAPCS 要求 8 字节栈对齐                                      |
| 符号引用/导出                                                | `IMPORT` / `EXPORT`              | `.extern` / `.global`                           | —                                                            |
| 使用者新增入口（例如接管 `NMI_Handler`）时，两个文件必须**同步修改且逐指令等价**，这是本架构的维护契约。 |                                  |                                                 |                                                              |

### 7.2 L2 C 入口层——"一次性冻结"语义的实现
三个入口 `vAppCrashDiagFaultEntry / RtosEntry / AssertCEntry` 结构完全一致，以 Fault 入口为例：
```c
void vAppCrashDiagFaultEntry(uint32_t *pulFaultStack, uint32_t ulExcReturn,
                             uint32_t ulReason)
{
    __disable_irq();                       // 双保险：汇编已 CPSID I，C 层再关一次
    if (s_ucCrashActive == 0U) {           // ① 只允许第一次进入者构建报告
        s_ucCrashActive = 1U;
        prvTextReset();                    // ② 长度清零，buf[0]='\0'
        prvAppendText("[CRASH][CAPTURE] source=EXCEPTION");
        prvAppendLineEnd();
        prvBuildFaultText(pulFaultStack, ulExcReturn, ulReason);  // ③ 全量构建
    }
    prvCrashRun();                         // ④ 无限重放，永不返回
}
```
**设计依据**：
- `s_ucCrashActive` 防护"诊断输出过程中再次异常"（例如 UART 驱动 bug 又触发 UsageFault）：第二次进入不会重建报告，直接落到输出循环重放旧报告，避免半新半旧的混合文本；
- "先构建完、再输出"的严格串行是**不需要双缓冲的根本原因**——构建期间无人消费，输出期间无人生产。

### 7.3 L3 报告构建层——顺序编排与缓冲区机制
#### 7.3.1 缓冲区：单块静态内存 + 写指针，数学上不可能溢出
```c
static uint8_t  s_aucCrashText[APP_CRASH_TEXT_BUFFER_SIZE];   // 4096
static uint16_t s_usCrashTextLength;
static void prvAppendChar(char cValue)
{
    if (s_usCrashTextLength < (APP_CRASH_TEXT_BUFFER_SIZE - 1U)) {  // 保留 1 字节
        s_aucCrashText[s_usCrashTextLength] = (uint8_t)cValue;
        s_usCrashTextLength++;
        s_aucCrashText[s_usCrashTextLength] = '\0';   // 永远保持合法 C 字符串
    }
}
```
- 超容量时**静默截断**（不 assert、不嵌套崩溃）——崩溃路径的第一原则是"绝不引入新故障"；
- 全部格式化函数手写（查表 hex、取模十进制），**零 printf / 零 malloc / 零除法库依赖**，避免了在损坏栈上执行 libc 的风险；
- 顺序编排 = 段落按固定次序 `prvAppendXxx` 追加，写入顺序即最终串口字节顺序，**没有重排、没有优先级、没有环形覆盖**。
#### 7.3.2 异常报告的段落顺序及逐段来源（`prvBuildFaultText`）
```
顺序  段落标记                 数据来源                                 源码函数
─────────────────────────────────────────────────────────────────────────────
 1   [CRASH][CAPTURE]        C 入口硬编码 source=EXCEPTION             入口函数
 2   [CRASH][BEGIN]          ulReason → prvReasonText() 静态映射表；    prvAppendCommonHeader
                             current_handle ← g_pvAppCrashCurrentTask
                             (来自 traceTASK_DELETE/CREATE 钩子维护的
                             "最近调度任务"影子变量)
 3   [CRASH][CORE] 头行      EXC_RETURN(R1 参数)、FRAME_SP(R0 参数)     prvBuildFaultText
 4   [CRASH][CORE] R0-R3     硬件栈帧 + FPU 偏移修正（见下）            同上
 5   [CRASH][CORE] R12/LR/PC/XPSR                                     同上
 6   [CRASH][CORE] R4-R11    g_aulAppCrashSavedRegisters[0..7]         prvAppendSavedRegisters
                             （汇编 STMIA 写入）
 7   [CRASH][STACK]          [8]=MSP [9]=PSP + 当刻 CONTROL/PRIMASK/   同上
                             BASEPRI/FAULTMASK (__get_* 内建)
 8   [CRASH][SCB]            SCB->CFSR/HFSR/DFSR/AFSR/MMFAR/BFAR/      prvAppendScbRegisters
                             SHCSR/ICSR（CMSIS 寄存器直读）
 9   [CRASH][DECODE]         CFSR/HFSR 位域 → 英文 flag 文本            prvAppendFaultDecode
10   [CRASH][RTOS]           registered_tasks / registration_drops     prvAppendTaskRecords
11   [CRASH][TASK] × N       影子注册表 s_axCrashTasks + 栈高水位扫描   同上
12   [CRASH][END]            repeat_seconds=10                          收尾
```
**第 4-5 段的 FPU 帧偏移是 M4F 平台最容易做错的点**：
```c
ulFrameOffset = ((ulExcReturn & (1UL << 4)) == 0U)
              ? APP_CRASH_EXTENDED_FRAME_WORDS   /* 18 字：S0-S15+FPSCR+保留 */
              : 0U;                              /* 基本帧：R0 从偏移 0 开始  */
ulFrameAddress = (uint32_t)pulFaultStack + (ulFrameOffset * sizeof(uint32_t));
ucFrameValid  = prvIsCpuRamRange(ulFrameAddress, 8 * sizeof(uint32_t));
```
依据：ARMv7-M 中 EXC_RETURN bit4=1 → 基本帧（8 字），bit4=0 → 扩展帧（FPU 寄存器压在 R0 之前）。**读栈帧前先做 RAM 范围校验**（`prvIsCpuRamRange` 检查 CCM `0x1000_0000~0x1000_FFFF` 和主 SRAM `0x2000_0000~0x2001_FFFF`，含加法回绕检查），栈帧指针本身若已被砸坏，输出 `frame_valid=0` 而不是 BusFault 二连。
**第 11 段任务记录的"读前校验链"**（元数据本身可能是被崩溃砸坏的）：
```
ulValid == 0x43524153 ("CRAS" 魔数，发布协议最后写)
  → low<=high、4 字节对齐
  → 长度 ≤ 16KB（APP_CRASH_MAX_STACK_BYTES）
  → 整段落在 CCM/SRAM 白名单
  全过 → 从栈底向上数连续 0xA5 (tskSTACK_FILL_BYTE) → hwm_words / hwm_bytes
  任一不过 → 打印 hwm=INVALID_RANGE，绝不解引用
```

### 7.4 L4 输出层——单缓冲、轮询阻塞、无 DMA
#### 7.4.1 输出循环（`prvCrashRun`）
```c
static void prvCrashRun(void)
{
    prvEnableCycleCounter();              // DWT CYCCNT 重新使能：唯一时基
    for (;;) {
        vAppCrashDiagWatchdogRefresh();          // 默认 no-op（ENABLE=0）
        (void)lAppCrashDiagWrite(s_aucCrashText, s_usCrashTextLength);  // 整块发出
        prvCrashDelayRepeatPeriod();             // DWT 忙等 10s（10Hz 喂狗节拍）
    }
}
```
- `lAppCrashDiagWrite` 在公共核心是 **APP_WEAK no-op（返回 -1）**，Coffee2 由 `coffee2_crash_log_port.c:18` 提供 **强符号** 绑定到 `lAppCommLogPortCrashWrite()` —— 这是公共核心与目标板串口解耦的唯一接触面；
- `prvCrashDelayRepeatPeriod` 用 `DWT->CYCCNT` 差值忙等，完全绕开 SysTick/RTOS tick（崩溃后内核时基不可信），每 100ms 一次喂狗节拍，10 秒周期 × `APP_CRASH_REPEAT_SECONDS`。
#### 7.4.2 Coffee2 串口端口行为（阻塞轮询，DMA 显式关闭）
```
lAppCommLogPortCrashWrite(buf, len):        // coffee2_crash_log_port.c:18
  1. CLEAR_BIT(USARTx->CR3, USART_CR3_DMAT) // 掐断可能残留的 DMA 请求，
                                            // 防止崩溃前后 DMA 与轮询双写 TX
  2. for each byte:
       spin 等待 USART_ISR_TXE (上限 APP_CRASH_UART_SPIN_LIMIT=1000000 次)
       写 TDR
     最后等 TC (Transmission Complete)
  3. 单次自旋超限 → 返回错误码，由 prvCrashRun 的下一轮重试兜底
```
结论回答本节标题三连问：
- **阻塞？** 是。逐字节忙等 TXE，纯同步输出，无任务、无回调、无中断；
- **DMA？** 否。且主动关闭 DMAT 防残留传输；
- **环形/双缓冲？** 否。一次 `write` 直接把冻结缓冲线性推完，缓冲管理复杂度为零——这是"崩溃路径越简单越可靠"原则的直接体现。

## 8. 模拟示例：一次任务栈溢出的完整调用链追踪
**场景设定**：任务 `CtrlTask`（优先级 3，栈 512 字，0xA5 填充）在 `sensor_read()` 里递归过深触发 `configCHECK_FOR_STACK_OVERFLOW=2` 检查。
### 8.1 全链路时序（从触发到串口字节）
| 步   | 执行者        | 动作                                                         | 源码位置                                                     |
| ---- | ------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 1    | FreeRTOS 内核 | 任务切换检查发现栈底魔数被破坏 → 调用钩子                    | `tasks.c` → `vApplicationStackOverflowHook(pxTask, pcTaskName)` |
| 2    | 汇编          | `MOVS R2,#5`；`B AppCrashRtosCommon`                         | `app_crash_fault_gcc.S`                                      |
| 3    | 汇编          | `CPSID I`；R4-R11/MSP/PSP → `g_aulAppCrashSavedRegisters[10]` | `AppCrashRtosCommon`                                         |
| 4    | 汇编          | `CONTROL.SPSEL←0` + `ISB`：切回 MSP；`B vAppCrashDiagRtosEntry`（R0=pxTask, R1=pcTaskName, R2=5） | 同上                                                         |
| 5    | C 入口        | `__disable_irq()`；`s_ucCrashActive 0→1`；`prvTextReset()`；写 `[CRASH][CAPTURE] source=FREERTOS_HOOK` | `vAppCrashDiagRtosEntry`                                     |
| 6    | C 构建        | `prvBuildRtosText(pxTask, name, 5)`：查影子注册表拿任务名 → 公共头 → 保存寄存器段 → SCB 段 → 任务表（扫描栈 0xA5）→ END；**忽略钩子传入的 pcTaskName**（可能指向已损坏 TCB，只用注册表副本） | `prvBuildRtosText`                                           |
| 7    | C 输出        | `prvCrashRun()`：使能 CYCCNT → 无限循环                      | 同上                                                         |
| 8    | 端口          | `lAppCrashDiagWrite` → `lAppCommLogPortCrashWrite`：关 DMAT → 逐字节轮询 TXE/TC 发出整份报告 | `coffee2_crash_log_port.c:18`                                |
| 9    | C 循环        | DWT 忙等 10s（每 100ms `vAppCrashDiagWatchdogRefresh`，默认 no-op） | `prvCrashDelayRepeatPeriod`                                  |
| 10   | 系统          | 第 9 步重复（每 10s 重放一次），直至 IWDG（若产品使能且本模块未喂狗）复位 MCU；复位后无持久化，**上次报告丢失**（对应第 3/4 章 NOT_IMPLEMENTED） | —                                                            |

| 汇编侧                                                    | 寄存器 | C 侧形参                                     |
| --------------------------------------------------------- | ------ | -------------------------------------------- |
| `pxTask`（钩子第一个参数）                                | R0     | `pvTaskHandle`                               |
| `pcTaskName`（malloc 钩子路径被 `MOVS R0/R1,#0` 置 NULL） | R1     | `pcTaskName`                                 |
| `MOVS R2,#5`                                              | R2     | `ulReason = APP_CRASH_REASON_STACK_OVERFLOW` |

### 8.4 从示例回看三个架构判断
1. **为什么钩子路径切 MSP**：步骤 3-4 若不切栈，步骤 6 的 C 函数 prologue push 就落在已溢出的 PSP 上，报告根本写不出来；
2. **为什么无环形缓冲**：步骤 6 构建与步骤 8 输出严格串行且中断全关，单缓冲 + 冻结重放即最优解；
3. **为什么轮询而非 DMA**：步骤 8 发生在中断全关、调度器停摆的上下文，DMA 传输完成中断永远不来，只有 CPU 忙等 TXE 是确定性行为——自旋上限（100 万次/字节）保证即使 UART 硬件异常也能退出，由步骤 7 的循环重试兜底。
