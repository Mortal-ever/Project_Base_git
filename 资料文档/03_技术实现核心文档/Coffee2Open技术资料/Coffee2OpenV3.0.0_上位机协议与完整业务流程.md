# Coffee2OpenV3.0.0 上位机协议与完整业务流程

> 状态：2026-08-26 软件实现基线  
> 适用目标：Coffee2  
> 不适用：MilkTea、Coffee1 封闭式储杯/出餐机构  
> 事实来源：Coffee2 当前源码、《咖啡售卖机下位机-通信协议》、`coffee2上位机对接下位机协议说明.txt`、Coffee1 MBP 与业务逻辑佐证、Coffee1 `coffee_close_v2.7.23_ccram`、咖博士 F200 协议、电气图与 3D 结构说明。

## 1. 最终边界

Coffee2 是开放式店中店机型：只有线下订单、两个开放式出餐口、一个压盖位；没有打印机、储杯位、出餐门、升降机构、风扇和灯带。协议中为其他产品保留的字段仍占用原地址，但 Coffee2 不执行对应业务。

| 事项 | Coffee2OpenV3.0.0 规则 |
|---|---|
| 软件版本 | `Coffee2OpenV3.0.0` |
| 订单目标出餐口 | 只读上位机命令 `0x000A`，必须为 1 或 2 |
| `0x000C` | 封闭式 v2 现场单字段；Coffee2 必须写 0，否则订单拒绝 |
| `0x0009` | 储杯字段；Coffee2 必须写 0，否则订单拒绝 |
| `0x0006` | 打印字段；Coffee2 忽略，不进入打印流程 |
| `0x0005` | 冰块目标克重，单位 1 g；不是温度 |
| 咖啡逻辑配方 | `0x0000～0x0021`；内部 `0xFFFF` 表示本单不调用咖啡机 |
| 机器人调试点位 | `0x0031` 只接受 `0x00～0x0F` |
| 咖啡机 | 咖博士 F200 自有 26 字节串口协议，不创建 Modbus RTU 实例 |
| 协议事务完成 | 只表示从设备接受了本次协议事务，不代替 Workflow 的物理后置条件 |

## 2. 架构职责

~~~mermaid
flowchart LR
    H[上位机\nModbus TCP :6001] --> S[C2Server\n协议解析/寄存器镜像/订单冻结]
    S --> W[C2Workflow\n唯一业务状态机]
    W --> R[C2Robot Owner\nModbus TCP :502]
    W --> B2[C2Bus2 Owner\nF200 自有协议]
    W --> B3[C2Bus3 Owner\n杯盖/糖浆/电能表]
    W --> B4[C2Bus4 Owner\n制冰/称重]
    W --> B5[C2Bus5 Owner\n外部 DI/DO]
    W --> IO[Coffee2 IO API\n本地 GPIO 与 IO 语义]
    R --> DL[公共 DeviceLibrary]
    B2 --> DL
    B3 --> DL
    B4 --> DL
    B5 --> DL
    R --> LOG[公共日志环]
    B2 --> LOG
    B3 --> LOG
    B4 --> LOG
    B5 --> LOG
    W --> LOG
    S --> LOG
~~~

职责必须保持清晰：

- Server 负责接收命令、校验协议范围、冻结订单快照和发布上位机状态，不直接操作设备；
- Workflow 决定先做什么、是否需要某设备、设备命令完成后还要等什么真实条件；
- Robot/Bus 任务独占各自物理链路，只执行原子协议事务并报告结果；
- DeviceLibrary 解释设备协议，不包含 Coffee2 订单业务；
- 本地 IO 或无协议 IO 模组由 Workflow 通过语义 API 控制，不伪装成 Modbus 设备；
- 日志是观察手段，不是系统启动或业务运行的前置条件。

## 3. 上位机订单接收闭环

~~~mermaid
sequenceDiagram
    participant H as 上位机
    participant S as C2Server
    participant W as C2Workflow
    participant D as Robot/Bus Owner
    participant P as 物理后置条件

    H->>S: FC16 写订单寄存器
    H->>S: 0x0007=1, 0x0008=1
    S->>S: 冻结订单快照并校验
    alt 非法字段或条件
        S-->>H: 0x1008=3
        S->>S: 记录 ORDER_REJECTED
    else 接收成功
        S->>W: 投递带真实订单号的快照
        S-->>H: 0x1008=1
        W->>D: 投递当前原子设备命令
        D-->>W: 本次协议事务完成/失败
        W->>P: 检查杯、重量、出餐口等业务条件
        P-->>W: 条件满足
        W-->>S: 流程完成
        S-->>H: 0x1008=2
    end
~~~

订单校验至少包含：

1. 订单号不能使用系统号 `0x0000` 或调试号 `0xF123`；
2. 咖啡配方必须为 `0x0000～0x0021` 或内部值 `0xFFFF`；
3. `0x000A` 必须是出餐口 1 或 2；
4. `0x0009`、`0x000C` 必须为 0；
5. 冰块目标克重、果乳量和糖浆量必须在下位机安全边界内；
6. 上电残杯初始化未完成时不接受订单。

订单状态不能再通过“命令区整体复制到状态区”产生。当前实现只显式回显协议定义字段，并由设备/Workflow 实时更新动态状态，避免 `0x100B/0x100C/0x101A/0x101B` 被订单参数覆盖。

## 4. 完整订单主流程

~~~mermaid
flowchart TD
    A[冻结并校验订单] --> B[刷新本单需要的设备]
    B --> C[机器人 Home]
    C --> D{冰块克重 > 0?}
    D -- 是 --> E[取冷杯并落杯]
    D -- 否 --> F[取热杯并落杯]
    E --> G[到制冰位]
    G --> H[称重/制冰闭环]
    H --> I{有果乳或糖浆?}
    F --> I
    I -- 是 --> J[到果乳/糖浆共用出口]
    J --> K[果乳 A/B IO 阀泵]
    K --> L[糖浆 1→4 串行协议命令]
    I -- 否 --> M{需要 F200?}
    L --> M
    M -- 是 --> N[到咖啡机前/内]
    N --> O[F200 制作咖啡/奶]
    O --> P[机器人从咖啡机取杯]
    M -- 否 --> Q{需要杯盖?}
    P --> Q
    Q -- 是 --> R[落盖→取压盖位→压盖]
    Q -- 否 --> S[按0x000A选择出餐口]
    R --> S
    S --> T[机器人放杯]
    T --> U[等待对应出餐口杯传感器]
    U --> V[状态=放杯完成]
    V --> W[机器人 Home]
    W --> X[订单完成]
~~~

### 4.1 冷热与落杯

- `0x0005 == 0`：热饮，使用热杯路径；
- `0x0005 > 0`：冷饮，数值同时是目标冰块克重，使用冷杯路径；
- 杯机协议命令返回成功后，Workflow 继续检查对应杯位传感器；只有传感器满足才进入下一段；
- 没有单独冷热字段，因此“冷饮不加冰”不能由下位机猜测，未来如需要必须扩展上位机协议。

### 4.2 制冰与称重

这一段由多个原子步骤组成：机器人到制冰位、称重去皮/读取、制冰机落冰、稳定重量复查、必要时按补偿系数补冰。Bus4 只确认每次 RTU 请求/应答；最终是否达到目标克重由 Workflow 判定。

### 4.3 果乳与四路糖浆

果乳和糖浆共用同一物理出口，但执行器不同：

- 果乳 A/B：Workflow 调用 IO 语义函数，按正常出液要求组合阀和泵；
- 糖浆 1～4：Workflow 按通道 1→4 串行向 Bus3 投递糖浆机 Modbus RTU 命令；
- 只有本单数量非 0 的通道才执行；
- 果乳/糖浆段结束后，才进入咖啡机工位，避免与 Coffee1 旧“都从咖啡机口出液”的结构混淆。

### 4.4 F200 咖啡/奶

上位机使用统一逻辑配方 `0x0000～0x0021`。Coffee2 F200 适配器发送的物理饮品号为“逻辑号 + 1”。因此现场 F200 菜单槽位必须按统一目录配置；若菜单顺序不同，协议通讯会成功但饮品会错误，这是调试验收项。

F200 制作完成后，Workflow 必须再执行“机器人从咖啡机取杯”。F200 的成功只说明饮品程序完成，不表示杯已离开咖啡机。

### 4.5 压盖与出餐

- Coffee2 只有一个压盖位置；取压盖动作就是在该位置取杯/盖组合；
- 目标出餐口只来自 `0x000A`；
- 放杯前将对应 `0x100B/0x100C` 置为 2；机器人失败置 3；对应杯传感器到位后置 5；
- 上位机通过 `0x000B=0x0001/0x0010` 确认出餐口1/2已取走，状态置 `0x0010`；
- 出餐完成后机器人回 Home，订单才进入完整完成态。

## 5. Robot 单步调试与闭环

`0x0031` 只支持以下 16 个值：

| 值 | 动作 |
|---:|---|
| `0x00` | Home |
| `0x01` | 热杯位 |
| `0x02` | 冷杯位 |
| `0x03` | 落盖位1 |
| `0x04` | 落盖位2 |
| `0x05` | 咖啡机前 |
| `0x06` | 咖啡机内 |
| `0x07` | 制冰位 |
| `0x08` | 果乳/糖浆出口 |
| `0x09` | 取/检查出餐口1 |
| `0x0A` | 取/检查出餐口2 |
| `0x0B` | 放到出餐口1 |
| `0x0C` | 取压盖位 |
| `0x0D` | 压盖 |
| `0x0E` | 放到出餐口2 |
| `0x0F` | 从咖啡机取杯 |

位置动作仍执行完整机器人握手：清目标动作区、置命令位、每 100 ms 读回；机器人把命令位清 0 后才记录 `ROBOT_ACTION_ACCEPTED` 并开始 60 s 运动计时；完成位置 1 后主控清结果位并确认回 0。TCP 掉线时保留在途事务，重连和机器人准备完成后继续协调，而不是把单次动作超时直接等同于链路断开。

## 6. 从设备事务成功的判定

设备任务不能因为“收到任意合法帧”就报告命令完成。

### 6.1 Modbus RTU

以 FC06 写单寄存器为例，响应必须同时满足：

- 从站地址等于本次目标 Unit；
- 功能码等于本次请求 FC06，而不是其他 FC03/FC01 帧；
- 回显寄存器地址等于本次写地址；
- 回显值等于本次写值；
- CRC 正确；
- 异常功能码和异常码不存在。

FC05、FC15、FC16 也按各自标准回显规则核对；读命令必须核对 Unit、功能码和字节数量。超时只代表本次通讯未闭环，由 Bus 的有限重试处理；不能因此直接跳过 Workflow 的业务条件。

### 6.2 F200 自有协议

F200 每次响应必须满足：26 字节长度、帧头/帧尾 0x7E、长度 0x1A、校验和正确、响应命令字等于本次请求命令。非查询命令若应用状态为 4，事务判失败。这样可以避免把周期查询或其他命令的帧误认为本次制作/清洗成功。

## 7. 独立维护任务

维护任务使用现有 Workflow 维护上下文，不创建额外任务和动态内存。

### 7.1 热水

- `0x0080` 触发热水任务，`0x0081` 指定加热分钟数；
- 低水位未到：打开热水桶供水阀进行注水；到低水位后必须关闭供水阀，再打开热水继电器；
- 高水位到达时停止注水并记录报警，防止继续加水；
- 注水超过配置上限仍未到低水位：关闭供水阀并报警；
- `0x1080/0x1081` 对上位机保持“1=未到位、0=已到位”的协议语义，因此对本地 active 信号取反投影。

### 7.2 F200 清洗

`0x0042` 支持 1～6：冲泡器快速冲洗、奶沫器快速冲洗、粉料快速冲洗、奶路强制冲洗、一键清洗、奶系统清洗。Workflow 投递真实 F200 命令并等待应用状态完整成功；不再用占位日志冒充完成。`0x0083` 非零映射到奶系统清洗。

### 7.3 糖浆与果乳清洗

- 糖浆清洗由糖浆机协议执行，Bus3 完成请求/应答；
- 果乳清洗由 Workflow 直接控制相应阀泵组合，并与同一物理出口的正常出液互斥；
- 清洗与订单是否可并行由真实共享资源决定，不使用“所有维护一律阻塞所有业务”的全局互锁。

## 8. 上电初始化

启动时使用系统订单号 `0x0000`：

1. 初始化 Transport、日志、设备表、IO、各 Bus、Robot、Workflow、Server；
2. 打印 `FW_VERSION:Coffee2OpenV3.0.0`；
3. 各物理 Owner 任务打印自己实际选中的 Driver/协议/Bus/Unit/波特率；
4. 等待 Robot、F200、杯盖设备和输入 IO 快照有效；
5. 检查出餐口 1/2 传感器基线；
6. 依次执行夹爪、咖啡机内部、压盖位残杯搬运验证；
7. 检查落杯/落盖四个位置传感器；
8. 最终回 Home；全部通过后整机进入待机；
9. 发现残杯则置整机报警，日志指出位置，人工清理并清报警后完整复查。

机器人允许空抓取；抓取安全、轨迹与碰撞边界由机器人 PLC/轨迹程序和调试工程师负责，STM32 不额外发明视觉或夹爪安全条件。

## 9. 上位机关键状态

| 地址 | Coffee2OpenV3.0.0 语义 |
|---:|---|
| `0x1008` | 制作状态：0默认、1制作中、2完成、3失败 |
| `0x1009` | 当前放杯出餐口：0/1/2 |
| `0x100B` | 出餐口1状态：0、2、3、5、0x10 |
| `0x100C` | 出餐口2状态：0、2、3、5、0x10 |
| `0x100D` | 当前订单目标出餐口：0/1/2 |
| `0x1018` | 当前 Workflow 步骤 |
| `0x101A` | DDSU666 累计电能整数部分，1 kWh |
| `0x101B` | DDSU666 累计电能小数部分，0.01 kWh |
| `0x1020` | 整机状态：0默认、1待机、2初始化、3忙碌、4报警 |
| `0x1023` | bit0 出餐口1有杯；bit1 出餐口2有杯 |
| `0x1051/52` | 热杯/冷杯余量，1有料、0缺料 |
| `0x1053/54` | 杯盖1/2余量，1有料、0缺料 |
| `0x1080/81` | 低/高水位未到位，1未到、0已到 |

## 10. 日志追踪

订单日志使用上位机真实订单号；单步调试使用下位机固定订单号 `F123`；启动初始化使用 `0000`。

典型链路：

~~~text
[1234INFO][C2Server:MBTcpServer] ORDER_ACCEPTED result=0 order=4660
[1234INFO][C2Workflow:Workflow] WORKFLOW_STEP_ENTER result=0 step=...
[1234INFO][C2Robot:MBTcpClient] ROBOT_ACTION_START result=0 action=...
[1234INFO][C2Robot:MBTcpClient] ROBOT_ACTION_SENT result=0 coil=...
[1234INFO][C2Robot:MBTcpClient] ROBOT_ACTION_ACCEPTED result=0 action=...
[1234INFO][C2Robot:MBTcpClient] ROBOT_ACTION_COMPLETE_SIGNAL result=0 coil=...
[1234INFO][C2Robot:MBTcpClient] ROBOT_ACTION_COMPLETE result=0 action=...
[1234INFO][C2Workflow:Workflow] WORKFLOW_CONDITION_MET result=0 condition=...
[1234INFO][C2Server:MBTcpServer] ORDER_COMPLETED result=0 order=4660
~~~

日志只在状态进入、变化、失败和完成时输出；100 ms 轮询本身不逐次打印。日志队列满时覆盖最早记录，日志串口未连接不能阻塞业务任务。

## 11. 当前完成度与验收边界

软件已完成本文件所述的协议收敛、F200 配方/清洗适配、订单主线、双出餐状态、能耗/物料/液位投影和版本输出，并通过 GCC Coffee2 Debug/Release 与 Keil ARM Compiler V5.06u7 构建。

仍必须由现场完成：

- F200 1～34 菜单槽位与逻辑配方目录逐项核对；
- 出餐口 1/2 传感器极性和物理对应；
- 热/冷杯及杯盖余量线圈极性；
- 16 个机器人单步点位、空抓取、咖啡机取杯、压盖、双出餐动作逐项验收；
- 冷/热、果乳、糖浆、咖啡、奶和杯盖组合订单矩阵；
- 热水注水上限、加热时间和高液位报警实机验证；
- 机器人断线重连后的在途动作恢复及上位机取杯确认闭环。

“编译通过”证明代码和链接闭合，不等于机械轨迹、菜单配置和传感器极性已经通过实机验收。
