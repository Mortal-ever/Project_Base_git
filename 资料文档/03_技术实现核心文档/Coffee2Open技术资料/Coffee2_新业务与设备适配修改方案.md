# Coffee2 新业务与设备适配修改方案

> 文档状态：方案评审版  
> 日期：2026-08-24  
> 本轮范围：只做分析、建模和实施规划，不修改源码。  
> 已确认机器人品牌：越疆。节卡协议尚未确定，不进入本轮设计和实现。

## 1. 结论先行

当前“设备协议外包、业务流程由 Workflow 把控”的方向正确，也适合继续发展。推荐保持以下边界：

~~~mermaid
flowchart LR
    H[上位机订单或调试命令] --> S[Coffee2 Server]
    S --> W[Workflow 业务状态机]
    W -->|设备命令| C[Coffee2Command]
    C --> O{物理链路 Owner}
    O --> R[Robot TCP Owner]
    O --> B[Bus2～Bus5 Owner]
    R --> DL[公共 DeviceLibrary]
    B --> DL
    DL --> D[真实设备]
    D --> DL
    DL --> O
    O -->|协议命令完成| W
    W -->|检查 IO/重量/配方条件| W
    W -->|步骤完成/失败| S
~~~

必须坚持：

1. DeviceLibrary 只负责设备原生协议、帧交互、字段解析和协议级命令结果。
2. Bus/Robot Owner 只负责链路独占、排队、通信重试、事务身份和结果回传。
3. Workflow 负责订单判断、前置条件、机器人与设备组合、IO/重量后置条件、继续/取消和订单终态。
4. Server 只做上位机协议解析、快照和投递，不直接编排设备动作。
5. 本地 GPIO 可以通过 Coffee2 专用语义 API 直接操作；外部 Modbus IO 仍必须经过 Bus5 Owner。

当前最需要修正的不是再增加一层运行时框架，而是：

- 把越疆 3100～3159 新地址模型真正落入公共设备库；
- 用 Coffee2 静态点位表表达本产品语义；
- 重写 Workflow 的业务步骤与判断；
- 把热水、清洗等维护流程做成同一个 Workflow 任务内的小状态机；
- 把四路糖浆的配方、逐通道执行、恢复和清洗流程补入 Workflow；
- 按图纸补齐 IO 模块和 Bus3 电能表绑定；
- 上电输出确定的设备、驱动、协议和链路清单。

这套方案不需要新增任务、动态内存、运行时 Profile 管理器或通用脚本引擎，符合奥卡姆剃刀原则。

## 2. 资料优先级与冲突处理

本方案按以下优先级解释需求：

1. 本轮用户确认的业务规则；
2. 奶茶机机器人寄存器整理表和越疆本体截图；
3. 店中店开放式咖啡机电气图；
4. 各设备正式通信协议；
5. Coffee1 v2.7.23_ccram 的已验证业务原型；
6. 当前 Coffee2 源码。

Coffee1 只用于继承动作时序、现场经验和失败处理，不复制其集中式全局状态机。电气 IO 与新机械结构发生冲突时，以 Coffee2 图纸和本轮需求为准。

## 3. 当前源码状态与目标差距

### 3.1 当前已具备

| 能力 | 当前状态 |
|---|---|
| 上位机 Modbus TCP Server | 已有，端口 6001，支持双客户端槽 |
| 订单号贯穿 | 已有，真实订单使用上位机订单号；调试固定 F123 |
| Robot TCP Owner | 已有，支持命令队列、握手、60 秒动作时间、断线重连与事务恢复 |
| Bus 物理独占 | 已有，每个 UART 只创建一种协议 Owner |
| 公共设备库 | 已有越疆、F200、杯盖、糖浆、制冰、称重、电表、数字 IO 驱动 |
| IO 全局镜像 | 已有本地 8 入 8 出及外部输入/输出镜像 |
| 日志公共核心 | 已有静态覆盖式环形缓冲与订单号前缀 |

### 3.2 当前仍不满足新业务

| 差距 | 证据与影响 |
|---|---|
| Workflow 仍是旧顺序 | 当前是落杯→咖啡→制冰→糖浆→落盖→出餐，未体现果乳独立出口和“先果乳后咖啡/奶” |
| 越疆协议 2/3 仍是占位 | DeviceLibrary 中协议 2/3 仍使用协议 1 的 40 点范围和连续清命令区 |
| 新的三组 10+10 地址无法由单一连续清区描述 | 新命令区是 3110～3119、3130～3139、3150～3159，不能继续使用一个 start/count |
| Coffee2 机器人 Target 语义选错 | Coffee2 应继续使用越疆协议1，但当前 `PUT_OUTPUT` 套用闭式机 3138 语义；应对齐 Coffee1 开放式业务，由上位机选择出餐口1/2，并映射到 3131/3111 或 3132/3112 |
| 果乳、热水业务未进入 Coffee2 Workflow | 当前只有 IO 点名，没有完整维护/配方状态机 |
| 四路糖浆虽有 Driver，但业务文档缺链路 | 当前源码能依次调用 1～4 路，却没有定义口味映射、数量到 0.1 秒的换算、恢复判断和逐阶段日志；通道 3/4 仍直接使用 0x0013/0x0014 魔法地址 |
| Device COMMAND_DONE 与业务完成仍易混淆 | 现有 prvRunStep 收到 COMMAND_DONE 就返回成功，缺少 Workflow 的传感器/重量后置判断 |
| 电能表仍绑定 Bus4 | 用户要求改到 Bus3、Unit3、9600 |
| 图纸表现为两块外部输出模块 | 当前只有一个 IO_OUTPUT Unit2 绑定，第二块站号尚未确认 |
| 启动日志只打印任务 | 不能直接看出每个设备选用了哪个 Driver、协议、Bus、Unit 和波特率 |
| 缺少上电业务初始化 | 当前 Manager 只完成模块/任务创建，Workflow 初始化后立即开放订单；没有残杯检查、初始化报警和人工确认后的重试流程 |
| 整机状态投影语义错误 | 正式上位机协议规定 0x1020 为 0默认/1待机/2初始化/3忙碌/4报警；当前源码直接投影 Workflow 枚举，IDLE/RUNNING/COMPLETED/FAILED/CANCELING 会被错误解释 |
| 初始化机器人语义未正确接线 | 协议1已有 3134/3114“取压盖位”与两个开放式出餐口点，无需新增机器人地址；当前 Target 枚举名和出餐解析需修正 |
| 杯盖四位置传感器尚未接入 Workflow | 公共 Driver 已读 Bus3/Unit1/FC01 的 0x1004～0x1017 原始线圈；其中 0x1008/0x100D/0x1012/0x1017 是设备线圈，不是同数值的 Host TCP 状态寄存器 |

## 4. 推荐的目标架构

### 4.1 分层

~~~mermaid
flowchart TB
    A[Host Protocol<br>寄存器、订单快照、调试入口]
    B[Workflow<br>订单与维护状态机]
    C[Target Semantic API<br>Coffee2 动作与 IO 语义]
    D[Command / Route<br>命令身份、队列、物理链路 Owner]
    E[DeviceLibrary<br>越疆/F200/杯盖/制冰/称重/电表/IO]
    F[Transport + ModbusPort<br>UART/TCP/FC01~FC16]
    G[HAL/BSP<br>GPIO、UART、ETH]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> F
    F --> E
    E --> D
    D --> B
~~~

### 4.2 四种“完成”必须分开

| 层级 | 完成含义 | 例子 |
|---|---|---|
| 通信事务完成 | 收到合法帧或确定通信失败 | FC06 收到正确回显 |
| 设备协议命令完成 | 设备 Driver 已完成该原子命令 | 落杯机接受落杯命令 |
| Workflow 步骤完成 | 业务后置条件满足 | 杯到位传感器已有效 |
| 订单完成 | 所有个性化步骤和出餐完成 | 订单状态置完成并释放订单槽 |

Bus 返回“落杯命令成功”以后，Workflow 还必须检查杯传感器。传感器没到位时不应伪装成通信超时，也不应进入下一步，而应保持 WAIT_CONDITION 并输出状态变化日志。

## 5. 越疆设备库修改方案

### 5.1 只实现越疆

本轮只实现：

- 越疆本体控制线圈；
- 越疆本体状态输入；
- 越疆协议 1；
- 越疆协议 2 / Robot1；
- 越疆协议 3 / Robot2；
- Coffee2 产品自己的语义点位表；
- 越疆专用启动序列。

节卡没有确定协议，不分配地址、不写启动流程、不出现在“可用设备”清单。当前若保留节卡枚举，也必须标为 RESERVED/UNAVAILABLE，不能被 Target 选中。

### 5.2 越疆本体控制与状态

本体控制是线圈 0～8，使用 FC05/FC15：

| 脚本地址 | 功能 |
|---:|---|
| 0 | 开始 |
| 1 | 停止 |
| 2 | 暂停 |
| 3 | 上使能 |
| 4 | 下使能 |
| 5 | 清除报警 |
| 6 | 进入拖拽 |
| 7 | 退出拖拽 |
| 8 | 切换自动模式 |

表格还提到“手动模式”索引 9，但截图未完整显示。索引 9 在机器人版本确认前不得作为已验证命令。

本体状态是离散输入 0～11，使用 FC02：

| 脚本地址 | 功能 |
|---:|---|
| 0 | 运行状态 |
| 1 | 停止状态 |
| 2 | 暂停状态 |

| 4 | 安全皮肤暂停状态 |

| 11 | 恢复模式状态 |

公共库应增加有名称的 enum 和位图解码，不让 Coffee2 用数组下标 7、8、9 解释业务。

### 5.3 三套位置协议

协议 1 保留旧版：

- 状态：3100～3119；
- 命令：3120～3139；
- 3120 启动信号保留特殊业务语义；
- 普通动作清零区不包含 3120。

协议 2 / Robot1 与协议 3 / Robot2 使用相同的地址几何：

| 组 | 状态区 | 命令区 |
|---|---|---|
| 第 1 组 | 3100～3109 | 3110～3119 |
| 第 2 组 | 3120～3129 | 3130～3139 |
| 第 3 组 | 3140～3149 | 3150～3159 |
| 保留 | 3160 | 3160 |

协议 2 和协议 3 的区别是“角色和语义映射”，不是 Modbus 帧格式不同。两者复用同一越疆 Driver，通过静态 Point Table 选择业务含义。

### 5.4 必须修正当前 ProtocolConfig

当前单一 usActionClearStart/usActionClearCount 不适用于三段命令区。最小改法是让协议描述符引用静态命令区数组：

| 协议 | 需要清理的普通动作区 |
|---|---|
| 协议 1 | 3121～3139 |
| 协议 2 | 3111～3119、3130～3139、3150～3159 |
| 协议 3 | 3111～3119、3130～3139、3150～3159 |

第 1 组的 3110 与旧版 3120 一样作为特殊启动信号时，不参与普通动作“全清后置一”。

建议使用静态 const 区间表，区间数据进入 Flash，不增加运行时管理器。协议 2/3 的 control count 应是 60，不是当前占位的 40，也不需要为 3160 分配第 61 个镜像字节。

### 5.5 Coffee2 必须使用协议1开放式语义 Profile

Coffee2 不使用奶茶机的协议2/3 三组 10+10 点位。它使用已在 Coffee1 开放式产品中验证的协议1 3100～3139，并在 Target 层选择开放式 Coffee2 Profile。关键语义如下：

### 5.7 越疆启动序列

Coffee1 已验证的冷启动流程为：

1. FC15 清本体控制线圈 0～9；
2. 清报警置 1；
3. 停止置 1；
4. 清报警置 0；
5. 清报警再次置 1；
6. 退出拖拽置 1；
7. 上使能置 1；
8. 停止置 1；
9. 开始置 1；
10. 必要时清业务完成位。

工程习惯称其为“9 步启动”，最后一项是业务完成位清理。推荐把 1～9 的本体控制序列做成 DeviceLibrary 中的静态 const 描述，由 Robot Owner 执行；“是否清业务完成位、清哪些区间”由所选位置协议决定。

连接恢复时不能无条件重复停止和清业务位。若有活动事务，应先读取命令位和结果位并恢复闭环；只有没有活动事务且机器人不处于可运行状态时才执行冷启动。

## 6. Bus 与设备绑定修改

### 6.1 目标绑定

| 链路 | 物理参数 | 设备 | 协议/站号 |
|---|---|---|---|
| Robot TCP | 192.168.5.1:502 | 越疆机器人 | Modbus TCP，Unit1 |
| Bus2 | 115200，8N1 | 咖博士 F200 | 自有 UART 协议，不创建 RTU |
| Bus3 | 9600，8N1 | 合体落杯落盖、糖浆、电能表 | Unit1、Unit2、Unit3 |
| Bus4 | 19200，8N1 | 制冰机、称重 | Unit1、Unit2 |
| Bus5 | 38400，8N1 | 外部 DI、外部 DO | Unit1、Unit2；第二 DO Unit 待确认 |

电能表必须从 Bus4 Unit3 移到 Bus3 Unit3。Bus3 的所有设备统一 9600，不能在任务中按设备切换波特率。

### 6.2 F200 业务语义

Workflow 不应写死“咖啡/奶是 Modbus”。Coffee2 当前选择的是咖博士 F200 自有 UART 协议。业务层只表达：

- 输出咖啡；
- 输出奶；
- 输出咖啡+奶配方；
- 清洗咖啡/奶管路；
- 查询状态/取消。

具体是 F200 自有协议还是未来 Modbus 咖啡机，由 Target Binding 选择的 Driver 决定。

### 6.3 四路糖浆协议与业务边界

正式《糖浆机接口文件》确认当前糖浆机是四路 Modbus RTU 设备：Bus3、9600、8N1、Unit2。协议寄存器如下：

| 地址 | 读写 | 含义 | 值/单位 |
|---:|---|---|---|
| 0x0000 | FC06 | 本次出糖时间 | 0.1 秒 |
| 0x0001～0x0004 | FC06/FC03 | 糖浆 1～4 任务/状态 | 写 1 启动；读 2 执行中、3 成功、4 失败 |
| 0x0005 | FC06/FC03 | 管路清洗任务/状态 | 写 1 启动；读 2/3/4 |
| 0x000A | FC06 | 糖浆剩余时间设置 | 0.1 秒 |
| 0x000B～0x000E | FC03 | 糖浆 1～4 剩余时间 | 0.1 秒 |

职责必须分开：

- DeviceLibrary 负责时间寄存器、通道任务寄存器、状态解析和 FC03/FC06；
- Bus3 Owner 负责 Unit2 的串口独占、通信重试和命令结果回传；
- Workflow 负责订单是否需要某种口味、四路执行顺序、配方换算、继续/取消和订单终态；
- Server 只接收配方或 F123 调试指令，不直接调用糖浆 Driver。

Coffee1 v2.7.23_ccram 可继承的经验是：同一订单只启动一次，多通道按编号串行执行，逐通道观察执行中和终态。Coffee1 的六通道兼容代码、`mount / 8` 换算和阻塞 delay 不属于本协议事实，Coffee2 不复制。

推荐的每通道闭环：

1. Workflow 从冻结订单取得该通道用量；
2. 通过静态校准把用量转换成 0.1 秒，拒绝 0、溢出和超出安全上限的值；
3. 向 Bus3 投递 `SYRUP_DISPENSE(channel, time_ds)`；
4. Driver 写 0x0000，再向对应 0x0001～0x0004 写 1；
5. Driver 每 100ms 读取该通道状态，但日志只在状态变化时输出；
6. 读到 2 表示设备执行中，读到 3 表示该通道完成，读到 4 表示设备失败；
7. 当前通道完成后，Workflow 才进入下一条非零通道；
8. 四路都跳过或完成后，糖浆步骤完成。

恢复与重试不能简单重写启动寄存器。对同一在途 CommandId：状态 2 时继续等待，状态 3 时完成当前通道，状态 4 时进入人工处理；只有状态明确为空闲且业务条件仍未满足时，继续指令才允许重发。协议没有序列号，因此新命令不能把触发前残留的状态 3 当成本次成功。

当前源码已经具备四路 Driver 和顺序调用，但仍需在实施阶段修正四点：

1. 为订单中的糖浆 3/4 建立正式命名常量，删除 Workflow 中 0x0013/0x0014 魔法地址；
2. 把“配方量→0.1 秒”定义为 Coffee2 静态校准，不再用固定 `COFFEE2_SYRUP_TIME_PER_VOLUME_UNIT=1` 混淆单位；
3. 将“单帧通信超时”和“状态长期不结束”分开，后者应进入设备异常/人工处理，不伪装成通信丢包；
4. 为发送、执行中、成功、失败、恢复增加订单关联日志。

### 6.4 外部输出模块缺口

图纸第 15 页可看到两块 16 路继电器输出模块：

- 第一块包含热水继电器、奶阀、果乳 A/B 阀、果乳 A 泵；
- 第二块包含果乳 B 泵和助力泵。

当前 Coffee2 只绑定一个 IO_OUTPUT Unit2。实施前必须确认：

1. 两块模块的实际 Unit ID；
2. 第二块是否为 Unit3；
3. 两块是否都挂 Bus5；
4. 点位是分别从 0 开始，还是由上位配置组成连续逻辑点。

公共 IO Driver 不需要复制；Target 只需增加第二个实例绑定和第二份 16 点镜像。

### 7.2 API 边界

不建议把所有 IO 操作都塞进 Workflow，也不建议让 Server 直接写 GPIO。推荐 Coffee2 Target 增加一对小文件，例如 Coffee2ProcessIo.c/.h：

- 读取已归一化语义：HotWaterLowReached、CupAtOutputFront；

- 构造外部 IO 命令：SetFruitValve、SetFruitPump；

## 8. Workflow 重构方案

### 8.1 上电初始化必须属于 Workflow

Manager 的职责到“模块初始化、任务创建、网络准备”结束。残杯检查会驱动机器人、读取 Bus3 杯盖状态和 Bus5 出餐口传感器，因此必须由唯一的 Workflow 任务编排，不能塞入 Manager，也不能新增 InitTask。

上电阶段使用系统订单号 `0000`，并复用现有 Robot/Bus 队列。初始化完成前：

- `ucOrderAdmissionOpen=0`，Server 收到订单时明确记录 `ORDER_REJECTED_INIT_NOT_READY`；
- 0x1008 制作状态保持 0，不伪装成正在制作；
- 0x1020 整机状态写 2（初始化中）；
- 找到残杯、传感器不可信或原子动作失败时写 4（报警中）；
- 全部检查完成后写 1（待机中）并开放订单；
- 正常订单或维护任务执行时写 3（忙碌中）。

0x0021 在正式协议中是“整机清除报警”，可在不新增上位机寄存器的前提下同时作为初始化报警确认：人工移除残杯后写 1，Workflow 重新读取所有传感器并从初始化起点复查。它不能只清日志或只向机器人发清报警。

推荐预留 800～899 作为初始化步骤号：

| 步骤 | 含义 |
|---:|---|
| 800 | 初始化开始、关闭订单准入 |
| 810 | 等待 Robot、F200、Bus3 杯盖、Bus5 输入镜像有效 |
| 820 | 检查出餐口 1/2 初始为空 |
| 830 | 检查机械手夹爪是否带杯 |
| 840 | 检查咖啡机内部是否有杯 |
| 850 | 检查压盖位是否有杯 |
| 860 | 检查落杯1/2、落盖3/4 四个出口传感器 |
| 870 | 最终回 Home、复查关键输入 |
| 880 | 初始化报警，等待人工处理和 0x0021 |
| 899 | 初始化完成、开放订单 |

### 8.2 运行状态模型

推荐保留一个 Workflow 任务，增加静态步骤上下文，不新增任务：

~~~mermaid
stateDiagram-v2
    [*] --> IDLE
    IDLE --> VALIDATE: 收到订单快照
    VALIDATE --> REJECTED: 参数或条件非法
    VALIDATE --> PRECHECK: 合法
    PRECHECK --> DISPATCH: 前置条件满足
    DISPATCH --> WAIT_COMMAND: 已投递设备命令
    WAIT_COMMAND --> WAIT_CONDITION: 协议命令完成
    WAIT_CONDITION --> NEXT_STEP: 业务后置条件满足
    WAIT_CONDITION --> WAIT_CONDITION: 条件未满足
    NEXT_STEP --> DISPATCH: 还有步骤
    NEXT_STEP --> COMPLETED: 全部完成
    WAIT_COMMAND --> FAILED: 通信/协议失败
    WAIT_CONDITION --> CANCELED: 取消
    REJECTED --> CANCELED
    FAILED --> CANCELED
    COMPLETED --> IDLE
    CANCELED --> IDLE
~~~

步骤上下文至少保存：

- OrderId、OrderEpoch；
- StepId、Action；
- DeviceId、CommandId；
- Phase；
- 条件检查结果；
- 是否已投递；
- 安全输出开启时间；
- 最后一次日志状态。

### 8.3 超时规则

| 类型 | 是否保留 | 说明 |
|---|---|---|
| 单次 Modbus/UART 通信超时 | 保留 | 当前默认 RTU 500ms，应按设备协议确认 |
| 无响应后的通信重试 | 保留 | 有副作用写命令优先查询状态再重发 |
| Robot 接单前等待 | 持续轮询 | 命令位未清零表示未接单，100ms 查询 |
| Robot 动作时间 | 60 秒 | 从命令位清零、确认接单后开始计时 |
| 杯传感器、重量条件等待 | 不称为通信超时 | Workflow 保持 WAIT_CONDITION |
| 阀/泵/加热器最大开启时间 | 必须保留 | 这是安全上限，不是设备动作成功判定 |

### 8.4 继续与取消

继续订单时：

1. 根据 OrderId 找到当前 StepContext；
2. 重新读取该步骤的后置条件；
3. 条件已满足：记录 RECOVERED_BY_CONDITION，进入下一步；
4. 条件未满足：重新投递同一步设备命令；
5. 使用新的 CommandId，但保留 OrderId、OrderEpoch 和 StepId；
6. 不回退已经完成的步骤。

取消订单时：

- 标记当前 OrderEpoch 取消；
- 停止当前危险输出；
- 对支持取消的设备发取消命令；
- Robot 事务按现有恢复边界处理；
- 订单写失败/取消状态并清理槽位。

## 9. 维护任务设计

热水、咖啡机清洗和果乳清洗不是订单步骤，但仍是多阶段动作。最小方案是让它们复用 Workflow 任务和 F123 调试订单号，使用独立 MaintenanceContext：

| 任务 | Owner | 设备访问 |
|---|---|---|
| 热水补水/烧水 | Workflow | 本地 DO3、DI5/DI6、Bus5 热水继电器 |
| 咖啡/奶管清洗 | Workflow | Bus2 F200 Driver |
| 糖浆四路出液/管路清洗 | Workflow | Bus3 Unit2 糖浆 Driver |
| 果乳 A/B 清洗 | Workflow | Bus5 阀和泵 |

不要为每种维护流程创建新任务。

## 10. 上电设备协议日志

不建议修改 `prvCreateTaskLogged` 来承担设备清单打印。它只证明 RTOS 任务创建成功，不能证明某个设备 Driver 已由链路 Owner 接管。原因是：

- 它只在创建任务时调用；
- 一个 Bus 任务挂多个设备；
- F200 Bus 与 RTU Bus 的设备信息不同；
- 它无法正确表达 Driver、Unit 和协议选择；
- 任务刚创建时，串口/TCP 还可能没有进入可用状态。

推荐由实际 Owner 在任务启动并完成链路初始化后，逐个打印本任务接管的静态绑定。现有日志源已经能表达 `C2Bus3:Cup`、`C2Bus3:Syrup`、`C2Bus3:Lid` 等模块，无需增加新格式或动态字符串。电能表来源表当前仍是旧的 `C2Bus4:EnergyMeter`，迁移 Route 时必须同步改成 `C2Bus3:EnergyMeter`：

~~~text
[0000INFO][C2Robot:MBTcpClient] DEVICE_PROTOCOL:DOBOT_P1_OPEN_C2 result=0 driver=1
[0000INFO][C2Robot:MBTcpClient] DEVICE_LINK:TCP_192.168.5.1_502 result=0 unit=1
[0000INFO][C2Bus2:Coffee] DEVICE_PROTOCOL:F200_UART result=0 driver=12
[0000INFO][C2Bus2:Coffee] DEVICE_LINK:UART2_115200_8N1 result=0 route=2
[0000INFO][C2Bus3:Cup] DEVICE_PROTOCOL:SHENGSHU_COMBINED result=0 unit=1
[0000INFO][C2Bus3:Syrup] DEVICE_PROTOCOL:SYRUP_4CH_MODBUS result=0 unit=2
[0000INFO][C2Bus3:EnergyMeter] DEVICE_PROTOCOL:DDSU666 result=0 unit=3
[0000INFO][C2Bus3:MBRtu] DEVICE_LINK:UART3_9600_8N1 result=0 devices=3
~~~

任务/模块前缀表达“谁在实际运行”，事件名表达“选了哪个协议”，字段表达 Driver、Unit 或 Route。设备名和协议名来自静态 const 表，放在 Flash；不新增任务、队列或动态字符串。`C2Main:System` 继续只打印全局模块初始化、任务创建、网络和内存状态。

## 11. RAM/Flash 影响评估

按最小实现估算：

| 项目 | RAM 增量 | 说明 |
|---|---:|---|
| Robot 控制镜像 40→60 | 20 B | 当前只配置一个机器人 |
| Workflow/Maintenance 上下文 | 约 64～128 B | 单实例静态上下文 |
| 第二外部输出模块镜像 | 约 20～32 B | 16 点+元数据 |
| 启动设备清单 | 0 B 常驻可变 RAM | const 名称与绑定表在 Flash |
| 越疆点位/命令区表 | 0 B 可变 RAM | const 数据在 Flash |
| 糖浆四路步骤上下文 | 约 8～16 B | 复用 Workflow 单实例，不复制 15 寄存器镜像 |
| 上电初始化上下文 | 约 24～40 B | 状态、位置、传感器基线、重试标志和时间戳；复用 Workflow 栈 |
| 合计 | 约 0.15～0.25 KiB | 不含任务栈变化 |

不新增任务、不增加队列深度、不使用 malloc 时，RAM 影响很小。Flash 会因新状态机、日志文本和表格增加数 KB，仍比运行时 Profile 框架轻得多。

## 14. 完整程序编排就绪度结论

当前已经具备“开始分模块编码”的架构条件，但还不具备“无需硬件确认即可一次写出完整量产程序”的事实条件。

| 领域 | 就绪度 | 结论 |
|---|---:|---|
| 公共设备协议与物理 Owner | 高 | 现有 DeviceLibrary、Robot Owner、Bus Owner 可复用 |
| 上位机订单快照与订单号日志 | 中高 | 基础已具备；整机状态 0x1020 必须先修正 |
| 普通订单 Workflow | 中 | 主链存在，但新果乳/糖浆/F200/传感器后置条件仍需落地 |
| 上电残杯检查 | 中低 | 状态机可以确定；三个机器人动作语义和若干传感器极性仍需实机冻结 |
| 量产安全与机械碰撞 | 低 | 3D 图只支持功能分区建模，不能替代机器人轨迹、夹具、杯型和干涉验收 |

因此正确交付顺序是：先冻结 C14～C20 并做机器人/IO 单步验收，再实现初始化状态机和订单状态机，最后进行整机联调。不能用延时、默认传感器值或复用语义不一致的 Robot Action 填补这些缺口。
