# 订单号贯穿、双槽流水线与订单日志方案审核

## 1. 结论

方案总体方向正确，可以作为后续 Coffee2 与 MilkTea 的共同架构基线，但必须修正两项关键判断：

1. **上位机订单号不能替代内部 `OrderEpoch` 与 `CommandId`。**
2. **MilkTea 不能按订单号数值大小决定执行先后，必须保留内部接纳顺序。**

除此之外，下列设计建议采纳：

- 上位机真实订单使用协议中的 16 位订单号；
- 调试命令统一使用 `0xF123`，系统和后台动作使用 `0x0000`；
- 接单时一次性 Snapshot，后续流程不再读取可被上位机修改的命令寄存器；
- MilkTea 使用两个固定活动订单槽，槽位直到完整出餐或完成安全终止才释放；
- Robot1 前段与 Robot2 后段形成流水线，第二笔订单允许停在 `WAIT_BACK`；
- 日志统一为 `[订单号LEVEL][TASK:MODULE] EVENT result=...`；
- 调试命令不占正式订单槽，但必须进入设备 owner 的正常命令路径；
- 不为订单动态创建任务、队列或对象。

## 2. 事实依据

### 2.1 上位机协议

`咖啡售卖机下位机-通信协议.docx` 已明确：

| 字段 | 地址 | 类型 | 语义 |
|---|---:|---|---|
| 订单编号 | `0x0000` | `UINT16` | 上位机下发的真实业务订单号 |
| 有无订单 | `0x0007` | `UINT16` | `1` 表示本次订单数据有效 |
| 订单核对结果 | `0x0008` | `UINT16` | `1` 表示上位机确认订单正确 |
| 当前订单编号 | `0x1000` | `UINT16` | 下位机向上位机回显正在制作的订单 |
| 制作状态 | `0x1008` | `UINT16` | 表中定义为未完成/制作中/完成/失败 |
| 取消订单制作 | `0x0022` | `UINT16` | 旧单订单协议的全局取消触发 |

订单号是完整 16 位字段，因此日志中的四位十六进制格式不会截断订单号。

协议正文仍是单订单语义，且 `0x1008` 的寄存器表与流程示例存在“1 表示制作中”与“1 表示完成”的冲突。MilkTea 新协议不能直接复制这处定义。

### 2.2 Coffee1 v2.7.23_ccram

Coffee1 的可借鉴事实是：

- `machine_input_to_hold()` 将 `0x0000` 的 `order_number` 镜像到 `0x1000` 的 `current_order_number`；
- `0x0007=1` 时复制订单信息，`0x0008=1` 后进入制作；
- `control_flow.c` 的业务判断长期读取 `current_order_number`；
- 流程是单活动订单、全局状态机、全局取消；
- 它没有把订单号带入每个设备命令和结构化日志。

因此 Coffee1 适合作为业务时序和协议交互参考，不适合作为双槽并发结构直接复制。

### 2.3 当前 Coffee2

Coffee2 已经完成了一半的订单号贯穿：

```text
0x0000 Host OrderId
  -> Coffee2Order_t.ausRegister[0]
  -> g_xCoffee2WorkflowStatus.usCurrentOrderId
  -> Coffee2Command_t.ulOrderId
```

同时还存在：

- `ulOrderEpoch`：区分同一固件生命周期内的不同流程世代，防止取消和陈旧完成串单；
- `ulCommandId`：区分同一订单内每一条设备命令；
- `usStepId`：标识业务步骤；
- 静态终态历史：用 `epoch + commandId` 精确找回被后续命令覆盖的完成结果。

当前主要缺口不是“Coffee2 完全没有上位机订单号”，而是：

- 日志底层没有 `OrderId` 字段；
- 手动命令 `prvSubmitManual()` 经过 `memset` 后保持 `ulOrderId=0`；
- 手动制冰 Workflow 将 `usCurrentOrderId` 设置为 `0`；
- Bus、Robot、Device 完成日志不能自动显示所属订单；
- Coffee2 仍是单活动流程加一笔“替换型 pending”，不是 MilkTea 双流水线。

### 2.4 当前 MilkTea

MilkTea Target 目前只是通信和 IO 骨架：

- `app_workflow.c` 每 20 ms 更新 IO；
- 没有订单结构、订单槽、前后段 Workflow 或设备命令关联；
- Robot TCP 仍是连接/测试轮询结构；
- 当前 MilkTea 日志尚未接入公共 `Application/Common/Log`。

所以 MilkTea 文档是目标设计，不代表当前源码已经具备双订单能力。

## 3. 三种身份必须同时保留

| 身份 | 来源 | 作用 | 是否输出给上位机/日志 |
|---|---|---|---|
| `HostOrderId` | 上位机 `0x0000` | 业务关联、状态监控、日志检索 | 是 |
| `OrderEpoch` | 下位机递增 | 区分取消世代和订单号复用 | 通常不输出，仅深度诊断 |
| `CommandId` | 下位机递增 | 区分一笔订单中的具体设备命令 | 通常不输出，仅深度诊断 |
| `StepId` | Workflow 常量 | 说明当前业务步骤 | 是，作为日志字段 |

不能只用 `OrderId + StepId` 匹配设备完成。原因包括：

- 相同步骤可能重试；
- 调试命令可能抢占订单设备命令；
- 上位机订单号可以在下一天复用；
- 队列中的旧完成事件可能晚于取消到达；
- Robot 断线恢复需要继续识别原命令事务。

推荐规则是：

```text
业务观察：HostOrderId + StepId
内部完成匹配：OrderEpoch + CommandId
```

## 4. 为什么不能按订单号大小排序

线上方案提出“选择最小订单号作为最早订单”，这一点不应采纳。

协议本身把不同来源编码在高位：

```text
0x0nnn：线上订单
0xDnnn：线下订单
```

如果先接收 `0xD001`，后接收 `0x0002`，数值排序会错误地让后到的线上订单先执行。以下情况也会破坏数值排序：

- 每日重新从 `0001` 计数；
- 16 位订单号回绕；
- 上位机重发或跨来源分配；
- 将来订单号编码规则调整。

MilkTea 每个活动槽应保存一个内部 `ulAdmissionSequence`：

```text
HostOrderId         负责“这是谁”
AdmissionSequence   负责“谁先来”
```

两个槽都为空时是否重置 `AdmissionSequence` 并不重要；使用 32 位自然递增并按无符号差值比较即可。它不进入协议，也不进入标准日志前缀。

## 5. 两个订单号槽的正确含义

推荐协议模型是：

```text
一个提交邮箱（Host 可写）
        |
        v
下位机校验 + Snapshot + Admission
        |
        +--> Active Slot 0（下位机拥有并对 Host 可读）
        +--> Active Slot 1（下位机拥有并对 Host 可读）
```

不建议让上位机直接选择并写两套完整 Slot，原因是会新增半写入、并发覆盖、槽位搬移和提交原子性问题。

如果后续上位机协议已固定为两个可写入口，则每个入口都必须有独立的 `Submit/Version`，下位机仍应先复制到内部 Slot，绝不能边制作边读取上位机可写区。

## 6. 订单槽释放规则

槽位从接纳起一直代表“系统容量已占用”。以下状态均不能清零：

```text
ACCEPTED
FRONT_RUNNING
WAIT_BACK
BACK_RUNNING
COMPLETING
CANCELING
SAFE_STOPPING
```

只有满足以下条件之一才允许释放：

- Robot2 完成最终出餐，终态已经发布；
- 失败后的设备停止和机械安全退出已经完成；
- 取消后的设备停止和机械安全退出已经完成。

最小发布顺序：

```text
写 Slot.State/Result = terminal
打印 ORDER_COMPLETE / ORDER_FAILED / ORDER_CANCELED
打印 ORDER_SLOT_RELEASED
最后清 Slot.OrderId = 0
```

上位机通过“原订单号变为 0”确认容量释放；若需要可靠保留历史终态，应在后续协议中增加独立的 `LastTerminalOrderId/Result`，但第一阶段不要求建立历史订单队列。

## 7. 调试订单号边界

建议冻结：

```c
#define APP_ORDER_ID_SYSTEM  0x0000U
#define APP_ORDER_ID_DEBUG   0xF123U
```

- `0000`：启动、网络、健康刷新、后台轮询、非业务故障；
- `F123`：上位机维护寄存器触发的原子调试动作；
- 其他值：上位机真实订单。

协议必须明确 `F123` 为保留值，上位机不得生成真实订单号 `F123`。调试命令不占用 MilkTea 正式订单槽，但仍通过 Device/Route owner 队列执行。

## 8. 日志格式审核

建议正式冻结为：

```text
[%04XLEVEL][TASK:MODULE] EVENT result=<int> [field=value ...]
```

示例：

```text
[0000INFO][C2Main:System] STARTUP_COMPLETE result=0
[0123INFO][C2Workflow:Order] ORDER_ACCEPTED result=0 slot=0
[0123INFO][C2Bus4:Scale] TARE_COMPLETE result=0 step=41
[F123INFO][C2Tcp1:Robot1] ACTION_COMPLETE result=0 action=114
```

其中：

- `TASK` 是实际 owner task/Route，不是协议名；
- `MODULE` 是逻辑设备或业务模块；
- 协议、native error、Modbus exception 作为字段输出；
- 100 ms Poll 不逐次打印，只打印阶段变化、重试、超时和链路边沿。

## 9. RAM 影响

当前公共 Logger 的 `AppLogEntry_t` 在常用 ARM ABI 下约 120 字节，32 条 Ring 约 3840 字节。把 `uint16_t usOrderId` 放在 `xSource` 附近可利用现有对齐空洞，预计结构大小仍为 120 字节，即 Ring 静态 RAM 增量可能为 0。

如果 ARMCC/GCC 最终布局未复用空洞，最坏是每条增加 4 字节，32 条共约 128 字节。实施时必须用两个工具链的 `sizeof(AppLogEntry_t)`/map 复核，不能仅凭手算。

MilkTea 两个订单槽的主要 RAM 是两份订单 Snapshot，若每份沿用 32 个寄存器则原始数据仅 64 字节；两槽加状态、epoch、接纳序号通常低于 256 字节。真正的 RAM 成本来自并行 Back Worker 栈，详见 MilkTea 流程设计。

## 10. 最终审核结论

| 方案项 | 结论 |
|---|---|
| Host OrderId 全链路 | 采纳 |
| `0000` 系统、`F123` 调试 | 采纳，需协议保留值 |
| 接单 Snapshot | 采纳 |
| 两个固定活动槽 | 采纳 |
| Slot 不搬家 | 采纳 |
| Front/Back 两阶段流水线 | 采纳 |
| 订单号数值决定 FIFO | 不采纳，改用内部 AdmissionSequence |
| 删除 OrderEpoch/CommandId | 不采纳，继续作为内部正确性机制 |
| 每订单动态 Task | 不采纳 |
| 日志 Ring 扩容 | 暂不采纳，先改关联字段并测高水位 |
| 同时扩展完整历史订单系统 | 暂不采纳 |
