# Coffee2 机器人调度、异常与订单恢复设计方案

> 文档状态：方案预审稿  
> 适用目标：`Coffee2Target`（店中店咖啡售卖机下位机）  
> 更新日期：2026-08-01  
> 目的：记录当前阶段对机器人命令、订单工作流、调试插入、异常处置和回 Home 策略的设计结论，作为后续实现与现场调试的共同依据。

---

## 2026-08-12 实现补充

Coffee2 Robot 任务现在保持永久重连循环：连接失败采用 1/2/5/10/30 秒封顶退避，达到封顶后仍持续重试。在线状态与严格就绪状态分离；严格就绪要求 ready、运行或 idle、上电、使能有效，并且 safety-pause、alarm、collision、drag、recovery 均为零。

Workflow Robot 动作保留 commandId/orderEpoch 和唯一活动事务。链路丢失时设备保持 BUSY/RECOVERING，Workflow 步骤暂停固定超时；重连后先读取目标命令/结果和就绪状态，连续三次一致且命令、结果均为零时才允许最多一次安全重放。结果为一时执行写零并读回零的确认握手；命令仍为一或信号矛盾时不盲目重放，取消立即终止恢复，恢复窗口为 120 秒。SERVER 手动 Robot 命令要求已连接、严格就绪、非 BUSY 且非 RECOVERING，链路故障不重放。

动作前只用 FC15 清除 3121..3139 共 19 个动作命令线圈，并读回确认；3120 不属于清除范围。轮询间隔为 100 ms，但每笔 Modbus 事务使用 `COFFEE2_ROBOT_IO_TIMEOUT_MS`（1000 ms）。关键连接、就绪边沿、恢复、重放和完成事件使用边沿日志，避免重复刷屏。

## 1. 设计边界与原则

Coffee2 是整机下位机主控：它作为 Modbus TCP Server 接收上位机订单和工程调试指令，并作为 Modbus TCP/RTU Master 调度机器人、咖啡机、落杯机、落盖机、糖浆机、制冰机、IO 等设备。

本方案只解决“机器人及其关联订单状态”的调度规则；其他设备应沿用同一套命令身份、完成事件和异常处理原则。

设计遵循以下原则：

1. **一条订单只由 Workflow 顺序推进。** 设备任务只执行命令，不自行决定下一步骤。
2. **EventGroup 只表达实时状态，不作为订单完成的唯一依据。** 工作流推进必须依赖携带订单身份的完成事件。
3. **异常时先保持物理现场，再由人工决定取消和恢复。** 未知物理位置时不得盲目自动回 Home 或继续下发后续动作。
4. **底层机器人控制优先于业务动作，但不抢占一条已经发出的 Modbus 请求。** 响应时间应可预测。
5. **工程调试可以插入单步命令，但必须可追溯，不能伪装成正常订单自动完成。**
6. **不增加无效抽象层。** 机器人仅使用一个执行任务、三条命令队列、一张动作映射表和现有的事件/日志机制。

## 2. 机器人协议分类

### 2.1 底层驱动类命令

机器人 `coil 0~7` 是底层程序控制命令：

| Coil | 含义 | 处理语义 |
|---:|---|---|
| 0 | 开始 | 写入成功即认为命令下发成功 |
| 1 | 停止 | 紧急控制；可能中断当前机器人动作 |
| 2 | 暂停 | 紧急控制；可能中断当前机器人动作 |
| 3 | 上使能 | 写入成功即完成 |
| 4 | 下使能 | 紧急控制；可能中断当前机器人动作 |
| 5 | 清除报警 | 写入成功即完成；不代表物理故障必然已解除 |
| 6 | 进入拖拽 | 工程维护控制 |
| 7 | 退出拖拽 | 工程维护控制 |

下位机写此类线圈时统一采用上升沿：先写 `0`，再写 `1`。这类命令没有“完成反馈线圈等待”语义：Modbus TCP 写入成功记录 `INFO`；写入、连接或协议失败才记录 `ERROR`。

### 2.2 机器人业务动作类命令

`coil 3120~3138` 是 Coffee2 发给机器人的动作命令；`coil 3100~3118` 是机器人给 Coffee2 的完成反馈。Coffee2 读取到完成反馈后必须清零该反馈线圈。

| 业务动作示例 | 命令 Coil | 完成 Coil |
|---|---:|---:|
| 启动信号 | 3120 | 3100（机器人就绪） |
| 回 Home | 3121 | 3101 |
| 取热杯 | 3123 | 3103 |
| 取冷杯 | 3124 | 3104 |
| 去落盖 1/2 | 3125 / 3126 | 3105 / 3106 |
| 去制冰机 | 3127 | 3107 |
| 去咖啡机前 / 放杯 | 3128 / 3129 | 3108 / 3109 |
| 去打印机 | 3130 | 3110 |
| 取出餐口 1/2 | 3131 / 3132 | 3111 / 3112 |
| 去咖啡机取杯 | 3133 | 3113 |
| 取压盖 / 压盖 | 3134 / 3135 | 3114 / 3115 |
| 放储杯 / 取储杯 | 3136 / 3137 | 3116 / 3117 |
| 放出餐口 | 3138 | 3118 |

业务动作必须等待对应完成线圈，且在等待期间检查机器人报警、连接状态和底层控制队列。动作成功后向 Workflow 发送带身份的完成事件。

## 3. 命令身份与订单防呆

### 3.1 每条命令必须携带的字段

所有由 Server 或 Workflow 发往设备任务的命令，应至少包含：

```text
order_id        订单号
order_epoch     订单代次；每开始、取消或替换订单时递增
command_id      单调递增的命令编号
source          WORKFLOW / MAINTENANCE
action          设备动作或底层控制项
timeout_ms      本动作的超时参数
retry_limit     最大重试次数
```

机器人完成事件必须原样带回 `order_id + order_epoch + command_id`。Workflow 仅接受与当前等待步骤完全匹配的完成事件；任何旧订单的残留事件、超时后的迟到事件或其他动作事件均只能记录日志，不能推进新订单。

### 3.2 EventGroup 的正确职责

每个设备保留独立 EventGroup，用于表达：在线、报警、忙碌、已到 Home、动作完成等实时状态，供日志、上位机状态页和安全条件读取。

EventGroup 不含订单号，因此不能单独证明“该完成状态属于当前订单”。订单推进只能依赖命令完成事件队列；EventGroup 只作为状态验证和安全互锁条件。

### 3.3 调试命令身份

工程调试命令固定使用：

```text
order_id = 1234
source   = MAINTENANCE
```

必须同时满足这两个条件才视为调试命令，不能只依据订单号判断。正式生产 Target 应关闭人工单机动作寄存器，或使其返回 Modbus 非法地址/非法数据异常；仅工程调试 Target 开启。

## 4. 机器人任务与队列优先级

### 4.1 单任务、三队列

机器人仍由一个 `C2Robot` TCP Client 任务独占 TCP 连接和 Modbus 事务，避免多任务同时访问同一机器人连接。该任务使用三条静态队列：

```text
RobotBaseQueue   底层控制：coil 0~7，最高优先级，建议深度 2
RobotDebugQueue  工程调试动作，第二优先级，建议深度 2
RobotAutoQueue   Workflow 自动订单动作，普通优先级
```

取命令顺序固定为：

```text
RobotBaseQueue → RobotDebugQueue → RobotAutoQueue
```

该设计比在单一队列中搬移和重排消息更直观，也避免额外的动态内存开销。所有队列及其控制块使用静态创建，放入符合 CCM 使用约束的区域。

### 4.2 任务优先级

`C2Robot` 任务优先级应高于 Workflow 和各 RTU Bus 任务，使 Server 投递的底层机器人控制能尽快执行；但不得高于网络协议栈所需关键处理和硬件中断，以免反向阻塞 TCP 收发。

### 4.3 等待动作完成期间的行为

业务动作的完成等待按短周期轮询，例如 `100 ms`：

```text
读取机器人报警和完成 Coil
→ 检查 RobotBaseQueue
→ 有底层控制命令则立即执行
→ 无底层控制则延时一个轮询周期
```

因此底层控制的响应上限约为：

```text
一个轮询周期 + 当前 Modbus TCP 事务时间
```

调试动作不在当前业务动作等待期间插入；它必须等待当前单步业务动作成功、失败或终止后再优先执行。这避免一条取杯、压盖等实体动作被另一条实体动作中途交叉。

## 5. 业务动作超时、恢复确认与重试

### 5.1 每个动作统一配置

机器人动作使用一张静态动作表，表项至少含：

```text
动作名称、命令 Coil、完成 Coil、标准超时、最大重试次数
```

超时不可全部固定为一个值；应在现场调试后按动作距离和负载分别配置。业务动作默认允许一次受控重试，即 `retry_limit=1`；底层控制 `retry_limit=0`。

### 5.2 受控重试顺序

网络异常时，不能在超时后直接重复写动作线圈。第一次命令可能已被机器人执行，只是完成反馈未能读回。统一流程如下：

```text
1. 写命令 Coil 上升沿：0 → 1。
2. 等待对应完成 Coil。
3. 超时后先恢复 TCP 连接（若已经断开）。
4. 读取：机器人报警、就绪和动作完成 Coil。
5. 完成 Coil=1：清零反馈，视为成功；禁止再次下发动作。
6. 完成 Coil=0 且无报警、机器人就绪：仅重发一次动作。
7. 最终仍未完成：输出 ERROR，向 Workflow 发送失败事件。
```

机器人报警时不允许自动重试；应立即终止当前动作并进入订单异常状态。

## 6. 自动订单、调试插入与人工干预

### 6.1 自动订单

Workflow 每次只投递下一条已确认具备前置条件的命令。设备完成事件到达后，Workflow 校验订单身份、代次、命令号和预期动作，再投递下一步。

这样故障时不会存在大量“已经排队、但不应继续执行”的后续物理动作。

### 6.2 调试插入

调试命令的规则是：

```text
当前机器人单步结束
→ RobotDebugQueue 中有命令时先执行一条
→ 再继续 RobotAutoQueue 中的订单动作
```

不实现“保存工作流上下文—暂停—恢复”的复杂机制。调试动作的结果只归属于调试命令，不能使订单步骤完成。

若工程人员在订单运行中插入会改变机器人位置、抓取物或设备状态的调试动作，Workflow 应置位 `MANUAL_INTERVENED`：

- 自动队列可按工程调试需要继续被读取；
- 但该订单不得自动上报为“可信正常完成”；
- 后续每一个自动动作都必须重新检查机器人就绪、报警和必要的前置位置条件；
- 条件不满足时进入异常锁定，而不是假定调试后仍处于原流程位置。

正式客户使用场景不开放此类插入操作。

### 6.3 底层控制插入

停止、暂停、下使能、拖拽等底层控制可以在业务动作等待期间执行。它们会标记当前订单为 `EXTERNALLY_INTERRUPTED`，因为当前动作是否仍可安全视为成功无法由软件自动断定。

## 7. 订单完成、异常、取消与回 Home

### 7.1 正常订单完成

Coffee2 建议统一使用以下收尾流程：

```text
饮品已放置到出餐口或储杯位
→ 订单业务完成
→ 机器人回 Home
→ Home 到位
→ IDLE_READY，允许接收下一订单
```

`0x1008=2` 可在饮品已实际交付后置位；同时需要通过流程状态寄存器表示“RETURNING_HOME”。在机器人尚未到 Home 前，Server 不接受下一订单，即使饮品状态已显示完成。

### 7.2 业务动作最终超时或设备异常

异常时进入 `FAULT_LATCHED`：

```text
ORDER_RUNNING
→ FAULT_LATCHED
→ 记录订单、步骤、设备、动作、错误码和最后已知状态
→ 停止自动调度后续命令
→ 保持状态轮询、日志、底层停止命令和取消命令可用
→ 等待人工处理
```

这里的“卡在当前流程”是状态机停在当前故障步骤，不是任务死循环或阻塞等待。FreeRTOS 任务必须继续响应网络、取消命令、设备状态和安全控制。

异常发生后**不得自动回 Home**：例如“取杯超时”时，机器人可能仍在运行、夹持杯子或仅是网络短时断开。此时直接回 Home 有重复动作、带杯碰撞或机械干涉风险。

### 7.3 人工取消与受控恢复

推荐上位机写 `0x0022` 作为“取消当前订单”命令。Coffee1 也采用该方式，并在异常状态等待人工取消。

Coffee2 取消流程：

```text
人工确认现场
→ 上位机写 0x0022
→ CANCELLING
→ 取消或停止可安全停止的外围设备
→ 根据当前杯子/设备状态执行必要的收尾
→ 确认机器人可安全移动后下发回 Home
→ Home 成功：IDLE_READY
→ Home 启动或完成超时：机器人 STOP，进入 FAULT_UNRECOVERED
```

建议保留 Coffee1 的两个保护时间：回 Home 启动超时约 `5 s`、回 Home 完成超时约 `15 s`，但应在现场按机器人实际动作时间确认。

与 Coffee1 不同，Coffee2 在“回 Home 成功且无报警”后不建议默认停止机器人程序，应保持已使能且就绪，等待下一订单。只有回 Home 失败、机器人报警或维护人员明确要求时，才下发停止机器人程序。

### 7.4 故障恢复顺序

```text
1. 上位机读取：订单号、当前步骤、错误码、设备状态、机器人状态。
2. 人员检查物理现场，确认杯子、机械臂和外围设备状态。
3. 写 0x0022，取消订单并执行受控收尾。
4. 若回 Home 成功：保留最近一次失败记录，系统进入待机。
5. 若回 Home 失败：维持 FAULT_UNRECOVERED，禁止新订单。
6. 故障已排除后写 0x0021 清报警，并确认机器人 Home、无报警、设备就绪。
7. 仅在 IDLE_READY 状态下接收下一订单。
```

取消或开始新订单时递增 `order_epoch`，设备任务收到旧代次的排队命令和迟到事件必须丢弃并记录诊断日志。

## 8. 上位机状态上报建议

保持 Coffee1 已验证的主状态语义：

| 寄存器/状态 | 语义 |
|---|---|
| `0x1008=1` | 制作中 |
| `0x1008=2` | 饮品制作/交付完成 |
| `0x1008=3` | 制作失败，需要人工处理 |
| 流程状态寄存器 | 当前 Workflow 状态，例如 `RETURNING_HOME`、`FAULT_LATCHED` |
| 设备状态寄存器 | 机器人、咖啡机、制冰机、IO 等在线/报警/忙碌状态 |
| 错误详情寄存器（待协议补充） | 错误设备、动作、步骤、错误码、重试次数 |

Coffee1 通过 `0x1008`、设备状态字段和流程状态字段向上位机报告错误；Coffee2 应保留这个可轮询模式，并补全“错误详情”和“是否允许新订单”的协议字段。

## 9. 日志规范

日志采用统一格式：

```text
[Level][Task][Module] 中文事件 result=值 field=value...
```

每条机器人动作日志必须区分来源：`自动调度`、`调试插入`、`底层控制`。不要使用语义不清晰的 `flag`，改用 `done`、`alarm`、`attempt`、`edge` 等字段。

示例：

```text
[INFO][C2Robot][MbTcpClient] 自动调度 下发取热杯指令 result=0 order=10086 epoch=7 command=52 step=3 cmd_coil=3123 done_coil=3103 attempt=1

[INFO][C2Robot][MbTcpClient] 自动调度 取热杯完成 result=0 order=10086 epoch=7 command=52 done_coil=3103 done=1

[INFO][C2Robot][MbTcpClient] 调试插入 下发压盖指令 result=0 order=1234 epoch=0 command=71 cmd_coil=3135 done_coil=3115

[INFO][C2Robot][MbTcpClient] 底层控制 执行机器人暂停 result=0 source=调试 coil=2 edge=rising

[WARN][C2Robot][MbTcpClient] 自动调度 取热杯等待超时，开始恢复确认 result=-1 order=10086 command=52 attempt=1 timeout_ms=30000

[ERROR][Workflow][Order] 自动调度 订单进入等待人工取消状态 result=-1 order=10086 epoch=7 step=3 action=取热杯 state=FAULT_LATCHED

[INFO][Server][ModbusTcpServer] 收到取消订单 result=0 order=10086 register=0x0022

[ERROR][C2Robot][MbTcpClient] 机器人回Home超时，停止机器人 result=-2 order=10086 timeout_ms=15000
```

日志只在状态变化、命令下发、动作完成、重试、异常、连接变化时输出；禁止在轮询循环中重复打印相同状态。

## 10. Coffee1 参考结论

Coffee1 可参考的内容：

- 订单异常后置制作失败状态并等待人工取消；
- `0x0022` 作为取消订单入口；
- 异常取消时先尝试处理杯子，再回 Home；
- 回 Home 发起和完成均有超时保护；
- Home 失败后停止机器人，避免状态机永久卡住；
- 上位机通过制作状态、设备状态和流程状态轮询故障。

Coffee1 不应直接沿用的内容：

- 多处散落的全局流程变量和计时器；
- 不同流程分支对“完成后是否 Home”的不一致行为；
- 用 Event/线圈状态直接推进新订单而未绑定订单身份；
- 取消流程中大量阻塞式延时和重复写线圈；
- 异常恢复后默认停止机器人、导致下一订单还需额外人工启动的行为。

Coffee2 应采用“命令身份 + 完成事件 + 统一动作表 + 受控取消”的方式实现相同目标。

## 11. 后续实现清单

1. 建立机器人动作映射表：动作、命令 Coil、完成 Coil、超时、重试限制。
2. 将现有机器人普通队列拆为底层控制、调试、自动三条静态队列。
3. 将业务动作等待改为可检查 `RobotBaseQueue` 的短周期等待。
