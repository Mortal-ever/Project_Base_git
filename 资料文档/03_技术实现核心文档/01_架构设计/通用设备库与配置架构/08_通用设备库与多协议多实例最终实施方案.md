## 2. 最终结论

设备库不是把所有设备和协议集中到一个大模块中，而是保存一套很小的公共关系：

```text
Category  设备类别
Role      产品中的业务角色
Instance  一个物理设备实例
Driver    设备行为和握手语义
Protocol  线上的帧格式、功能码和校验
Route     一个物理通信资源及其唯一 owner
Transport 字节收发载体
```

最终规则如下：

1. `Workflow` 只提交业务命令，不接触 UART、TCP、Unit ID、寄存器或线圈。
2. `Driver` 负责同一类设备的行为，例如制冰、去皮、机器人动作握手。
3. `Protocol` 只负责线帧，不解释“制冰机前”或“奶茶机前”。
4. `Route` 选择且固定一种 Protocol，并拥有队列、通信上下文和 owner task。
5. `Transport` 只负责 UART、TCP 等字节通道。
6. 同品类但不同协议使用不同 `DriverId`，并由 Driver 声明所需 Protocol。
7. 同一协议但语义不同使用同一 Driver 加不同实例的 `const` 点位表；不创建
   独立 Profile 层，不建立 Profile registry/manager/ID 运行态。
8. 一个物理 UART 在一次启动生命周期内只选择一种协议。私有 UART 仍创建
   UART Transport，但不创建 ModbusPort/nanoMODBUS。
9. 一个物理资源只有一个 owner。普通 Serial Route 通常对应一个 owner task
   和一个队列；Local GPIO 不创建通信 task。
10. 两台或多台机器人复用 task 函数和 Driver 代码，但各自拥有 endpoint、
    runtime、queue、事务和断线状态；不能复制 `robot1.c`、`robot2.c`。

### 2.1 本方案明确拒绝的结构

以下结构不进入第一版公共架构：

- 独立 `ProfileId`、Profile 注册表、Profile 管理任务和运行时 Profile 切换。
- 一个万能 `CustomPort`，在其中用大 switch 兼容所有私有协议。
- 每种协议、每个设备各创建一个无边界任务。
- `DeviceManager` 任务作为所有命令的第二个调度中心。
- 运行时动态插件、字符串查找注册表、动态内存配置对象。
- 为未来可能存在的设备提前配置全部品牌、协议和最大数组。

## 3. 已确认需求与非目标

### 3.1 必须满足的需求

- Coffee2 的设备调度行为可以作为 MilkTea 的迁移母体。
- 同一工程可以拥有 Robot1、Robot2，后续可以增加 Robot3 等实例。
- 同品类设备可以使用 Modbus RTU、Modbus TCP 或确定的私有协议。
- 同一种线上协议在不同产品或机器人实例中允许有不同业务语义。
- 同一物理 UART 可以挂多个 Modbus Unit；一个私有无寻址协议只能挂一个设备。
- 私有协议的 UART 不创建 `ModbusPort`，避免协议层误用和无效 RAM。
- IO 支持本地 GPIO 和远程 Modbus IO；同一个逻辑输出只能有一个 writer。
- 命令、完成、取消、超时、重连、结果和日志仍使用现有 commandId、orderEpoch、
  EventGroup、terminal history 和日志体系，不建立第二套票据体系。
- 不增加运行时 malloc；公共配置、描述符和点位表使用 `const`，运行态使用
  静态对象。

### 3.2 非目标

- 本方案不冻结 MilkTea 未提供的设备协议地址、波特率、IP、Unit ID 或电气图
  参数。正式协议和电气资料冻结前，MilkTea 的具体数值不得猜测。
- 不把产品订单流程、奶茶配方、咖啡业务步骤抽成设备库能力。
- 不在本阶段实现 Flash 持久化配置、运行时换协议、在线新增设备或动态脚本。
- 不把 Robot TargetId 变成公共业务枚举；它是产品/角色局部语义。
- 不承诺机器人数量无限增加。每新增一个 owner task 都必须重新测量 RAM、堆和
  栈高水位。

## 4. 概念词典与判定树

### 4.1 概念定义

| 概念 | 一句话定义 | 典型例子 |
| --- | --- | --- |
| Category | 设备硬件/行为的大类，决定可选 Driver 范围 | ROBOT、ICE、SCALE、IO |
| Role | 产品业务对设备的角色命名 | Robot1、Robot2、IceDispenser |
| Instance | 一个真实、可独立监控和投递命令的设备 | MilkTea Robot2 |
| Driver | 面向设备行为的执行算法和状态机 | IceDriver、DobotRobotDriver |
| Protocol | 设备在线路上的帧、功能码、校验和错误规则 | Modbus RTU、私有 UART |
| Route | 一个通信资源及其协议选择、队列和 owner | UART4/ModbusRTU |
| Transport | 实际收发字节的后端 | UART/RS485、TCP |
| TargetId | 某个产品/角色内的目标语义索引 | Robot2 的 TO_TEA_MACHINE |

### 4.2 选择判定树

```text
新增需求
  │
  ├─ 是否同一物理资源上的另一台设备？
  │       ├─ 是：新增 Instance，不能新增 owner 争抢同一资源
  │       └─ 否：继续判断
  │
  ├─ 线上的帧格式/校验/同步是否不同？
  │       ├─ 是：新增确定的 Protocol 和匹配的 DriverId
  │       └─ 否：继续判断
  │
  ├─ 设备行为和握手是否相同，仅地址或产品语义不同？
  │       ├─ 是：复用 Driver，换 const 配置/点位表
  │       └─ 否：继续判断
  │
  ├─ 是否只有一个固定分支不同？
  │       ├─ 是：先在现有 Driver 内增加明确的小分支，并记录审查卡
  │       └─ 否：新增 DriverId，声明 RequiredProtocolId
  │
  └─ 是否真的需要跨产品运行时切换？
          ├─ 否：保持编译期 const 配置
          └─ 是：先证明现有静态配置无法满足，再单独做资源审查
```

## 5. 最终分层与调用边界

```text
Product Workflow / Server
        │  Role + TargetId + parameters + commandId/orderEpoch
        ▼
Device command API / Instance binding
        │  Instance -> Route + Driver + Protocol requirement
        ▼
Route owner task / queue
        │  串行化事务，保存 route/runtime，调用 Driver
        ▼
Driver
        │  设备行为、握手、状态和恢复；不拼线帧
        ▼
Protocol
        │  ModbusPort 或确定的 PrivateProtocolPort
        ▼
Transport
        │  UART/RS485 或 TCP；不解释设备语义
        ▼
HAL / lwIP
```

越层限制：

| 层 | 可以做 | 禁止做 |
| --- | --- | --- |
| Workflow/Server | 业务步骤、参数、取消、上位机 ABI | 访问串口、寄存器、线圈、帧缓冲 |
| Device API | 查 Instance、送统一命令、读取标准结果 | 直接操作具体 UART |
| Route owner | 排队、资源互斥、调用 Driver、发布结果 | 解释订单语义、复制协议状态机 |
| Driver | 行为、握手、超时、重连恢复 | 自己选择另一条 Route 或拼接产品流程 |
| Protocol | 组帧、分包、校验、功能码、错误映射 | 判断设备“是否落冰成功” |
| Transport | 打开/关闭、发送/接收、原生错误 | 解析 Modbus 或私有协议字段 |
| HAL/lwIP | 外设和网络原语 | 反向调用 Workflow |

## 6. 最终静态数据模型

下面是设计草案，用于冻结概念和所有权，不要求一次性照抄进当前源码。写法兼容
ARMCC V5.06：不使用 C11、`//` 注释、变长数组或动态分配。

```c
typedef enum {
	DEVICE_CATEGORY_ROBOT = 1,
	DEVICE_CATEGORY_ICE = 2,
	DEVICE_CATEGORY_SCALE = 3,
	DEVICE_CATEGORY_POWER_METER = 4,
	DEVICE_CATEGORY_IO = 5
} DeviceCategory_e;

typedef enum {
	DEVICE_ROLE_ROBOT_1 = 1,
	DEVICE_ROLE_ROBOT_2 = 2,
	DEVICE_ROLE_ICE = 3
} DeviceRole_e;

typedef enum {
	PROTOCOL_NONE = 0,
	PROTOCOL_MODBUS_RTU = 1,
	PROTOCOL_MODBUS_TCP = 2,
	PROTOCOL_MILKTEA_VENDOR_UART_V1 = 3,
	PROTOCOL_ICE_PRIVATE_UART_V1 = 4
} ProtocolId_e;

typedef enum {
	DRIVER_ROBOT_DOBOT_3100 = 1,
	DRIVER_ICE_MODBUS_V1 = 2,
	DRIVER_ICE_PRIVATE_V1 = 3
} DriverId_e;

typedef enum {
	TRANSPORT_UART = 1,
	TRANSPORT_TCP = 2,
	TRANSPORT_LOCAL_GPIO = 3
} TransportType_e;

typedef struct {
	uint16_t usCommandCoil;
	uint16_t usResultCoil;
} RobotPoint_t;

typedef struct {
	const RobotPoint_t *pxPoints;
	uint8_t ucPointCount;
	uint8_t ucReserved;
} RobotDriverConfig_t;

typedef struct {
	DriverId_e xDriverId;
	DeviceCategory_e xCategory;
	ProtocolId_e xRequiredProtocol;
} DeviceDriverRef_t;

typedef struct {
	uint8_t ucRouteId;
	TransportType_e xTransport;
	ProtocolId_e xProtocol;
	uint8_t ucEnabled;
	const void *pvTransportConfig;
	const void *pvProtocolConfig;
} RouteConfig_t;

typedef struct {
	DeviceRole_e xRole;
	uint8_t ucInstanceId;
	uint8_t ucRouteId;
	uint16_t usProtocolAddress;
	const DeviceDriverRef_t *pxDriver;
	const void *pvDriverConfig;
} DeviceInstanceConfig_t;
```

关键约束：

- `DeviceInstanceConfig_t::pvDriverConfig` 复用现有配置入口，不增加 Profile 指针；
  Driver descriptor 只描述 DriverId 和 RequiredProtocol，不持有实例运行态。
- Robot 的 `TargetId` 是产品侧枚举，直接作为 `RobotPoint_t` 数组下标。
- 点位表只包含命令线圈和结果线圈；不存字符串、函数指针或运行时状态。
- `RouteConfig_t` 是启动时固定选择；运行中不依据每条命令切换协议。
- `RouteConfig_t::pvTransportConfig` 保存该 Route 的 UART 参数或 TCP
  endpoint；`pvProtocolConfig` 只指向该 Route 选中 Protocol 所需的
  最小 const 配置。两者都不放入 Instance，也不创建最大 union。
- Category 由 Driver descriptor 唯一给出，Instance 不再重复保存 Category。
- `usProtocolAddress` 在 Modbus 中表示 Unit ID，在有寻址能力的私有协议
  中表示节点地址；无寻址点对点协议使用 0，其合法性由所选
  Protocol validator 判定。
- 所有 runtime、queue、Transport context、协议镜像和状态必须由 owner 负责静态
  保存，不能把 `const` 配置误当成可写状态。

## 7. 同品类不同协议

### 7.1 判定规则

同一 Category 只表示“这是同一类设备”，不代表线路协议相同。以下任何一项不同，
都不能把两个设备强行塞进同一 Protocol：

- 帧头、长度、转义、分包或粘包规则不同。
- 校验方式不同。
- 请求/响应匹配规则不同。
- 失败码、重试和设备 ACK 语义不同。
- Modbus 功能码模型与私有命令模型不同。

处理方式是：

```text
Category=ICE
  ├─ Driver=ICE_MODBUS_V1  -> RequiredProtocol=MODBUS_RTU
  └─ Driver=ICE_PRIVATE_V1 -> RequiredProtocol=PRIVATE_UART
```

Route 必须同时声明 `ProtocolId`，启动校验时比较：

```text
Instance.Driver.RequiredProtocol == Instance.Route.Protocol
```

不相等时拒绝启动该 Instance，并打印配置错误；不得运行时“先按 Modbus 发，失败
后再试私有协议”。

### 7.2 Modbus Route

- 创建 UART Transport、ModbusPort/nanoMODBUS 和一个 owner task。
- 一个 Route 可以挂多个有 Unit ID 的设备。
- 每个设备的地址、最小帧间隔和参数放在 const Instance/Binding 配置中。
- Route 的 UART 参数在启动时固定；同一物理 UART 不在命令之间切换波特率。
- 事务顺序由 owner task 保证，避免多个任务同时访问同一 RS485 收发器。

### 7.3 私有 UART Route

- 创建 UART Transport 和私有协议 Port。
- 私有 Port 负责组帧、分帧、粘包处理、校验、ACK/响应匹配和错误映射。
- 不创建 ModbusPort，不调用 nanoMODBUS。
- 无寻址私有协议只能绑定一个设备；若硬件有多个相同设备，必须使用独立
  UART/独立 Route，或由正式协议提供设备地址后再评审。
- 不创建万能 `PrivatePort` 来兼容所有品牌；每种私有协议有确定 Port 类型。

### 7.4 TCP Route

- Modbus TCP Robot 使用 TCP Transport + ModbusPort + Robot Driver。
- 每一个独立 endpoint/session 是一个独立 Route。
- 同一 TCP 任务模板可被多个实例复用，但每个实例保存自己的连接、重连、事务
  和命令队列。

## 8. 同协议不同语义：Robot 的最小扩展

越疆类机器人可能使用 Modbus TCP 和 3100～3139，或者扩展到 3100～3150；
但同一个动作线圈在 Coffee2
表示“去制冰机”，在 MilkTea 可能表示“去奶茶机”。这不是新 Protocol，也不是
新 Driver；它是同 Driver 的实例级语义映射。

当前公共库把寄存器范围作为协议变体处理：

- `DOBOT_ROBOT_PROTOCOL_LEGACY_3139`：读取 3100～3139，允许 Robot1、Robot2、
  Robot3 角色使用。
- `DOBOT_ROBOT_PROTOCOL_EXTENDED_3150`：读取 3100～3150，只允许 Robot1、
  Robot2。3140～3150 尚无正式点位语义，因此仅纳入合法读取范围，不映射成业务
  动作。
- Robot3 计划使用节卡协议；当前只保留 Driver/Protocol 标识，不实现帧、动作或
  运行态，避免用越疆语义假装兼容节卡。

### 8.1 数据布局

```text
Robot1 Instance -> RobotDriverConfig_t -> const s_axCoffeeRobotPoints[]
Robot2 Instance -> RobotDriverConfig_t -> const s_axMilkTeaRobot2Points[]
```

每个点 2 个 `uint16_t`，占 4 B。19 个动作点约占 76 B Flash/Robot；映射新增
常驻 RAM 为 0 B。相同映射可由多个机器人共享同一张 const 表。

```c
typedef enum {
	COFFEE2_ROBOT_TARGET_HOME = 0,
	COFFEE2_ROBOT_TARGET_CUP = 1,
	COFFEE2_ROBOT_TARGET_ICE = 2,
	COFFEE2_ROBOT_TARGET_LID = 3,
	COFFEE2_ROBOT_TARGET_EXAMPLE_COUNT = 4
} Coffee2RobotTarget_e;

typedef enum {
	MILKTEA_R2_TARGET_HOME = 0,
	MILKTEA_R2_TARGET_CUP = 1,
	MILKTEA_R2_TARGET_TEA_MACHINE = 2,
	MILKTEA_R2_TARGET_LID = 3,
	MILKTEA_R2_TARGET_EXAMPLE_COUNT = 4
} MilkTeaRobot2Target_e;

static const RobotPoint_t
	s_axCoffeeRobotPoints[COFFEE2_ROBOT_TARGET_EXAMPLE_COUNT] = {
	{ 3121U, 3101U },
	{ 3123U, 3103U },
	{ 3127U, 3107U },
	{ 3134U, 3114U }
};

static const RobotPoint_t
	s_axMilkTeaRobot2Points[MILKTEA_R2_TARGET_EXAMPLE_COUNT] = {
	{ 3121U, 3101U },
	{ 3123U, 3103U },
	{ 3127U, 3107U },
	{ 3134U, 3114U }
};
```

示例只列出 4 个点，不用未初始化的零值冒充 19 个正式点。完整实现若有
19 个有效点，则表数据为 76 B。正式地址必须以该产品机器人 PLC 信号表冻结。Driver 只
读取 `pxPoints[TargetId]`，不读取“制冰机/奶茶机”等字符串。

### 8.2 调用关系

```text
Coffee2 Workflow: TargetId=COFFEE2_ROBOT_TARGET_ICE
MilkTea Robot2 Workflow: TargetId=MILKTEA_R2_TARGET_TEA_MACHINE
                         │
                         ▼
Robot Driver(instance): point = pxConfig->pxPoints[TargetId]
                         │
                         ├─ command coil: point.usCommandCoil
                         └─ result coil : point.usResultCoil
```

产品 Workflow 仍可以为不同 Role 定义不同 TargetId 名称；不要把一个产品的
`COFFEE2_ACTION_ROBOT_TO_ICE=114` 直接作为公共 Driver API。

### 8.3 Robot1/Robot2 与 Robot3 边界

每个机器人 Instance 独立拥有：

- Role、InstanceId、TCP endpoint、Unit ID。
- `RobotRuntime`、状态镜像、当前事务、重连计数和重连阶段。
- 命令队列和 owner task。
- `RobotDriverConfig_t` 及其 const 点位表。

Driver 代码和 task 函数只有一份。Robot1 掉线时只进入 Robot1 的恢复状态；不能
清空 Robot2 队列、覆盖 Robot2 状态或让 Workflow 把 Robot2 当成离线。

Robot3 若采用节卡协议，必须在正式协议到齐后建立新的确定 Driver 和 Required
Protocol；它不能复用越疆点位表。公共多实例结构仍可复用，但节卡的连接、握手、
动作和恢复状态机必须由节卡协议证据重新冻结。

## 9. IO 设计

IO 的“逻辑点”与“物理提供者”分开：

```text
LogicPoint -> IO Provider -> Local GPIO 或 Remote Modbus Route
```

- Local GPIO：直接使用已定义的 GPIO owner，不创建 Protocol、ModbusPort 或
  通信 task。
- Remote Modbus IO：使用正常 Modbus RTU Route，由 IO Driver 读写寄存器/线圈。
- 读写后确认由 Provider/Driver 完成；Workflow 只等待统一 DeviceResult。
- 每一个逻辑输出只能登记一个 writer。冲突在启动校验时拒绝，不能依赖调用顺序
  解决。
- 当前 IO 设备需要继续沿用已有日志和状态镜像，不另造一套 IO 状态总线。

第一版不建立复杂 Provider registry。固定产品可以使用 const 映射和小型 switch；
当实际 IO 类型超过单个小模块可维护范围，再使用架构审查卡评估拆分。

## 10. 多实例、任务与资源所有权

### 10.1 所有权规则

| 资源 | owner | 共享规则 |
| --- | --- | --- |
| 物理 UART/RS485 | 一个 Serial Route owner task | 其他任务只能投递命令 |
| ModbusPort | 所属 Route task | 不跨任务调用 |
| 私有 Protocol Port | 所属 Private Route task | 不与 ModbusPort 共用 |
| TCP endpoint/session | 一个 TCP Route/Robot owner | 每实例独立连接状态 |
| Local GPIO 输出 | 一个逻辑 writer/provider | 其他模块提交逻辑命令 |
| 命令队列 | 所属 Route/Robot instance | 只由 owner 消费 |
| 业务订单队列 | Workflow | 设备任务不能反向读取订单 |
| 日志队列 | 日志模块 | 业务模块只写现有日志 API |

不新增 `DeviceManager task`。设备库的“管理”只体现在启动时遍历 const 配置、
注册 Route 和创建按需 owner task；运行时命令直接进入目标 Route 队列。

### 10.2 TCP Robot 为什么暂时一实例一任务

当前 Transport/Modbus 调用包含同步等待。多个机器人硬塞进一个共享任务会产生头部
阻塞：Robot1 一次连接/响应等待可能延迟 Robot2 的 100 ms 接单轮询和动作结果轮询。

因此第一阶段使用：

```text
一个 Robot Instance -> 一个 owner task -> 一个 TCP session -> 一个 queue
```

代码不复制；通过 `pvArgument` 传入 `RobotRuntime`。只有在实测三台以上的 RAM
不足，且确实需要继续增加机器人时，才重新评审“全非阻塞共享任务”。

### 10.3 资源预算

完整 Robot Instance 不等于 0 RAM。根据当前 Coffee2 配置和已有观测：

- `COFFEE2_ROBOT_TASK_STACK=1024` words，约 4096 B/新增 owner task。
- 4 深度静态命令队列约 212 B（含队列存储和控制开销的工程估算）。
- 另有 TCB、Robot runtime/status/data、Transport TCP 状态和 lwIP 连接资源。
- Coffee2 日志曾观察到 `HEAP_AFTER_TASK_CREATE` 约 11272 B；这是当前母体的
  观测基线，不是 MilkTea 的容量承诺。

判断：

- Robot1 + Robot2：作为第一阶段目标，通常可行，但必须实测堆和每任务栈高水位。
- Robot3：多实例架构允许，但当前节卡协议未提供，只有保留标识；实施前既要冻结
  协议，也要在 MilkTea 最终任务集合下重算 heap、TCB、TCP PCB、pbuf 和栈余量。
- Robot4 及以上：不能仅按“多加配置”承诺；若资源不够，必须先做容量报告再
  选择减少栈/队列、拆分功能或设计共享非阻塞任务。

## 11. 配置、装配与启动校验

### 11.1 配置归属

```text
ProductConfig
  ├─ enabled Routes
  │    ├─ Transport + fixed serial/TCP parameters
  │    └─ ProtocolId
  └─ enabled DeviceInstances
       ├─ Category + Role + InstanceId
       ├─ RouteId
       └─ DriverId + const DriverConfig
```

产品配置放在产品自己的 `Application/UserAPP/<Product>App/Config` 或已有产品
配置目录中；公共层只定义稳定类型和校验函数，不知道 Coffee2/MilkTea 的订单。

### 11.2 最小校验项

启动时只校验当前需求能证明有价值的项目：

1. Instance 配置、Driver 引用和 Route 引用非空。
2. InstanceId、RouteId、DriverId、ProtocolId 在边界内。
3. Driver 所需 Protocol 与 Route Protocol 一致。
4. disabled Route 不创建 task、queue、Transport context 或 Protocol context。
5. 一个物理 UART 只有一个 Route owner。
6. 一个逻辑 IO 输出只有一个 writer。
7. Robot point table 非空、点数不超过 `ROBOT_TARGET_COUNT`，地址在 3100～
   3139 约束范围内（以正式协议冻结为准）。
8. 私有无寻址协议的 Route 绑定设备数为一。
9. TCP endpoint 的地址、端口和 Instance 唯一。

不做排序、哈希、字符串注册表或复杂重复检测；如果重复的 Robot 点位是产品
有意合并语义，不应被通用校验误判。配置失败要记录 Role/Instance/Route 和
错误类型，并使该 Instance 保持 disabled；不能半初始化后继续运行。

## 12. 命令、结果和日志契约

### 12.1 统一命令

保留现有 `commandId`、`orderEpoch`、`action`、参数、来源和超时字段。新的设备
库只改变“命令如何路由到实例”，不建立第二个 Command 类型。
迁移期可直接沿用 `Coffee2Command_t`；当 Coffee2 和 MilkTea 真正共用同一
契约时，应替换式移动/重命名为公共 `DeviceCommand_t`，而不是让两种命令
长期并存并相互复制。

Workflow/Server 提交：

```text
{ instance/role, target/action, parameters, commandId, orderEpoch, timeout }
```

Route owner 在完成或失败时写入现有 terminal history，并通过现有 EventGroup 发布
终止事件。取消、superseded 和 OTA 等已有语义保持不变。

### 12.2 统一结果

公共结果至少区分：

```text
OK
INVALID_ARG
INVALID_CONFIG
NOT_READY
QUEUE_FULL
TIMEOUT
TRANSPORT_ERROR
PROTOCOL_ERROR
DEVICE_FAULT
CANCELED
SUPERSEDED
NOT_SUPPORTED
```

结果同时保留 protocol/native 诊断值，例如 Modbus exception、HAL 错误或 lwIP
`err_t`；上层只依据稳定结果分类，不解析底层私有错误码。

### 12.3 日志最小字段

复用当前日志 source 和环形日志队列。关键字段为：

```text
role, instance, route, driver, protocol, commandId, target, result, native
```

不要为每个 Profile、设备名称或协议建立运行时字符串对象。连接、发送、接收、
接单、运动、完成、清结果、重连和最终结果应在状态边沿记录；周期轮询只在状态
变化或错误时打印，避免刷屏。

## 13. Coffee2 当前事实与迁移边界

### 13.1 当前已存在的可复用基础

- `Application/Transport` 已有通用 Transport、UART/RS485、TCP 后端。
- `Application/ProtocolStack/ModbusPort` 已有 RTU/TCP Modbus Port 和统一结果。
- `Application/New_Party/nanoMODBUS` 已是底层 Modbus 实现。
- Coffee2 已有 Device command、Route queue、EventGroup、terminal history、
  `commandId/orderEpoch` 和日志闭环。
- Coffee2 已将 Robot TCP、Bus2～Bus5、Workflow、Server 分任务运行。
- Coffee2 当前绑定表包含 Device、Route、Unit、最小间隔和波特率。
- `Application/DeviceLibrary` 已建立公共身份、越疆机器人协议变体/点位解析、
  咖乐美 O/X Modbus 行为和咖博士 F200 固定帧协议。
- Coffee2 Binding 已补 Category、Role、DriverId、ProtocolId；当前咖啡机选择 X
  系列 Modbus Driver，保持已有线路和上位机 ABI。

### 13.2 当前需要承认的限制

- Coffee2 Robot 是全局单例：`g_xCoffee2RobotTcpStatus`、
  `g_xCoffee2RobotData` 和单个 Robot task 不能直接承载 Robot2。
- Coffee2 设备绑定和 RTU 执行仍带产品硬编码，Bus task 内含 ModbusPort。
- Coffee2 的机器人点位解析和三种咖啡机协议已进入公共库；杯、糖浆、盖、制冰、
  称重、电表和 IO 的执行行为仍集中在 `coffee2_rtu_protocol`，本轮只补公共身份，
  不为追求目录完整一次性搬迁。
- Coffee2 当前 RTU 实现会依据绑定选择串口配置；目标架构要求 Route 在启动时
  固定协议和串口参数，迁移时必须先确认硬件分路，不能无依据继续扩大动态切换。
- MilkTea 当前有任务和协议骨架，但不能视为已经完成目标设备库。

### 13.3 替换式迁移，不做叠加式双架构

迁移一个设备时，先把旧路径的行为测试固定下来，再将该设备的执行入口替换为
目标 Route/Driver/Protocol 路径。旧函数不要和新框架同时长期运行，否则会产生
两个 owner、双写 UART 或两个状态来源。

## 14. Coffee2 → 公共层 → MilkTea 实施阶段

### 阶段 0：行为基线

范围：不改业务行为。

验收：记录每个设备的 Route、串口参数、Unit、命令、响应、超时、日志和取消结果；
Robot 记录命令位清零接单、60 s 动作窗口、完成位清除和断线恢复。

### 阶段 1：冻结公共契约

范围：只加入最小公共类型、结果转换和配置校验；不新建 DeviceManager。

验收：Coffee2 构建不改变上位机 ABI；disabled Route 不创建资源；map 显示公共
层净增 RAM ≤1 KiB 的目标可测量。

### 阶段 2：迁移一条成熟 Modbus RTU Route

范围：选择制冰机或称重模块，将原协议调用包在一个确定 Driver 中，复用现有
`ModbusPort` 和 UART owner。

验收：单机读、写、超时、设备掉线和日志与阶段 0 一致；串口无双 owner。

### 阶段 3：迁移 IO

范围：先完成远程 Modbus IO 写后读回，再接入 Local GPIO Provider；不新增复杂
Provider registry。

验收：每一个逻辑输出只有一个 writer；写入、读回、失败和断线都有标准结果。

### 阶段 4：迁移 Robot 单实例和点位表

范围：保持现有 Robot 握手、100 ms 接单轮询、60 s 动作窗口、完成位清除和重连
恢复，只替换硬编码点位来源为 const table。

验收：Coffee2 所有旧动作点地址逐项相等；日志包含 role/target/coil；断线后
同一 commandId/orderEpoch 能继续或按协议判定结果，不重复创建第二套事务。

### 阶段 5：MilkTea Robot1/Robot2

范围：同一 Robot Driver/task 函数，用两个静态 Runtime/Route/queue/endpoint；
正式协议冻结后分别提供点位表。

验收：Robot1/Robot2 可同时连接；一个断线不影响另一个；编译、heap、栈高水位、
TCP 资源和命令完成链有实测记录。

### 阶段 6：MilkTea 私有协议设备

范围：以正式资料冻结的第一种私有 UART 协议建立确定 Port 和 Driver；不创建
ModbusPort。

验收：抓取真实帧验证组帧、分包、校验、ACK、超时和错误映射；同一 UART owner
不混用 Modbus。

### 阶段 7：产品 Workflow 替换

范围：将 MilkTea 业务步骤改为提交 Role/TargetId；设备细节从 Workflow 移出。

验收：Workflow 不出现 UART、寄存器、线圈、私有帧或 Unit ID；订单取消和单机
调试都能沿统一命令结果路径完成。

### 阶段 8：后置配置持久化（按需）

只有现场证明同一固件必须服务多种硬件组合时，才评估 Flash 配置。评估必须额外
给出版本、CRC、回滚、掉电和启动时 RAM 预算；未达到条件时继续使用编译期 const。

│  ├─ Robot/Dobot/             越疆旧版/新版范围和点位解析
│  └─ CoffeeMachine/           O/X Modbus 与 F200 私有 UART

- 不为每个 Robot 建一份源文件；配置、Runtime 数组和 task 参数区分实例。
- 不把产品 Workflow 搬进 `DeviceLibrary`。

## 16. RAM、Flash 与工具链门槛

### 16.1 预算目标

目标不是“所有新增结构为零成本”，而是将 const 关系和运行态严格分开：

| 项目 | 目标/事实 |
| --- | --- |
| Robot 点位映射 | 19 点约 76 B Flash/Robot |
| Robot 点位映射新增 RAM | 0 B |
| 公共层常驻 RAM 净增 | 旧版默认实测 0 B；新版 51 点镜像约增加 16 B CCM |
| 公共层 Flash 净增 | Coffee2 Debug +388 B；Release +660 B（相对本轮前 ELF） |
| Coffee2 应用槽余量 | 迁移后目标保留约 12 KiB，以 map 为准 |
| 新 Robot owner task | 当前栈配置约 4096 B/实例，另含 TCB/queue/TCP 资源 |

### 16.2 必须测量的项目

- GCC 和 Keil 两条工具链的 `.map`：Flash、SRAM、CCM、ZI、只读表大小。
- `xPortGetFreeHeapSize()` 和最小历史余量。
- 每个 owner task 的 `uxTaskGetStackHighWaterMark()`。
- 最差连接、重连、HTTP/Modbus 流量、日志刷屏和多 Robot 并发场景。
- Ethernet/lwIP pbuf、TCP PCB、UART DMA/中转缓冲的可访问内存区域。

公共配置必须放只读 Flash；队列 storage、协议状态、Runtime 和 TCP 上下文使用
有界静态存储。现有 Task 可继续在启动期由 `xTaskCreate` 从固定 32 KiB
FreeRTOS heap 一次性创建栈和 TCB，但禁止运行期反复创建/销毁 owner task。
DMA/以太网缓冲必须位于 DMA 可访问 SRAM，并核对最终 map 地址。

## 17. 后置能力与禁止项

### 后置能力

- Flash 持久化配置。
- 大规模非阻塞多 Robot 共享任务。
- 多级 Provider registry。
- 自动生成设备库代码和协议表。
- 运行时诊断脚本或远程参数编辑。

### 禁止项

- 用 Profile 解决本来只需要点位表的问题。
- 用 Category 推断协议或用 Runtime 参数随意拼接 Protocol。
- 在同一个 UART 上创建 Modbus task 和私有协议 task。
- 让 Workflow 直接调用 ModbusPort、Transport 或 GPIO。
- 把离线设备状态当作另一套结果体系，绕过 commandId/orderEpoch。
- 为“将来可能出现”预留大量最大数组、字符串和动态对象。

## 18. 每次新增架构的强制审查卡

新增任何 Profile、Registry、Manager、Provider、Router、队列、任务或公共结构体
前，必须填写：

| 审查项 | 必须回答的问题 |
| --- | --- |
| 真实问题 | 哪个已复现的需求或日志证明它必要？ |
| 最小替代 | 现有字段、const 表、switch、Route 或事件为什么不能解决？ |
| RAM/Flash | 常驻 RAM、栈、队列、Flash、启动时间增加多少？ |
| 所有权 | 哪个 task/Route 创建、使用、释放或清理它？ |
| 生命周期 | 初始化、失败、重连、取消、复位如何处理？ |
| 失败路径 | 指针、协议、传输、超时、队列满如何返回？ |
| 测试 | 哪个单机测试和仿真变量能证明闭环？ |
| 删除检查 | 删除这一层后，当前已确认需求是否仍能工作？ |

审核顺序固定为：RAM → 逻辑复杂度 → 当前需求完整性 → 扩展性。只有“未来可能
需要”不能作为新增架构的理由。

## 19. 最终守则

```text
先固定行为，再抽公共边界；
先复用 Route/Transport/ModbusPort，再新增 Port；
先用 const 表表达差异，再新增 Driver；
先实例化同一 Driver，再复制代码；
每个物理资源只有一个 owner；
每条命令只有一套 commandId/orderEpoch/terminal history；
每个新抽象都必须经过 RAM、复杂度、需求和删除审查。
```
