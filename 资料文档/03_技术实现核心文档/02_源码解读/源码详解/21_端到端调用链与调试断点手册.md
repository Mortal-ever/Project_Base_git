# 21 端到端调用链与调试断点手册

日期：2026-09-08。以下箭头表示源码责任和调用/数据交接，跨任务的位置特别写出队列；不是同一栈连续执行。函数行号在[符号索引](22_枚举_结构体_函数与源码文件总索引.md)可查。

## 1. 上电到业务初始化

Reset_Handler → SystemInit/C运行库 → main → MX_FREERTOS_Init → xAppTaskManagerCreateTasks → 模块初始化和xTaskCreate → 调度器启动。默认任务完成MX_LWIP_Init后进入产品默认服务；Workflow自己的任务执行prvRunInitialization。

观察manager.xStartResult与ulTaskCreatedMask；再看Workflow初始化标志。任务全部建立而残杯未通过是两种不同结论。推荐断点：CreateTasks、prvRunInitialization失败return、网络ready发布。

## 2. 上位机FC16订单

TCP socket → TransportTcp → ModbusPortServerPoll → nanoMODBUS写回调 → 私有命令数组更新 → prvEvaluateOrder → WorkflowSubmitOrder → 【静态订单队列】 → WorkflowTask → prvRunOrder。

观察ausRegister[0..31]入队快照和s_ucOrderLatched。FC16返回并不能证明prvRunOrder成功。错误可能是地址区间非法、值非法、队列忙、后续物理条件失败。

## 3. 设备命令闭环

prvRunStep建立Command → CommandSubmit/prvSubmit分配ID → Binding选route → 【owner队列】 → RtuBusTask → Started → prvExecute → 公共设备函数 → Completed → 【事件位+终态记录】 → DeviceWaitCommand → Workflow下一步骤。

观察ulCommandId+ulOrderEpoch两端一致；Step只是诊断号。队列失败未发帧，TIMEOUT表示下层等待失败，DONE可能还要继续物理验证。

## 4. Coffee2 F200

Coffee2 step80 MAKE → Bus2私有F200动作/配方映射 → xCoffeeMachineF200Execute → 构原生帧/Exchange → TransportUART → 解析 → CommitF200 → step85 WaitDeviceReportedComplete刷新直到应用完成/失败 → step90机器人取杯。

断点：MapRecipe、Execute、CommitF200、WaitDeviceReportedComplete。若帧有回包但一直等完成，检查映射后的应用状态，别按Modbus功能码解析F200。

## 5. Coffee3 M50

Coffee3 step80 → Bus2映射CoffeeMachineM50Action_e → xCoffeeMachineM50Execute → ModbusPort FC接口 → nanoMODBUS → TransportUART → 公共M50Image → 私有CommitM50。

断点：Bus2 prvExecute咖啡分支、M50Execute、port返回、CommitM50。M50非刷新命令retryLimit被置0，丢响应不应重复制作。设备动作何时代表完成以M50内部实现为准，不沿用F200步骤85。

## 6. 机器人动作和计时

Workflow action → Device route0队列 → RobotTcpTask → 私有Dobot点位表 → ucDobotRobotResolvePoint → ModbusPort TCP线圈命令 → WAIT_ACCEPT → accepted → MOVING → 结果清除 → 终态。

断点：ResolvePoint、DeviceSetRobotPhase、DeviceSetRobotAccepted、DeviceCommandCompleted。日志等待受理时看命令线圈是否被对端消费；运动60秒计时在受理后起算，恢复阶段可能重置起点。此处不能把排队开始到现在的时间当作同一个运动timeout。

## 7. IO刷新到展示页

Workflow prvServiceIoRefresh → 本机IoRefreshLocal；外部REFRESH进Bus5 → Unit1 FC02/Unit2 FC01 → 成功commit输入/输出数组 → Server prvRefreshStatusRegisters → FC03拷贝0x10F0..0x10FF。

观察valid、update tick、数组和寄存器四层。输入低有效转换在本机IO层，外部Modbus数据不按STM32极性再取反。数组MB2YPin对应展示外部DO第1组0x10FA。

## 8. IO调试两个入口

FC06/FC16写0x0208 → 初始化检查和8位mask验证 → ApplyLocalDebugMask → GPIO WritePin逐点 → RefreshLocal。写0x05开启DO1/DO3，关闭其他点。

写0x0209 → 私有IO_WRITE_MASK → owner队列 → 公共IO逐点控制/读回 → 镜像。第一次Modbus应答是受理，不保证外部硬件已完成。失败看设备10、Bus5、unit2的终态。

## 9. 超时传播

Transport错误/接收超时 → nanoMODBUS/ModbusPort result → RtuBus记录device/action/source/step → Device terminal保存原始result → Workflow GetTerminalResult → 业务DEVICE分类。

应同时看原始result、设备名、step和命令键。`WORKFLOW_STEP_START result=1`中的1可能是action REFRESH，而非失败；不要跨事件给所有result一个统一含义。

## 10. OTA

Server升级命令/HTTP接入 → WorkflowAcquireOta准入 → 产品OtaConfig → 公共FlashBegin/Write/Finish → metadata/staging → 复位后的Bootloader。Bootloader不属于本工程Application，不能用应用日志证明它已正确搬运镜像。

断点：AcquireOta返回、FlashBegin、Finish校验失败、metadata提交；不为阅读教材实际执行擦写。

## 11. 崩溃

Fault入口/诊断hook → Common Diagnostics保存上下文 → lAppCrashDiagWrite弱接口的产品强实现 → 产品早期串口输出。普通队列消费或调度器可能不可用，所以从正常LogTask找不到崩溃输出并不奇怪。看堆栈指针、异常PC/LR、fault寄存器和具体工具链入口，详见04。

## 12. Coffee3出餐后还能否接单

线下内容完成先发布production=2 → 最终PUT_OUTPUT → 有杯条件 → 出口5 → 门下降；制作路径末尾机器人HOME。后续ServicePickup保留出口事务；观察杯从有到无且持续30秒→出口0x15→门上升→满足ACK/上限位/无杯后释放。

生产完成与出口释放不同，下一单还要过资源准入：线上储位、线下出口、缺水/恢复锁等。不能因production=2就推出所有下一单都能接收。

## 实际单步方法

选一条链只跟一个commandId，把入队、出队、设备回包、终态、物理条件记录在同一页。对每个断点写下当前任务名称、输入对象、修改字段、下一个函数。跨任务不要用Step Into期待跳过队列进入另一个任务；在消费入口设断点。实机运行受断点影响会触发通信timeout，理解代码时需区分断点人为延迟。
