# 03_L3 公共设备库层源码带读

> 只读 Review 分层文档（2026-09-02）。配套：`00_Coffee2工程架构分析.md`。
> 本层 = `Application/DeviceLibrary`。所有驱动 target-neutral，可由任意 Target 选择。

## 1. 本层职责

- 设备原生请求构造（帧/寄存器/点表）；响应解析；设备寄存器/协议定义。
- 设备上下文与镜像结构；设备级状态；设备级错误返回。
- 公共契约：`Application/DeviceLibrary/Inc/device_library.h` + 各设备目录头文件。

## 2. 本层不负责什么

- 不解释 Coffee2 命令/订单/寄存器语义；不写 Coffee2 状态 image；不绑定物理总线/从站
  地址/波特率/IP（由调用方传入）。
- 不创建任务、队列、同步对象；不做业务编排。
- 不提供“统一转发层”（无 DeviceProtocol）。

## 7. 本层依赖

- `device_library.h`、`modbus_port.h`（除 F200）、`transport.h`（F200 直连）。
- CMake：`device_*` → `product_interfaces` +（`app_modbus_port`/`app_transport`）
  （`Application/CMakeLists.txt:74-127`）。

## 8. 本层调用者

- Coffee2 Bus owner `prvExecute`（`coffee2_rtu_bus.c:387-558`）按设备分派；
  Robot owner（`coffee2_robot_tcp.c`）用 Dobot 公共结构做解析/校验。
- 其他未来 Target 直接复用（协议/Unit ID/总线拓扑由调用方决定）。

## 9. 初始化顺序

无独立初始化：驱动是无状态函数集；仅 `const` 描述符与协议配置，无运行时初始化。

## 10. 关键数据结构

- `DeviceDriverDescriptor_t`：driver/category/protocol 三元组。
- `CoffeeMachineF200Status_t`（`coffee_machine_f200.h:53-61`）。
- `DobotRobotProtocolConfig_t/DobotRobotPoint_t/DobotRobotDriverConfig_t`
  （`dobot_robot_device.h:115-145`）。
- O/X/M50 `Config_t+Image_t`；`CupLidShengShuImage_t`；`SyrupMachineModbusImage_t`
  （15 寄存器）；`IceMachineModbusImage_t`（13 寄存器）；`ScaleBsqDgV2Image_t`
  （0.1 g 归一化）；`PowerMeterDdsu666Image_t`（float 工程值）；
  `IoModuleModbusDigitalImage_t`（48 点）。

## 11. 静态和全局对象

- `const` 全局：各 `g_x*Driver` 描述符；Dobot 3 协议配置 + 3 描述符 + Jaka 占位
  （`dobot_robot_device.c:15-82`）等。
- 无可变全局业务状态；镜像由调用方拥有。

## 12. 任务上下文

驱动在 owner 任务上下文同步调用（RTU/TCP 单 owner），无独立任务。

## 13. 队列和同步对象

无。

## 14. 关键函数带读（逐设备代表）

### xCoffeeMachineF200Execute / xCoffeeMachineF200Exchange

- 文件：`coffee_machine_f200.c:194-249`（Execute）、`:145-192`（Exchange）。
- 层：L3。调用者：`coffee2_rtu_bus.c:427-429`。被调用者：BuildFrame/ParseFrame、
  `xTransportSend`/`xTransportReceiveExact`。
- 输入：`TransportChannel_t*`、动作、drink id、超时、状态出参、取消回调。
- 返回：`CoffeeMachineF200Result_e`。
- 正常路径：MAKE/CLEAN 先 QUERY(0x10)，机头 IDLE(0x02) 才发命令；26 B 帧
  head 0x7E/len 0x1A/checksum/tail 0x7E（`coffee_machine_f200.c:13-27`）。
- 错误：app state 0x04 → REJECTED（`:187-190`）；解析失败 → PROTOCOL；传输超时 →
  TIMEOUT。取消回调当前未接入 F200 执行路径（`:210-211`），见 §23 P3。
- RAM/栈：26 B TX/RX 局部帧。断点：`:165`（发送前）、`:180`（解析后）。
- 问题：F200 为何直连 Transport 而非 ModbusPort？取消回调未接入是否有实际影响？

### xCoffeeMachineOExecute / X / M50

- 文件：`coffee_machine_O.c`（149 行）、`coffee_machine_X.c`（148 行）、
  `coffee_machine_m50.c`（107 行）。
- API：`Config_t* + ModbusPort_t* + UnitId + 动作 + 参数 + 超时 + 镜像 + 取消回调`。
- 行为：动作映射 FC06 寄存器写（make/pause/resume/clean/cancel/reset/power；
  M50 为 make/clean/fault_ack/cancel）；Refresh 用 FC03 读 16/24/16 状态寄存器。
  寄存器地址/取值在 `Config_t`（`coffee_machine_O.h:37-49`、`m50.h:34-42`）。
- 层：L3。Coffee2 当前未选用（绑定表无 O/X/M50）；未来 Target 可选。GCC 链接期
  丢弃、Keil IncludeInBuild=0。
- 问题：O/X/M50 为何可由其他 Target 选择？（无 Coffee2 引用、公共驱动。）

### xCupLidShengShuRefresh / Run

- 文件：`cup_lid_shengshu.c`（95 行）。层：L3。
- 调用者：`coffee2_rtu_bus.c:439-453`（CUP）、`:476-491`（LID）。
- 协议：同一寄存器集合；角色 CUP/LID 与 Unit ID 由调用方给
  （`cup_lid_shengshu.h:7-13`）。Refresh 读任务寄存器 + 10 线圈；Run 写任务后轮询
  `CUP_LID_SHENGSHU_STATUS_*`（working/success/failed）。
- 断点：refresh 返回后、run 轮询点。问题：杯与盖分属两个 Unit，为什么共用同一驱动？

### xSyrupMachine* / xIceMachine* / xScaleBsqDgV2* / xPowerMeterDdsu666Refresh

- 均经 `modbus_port` FC03/FC06/FC04。镜像见 §10。
- 冰机把“设备故障位”与“通讯结果”解耦（`ice_machine_modbus.h:9-11`），
  `ucIceMachineGetFaultMask` 供 owner 把故障当协议层结果返回
  （`coffee2_rtu_bus.c:497-499`）。
- 秤 0.1 g 归一化（`scale_bsq_dg_v2.h:7-9`）；电表 FC04 + IEEE-754 高字在前
  （`power_meter_ddsu666.h:7-10`）。

### xIoModuleModbusReadInputs / ReadOutputs / WriteOutput

- 文件：`io_module_modbus_digital.c`（112 行）。
- 输入 FC02；输出观察 FC01；写 FC05 + 全范围 FC01 回读校验
  （`io_module_modbus_digital.h:7-12`）。
- 调用者：`coffee2_rtu_bus.c:525-554`（Bus5 IO_INPUT/IO_OUTPUT）。
- 问题：写后回读不一致返回 `MODBUS_PORT_RESULT_PROTOCOL`，owner 如何投影到 IO 镜像？

### Dobot 公共数据结构的使用（非 IO 发起方）

- `coffee2_robot_tcp.c` 用 `prvResolveCoffee2Dobot`/`ucDobotRobotResolvePoint` 把
  Coffee2 动作解析成命令/结果线圈对（`coffee2_robot_tcp.c:950-968` 等）。Dobot
  驱动不发起 IO；点表与协议配置是公共 const。
- 问题：为什么 Robot 读写仍发生在 L4 owner 而解析函数在 L3？（命令线圈属设备协议，
  业务选择属 L4。）

## 15. 正常路径

- RTU：owner 从命令队列取 Coffee2Command → 按 `pxBinding` 选驱动函数 → 驱动经
  modbus_port/transport 完成一次或多次事务 → 镜像/状态返回 → owner 提交结果。
- F200：owner → `xCoffeeMachineF200Execute`（Query+Make/…）→ transport UART。
- Robot：owner 直接用 modbus_port 读写线圈；`ucDobotRobotResolvePoint` 负责把动作
  解析成线圈对。

## 16. 错误和超时路径

- 驱动层返回 `MODBUS_PORT_RESULT_*` 或 `CoffeeMachineF200Result_e`；
  冰机把设备故障转 `MODBUS_PORT_RESULT_PROTOCOL`；IO 写回读失败返回
  `MODBUS_PORT_RESULT_PROTOCOL`；owner 统一 `vCoffee2DeviceCommandCompleted`。

## 17. 日志位置

驱动不写日志；设备名/协议事件/失败日志由 owner 以 Coffee2 source 输出
（`coffee2_rtu_bus.c:686-711,748-762`）。

## 18. RAM、Flash、栈和 DMA

- 驱动栈上局部帧/镜像（F200 26 B；IO 48 点 48 B；镜像一般 ≤ 数十 B）。
- 无 DMA 缓冲归本层所有（传输缓冲在 Transport）。
- 若启用 O/X/M50，Flash 占用会增加；当前 Coffee2 不包含。

## 23. 已发现问题

- P3/UNKNOWN（L3）：`xCoffeeMachineF200Execute` 的取消回调参数被置空
  （`coffee_machine_f200.c:210-211`）——F200 事务自身不做协作取消点；
  若 F200 卡在较长查询周期，owner 只能等单次事务超时。当前 Coffee2 的 F200
  动作（MAKE 等）后续由 Workflow 轮询完成状态，取消通过 `COFFEE2_ACTION_CANCEL`
  单独下发，影响有限；如需快速取消需在 Exchange 循环内查回调。本任务是否修改：否。
- P3（一致性）：冰机把故障转 PROTOCOL 后，owner 会将该设备标为通讯结果失败路径
  （`coffee2_rtu_bus.c:497-499`），语义上是“设备故障”而非“链路断”，日志需用
  设备 source 区分（已用 `prvGetDeviceLogSource`）。本任务是否修改：否。
- P2/CONFLICT（构建图）：O/X/M50 在 GCC 被编译但在链接期丢弃、Keil
  IncludeInBuild=0——与 `CHANGES.md`（2026-08-21）表述的“完整排除”不完全一致。
  本任务是否修改：否。

## 24. 必须解释的四点（任务要求）

1. **F200 不是 Modbus，为什么仍属于公共设备库**：公共属性 = 无 target 业务语义、可被
   任意 target 复用（`AGENTS.md:33-34`）；协议类型不决定公共属性。F200 只依赖
   `transport.h` 与自身帧定义，不引用 Coffee2。
2. **O/X/M50 为什么可以由其他 Target 选择**：它们不包含 Coffee2 头文件/绑定/命令，
   寄存器点表用 `Config_t` 描述（`coffee_machine_O.h`），任何 target 传入自己的
   ModbusPort/Unit 即可。
3. **DeviceLibrary 为什么不能引用 Coffee2 状态和命令**：Coffee2 状态 image 与命令在
   `UserAPP/Coffee2App`（L4）；公共驱动一旦 include 它们就无法被其他 target 复用，
   且破坏 L3→L4 禁止依赖方向（`AGENTS.md:45-47`）。
4. **设备原生协议为什么不需要 DeviceProtocol 层**：原生协议已内聚在驱动内
   （帧/点表/解析/校验），L4 直接调用 L3 驱动即可；转发层既不增加复用也不增加状态，
   见主文档 §4。
