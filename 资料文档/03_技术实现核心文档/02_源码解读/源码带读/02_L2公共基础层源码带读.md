# 02_L2 公共基础层源码带读

> 只读 Review 分层文档（2026-09-02）。配套：`00_Coffee2工程架构分析.md`。
> 本层覆盖 `Application/Common`（Log、Diagnostics、LwipAlert、Ota、TcpClientSession）、
> `Application/Transport`、`Application/ProtocolStack/ModbusPort`、
> `Application/New_Party/nanoMODBUS`。本层全部 target-neutral。

## 1. 本层职责

- 异步日志核心（`app_log`）；崩溃诊断核心（`app_crash_diag`）。
- lwIP 资源告警（`app_lwip_alert`）。
- 公共 OTA：Flash 分段写（`app_ota_flash`）+ 原始 lwIP HTTP 上传（`app_ota_http`）。
- TCP 客户端会话状态机（`tcp_client_session`）。
- 字节传输：`transport` / `transport_uart` / `transport_tcp`。
- Modbus 端口适配（`modbus_port` 绑定 nanoMODBUS ↔ Transport）。
- nanoMODBUS 协议栈（vendor v1.23.0 + 5 条本地补丁）。

## 2. 本层不负责什么

- 无产品命令枚举/寄存器/物理总线绑定（Coffee2 私有，L4）。
- 无设备原生协议语义（L3 DeviceLibrary）。
- 无 CubeMX 平台管理（L1）。

## 7. 本层依赖

- 内部：`app_log`→transport；`app_modbus_port`→transport+nanomodbus；
  `tcp_client_session`→transport；`app_ota`→app_log+L1 Flash。
- 向下依赖 L1（HAL/FreeRTOS/lwIP）。CMake 中公共目标均 `PUBLIC product_interfaces`，
  公共目标不反向依赖产品（`Application/CMakeLists.txt:25-148`）。

## 8. 本层调用者

- L4：`coffee2_log.c`（包装 app_log）、`coffee2_crash_log_port.c`（强实现
  `lAppCrashDiagWrite`）、`coffee2_ota.c`（分区绑定 app_ota）、`coffee2_rtu_bus.c`/
  `coffee2_robot_tcp.c`/`coffee2_server.c`（transport+modbus_port）。
- L3：各 Modbus 驱动调 `modbus_port`；F200 直连 transport。
- 未来任意 Target 可独立选择公共目标。

## 9. 初始化顺序（本层视角）

- 由 L4 owner 驱动：`vTransportManagerInit` → `xCoffee2LogInitWithTransport`
  （USART1 通道）→ `xCoffee2RtuBusInitialize`（Bus2-5 静态队列 + 注册 route），
  各 Bus 任务内 `xTransportUartCreate`+Open + `xModbusPortClientInit`；Robot 任务内
  `xTransportTcpCreate`+`xModbusPortClientInit(TCP)`；Server 每槽位 accept 后
  `xTransportTcpSocketAttach`+`xModbusPortServerInit`。
- 崩溃诊断 `vAppCrashDiagInit()` 在 main（L1）；任务登记经 FreeRTOS trace 钩子
  （`FreeRTOSConfig.h:180-197`）。

## 12. 任务上下文

- 本层无自建任务：`vAppLogTask` 由 L4 `vCoffee2LogTask` 常驻调用
  （`coffee2_log.c:174-179`）。崩溃路径运行于关中断的 fault/assert/RTOS 钩子上下文。
- Transport/ModbusPort 只被 owner 任务串行调用（`modbus_port.h:76` 单 owner 警告）。

## 13. 队列和同步对象

- app_log：binary semaphore `s_xLogSignal`（`app_log.c:74-77`），producer give /
  consumer take；ring + 信号量，无队列。
- transport_uart：每通道 `xTxMutex`（写者互斥）+ `xTxDone`（TX 完成信号）+
  `xRxStream`（ISR→任务，256 B StreamBuffer）（`transport_uart.h:44-53`）。
- 业务命令/订单队列在 L4，本层不创建。

## 14. 关键函数带读（核心）

### xAppLogWriteFieldOrder / vAppLogTask

- 文件：`app_log.c`（写 `:245-321`，任务 `:391+`）。所属层：L2。
- 调用者：各产品源（经 Coffee2 适配层）。被调用者：ring 操作、`xTransportSend`。
- 上下文：任务（非 ISR）。阻塞：任务等待信号量；单次发送 100 ms 上限。
- 正常路径：入 ring（满则覆盖最旧并 `ulDroppedCount++`）→give 信号量→Log 任务
  格式化→transport 发送。
- 错误路径：Transport 失败重试 100-1000 ms 退避；ring 仍可用（buffer-only 降级）。
- 断点：ring 写入点与任务发送点。
- 问题：为什么用 overwrite ring 而不是阻塞队列？ISR 能不能调用？（不能，文档明示。）

### 崩溃诊断：弱接口与强实现

- 文件：`app_crash_diag.c`。弱 `lAppCrashDiagWrite` `:53-59`（返回 -1）；
  `vAppCrashDiagFaultEntry` `:287-299`；`vAppCrashDiagRtosEntry` `:303-315`；
  `vAppCrashDiagAssertCEntry` `:319+`；任务登记 `:200+`。
- 汇编入口：`app_crash_fault_gcc.S`（GCC）/ `app_crash_fault_armcc.s`（ARMCC），保存
  R4-R11/MSP/PSP 后进入 C 入口（`app_crash_fault_gcc.S:30-103`）。
- 正常：抓现场→`prvCrashRun` 重复输出（周期 10 s，`app_crash_diag_config.h:22`）。
- 错误路径：弱输出不可用→Coffee2 强实现 `lAppCrashDiagWrite`
  （`coffee2_crash_log_port.c:63-66`）走 USART1 LL 轮询（关 DMA、有界自旋）。
- 断点：`app_crash_fault_gcc.S:50`、`app_crash_diag.c:287`。
- 问题：为什么必须关中断且不使用 RTOS API？（`AGENTS.md:59-60`）

### vAppLwipAlertReportFailure

- 文件：`app_lwip_alert.c:85-128`。调用者：L4 `vCoffee2LogLwipResourceFailure`
  （Server/Robot/OTA 的 lwIP 失败点）。行为：读 `lwip_stats`，错误计数上升才写
  WARNING/ERROR 日志（alloc/capacity 事件表 `:47-74`）。
- `#if LWIP_STATS && MEMP_STATS`，Coffee2 下由 `lwipopts.h:139-185` 打开；
  否则 no-op。问题：为什么事件触发而非周期轮询？（防刷屏。）

### xTransportUartCreate / prvSendRuntime / 接收与 HAL 回调

- 文件：`transport_uart.c`。Create 注册通道并静态创建信号量/StreamBuffer；
  `prvSendRuntime` `:364-439`：半双工方向切换→暂停 RX→发送（DMA chunk 或轮询）
  →恢复 RX；TX 经 DMA 可访问的普通 SRAM 暂存。
- 接收：HAL RX 单字节中断写 `xRxStream`，溢出计数。
- 断点：`transport_uart.c:416`（发送前）、RX 回调。问题：为什么 TX 用 DMA、RX 用
  单字节中断？DMA 缓冲为何不能在 CCM？

### xTransportTcpCreate / Netconn client connect / Socket attach

- 文件：`transport_tcp.c`。Coffee2 用 Netconn 客户端（Robot）与 Socket 后端（Server
  槽位）；客户端 connect 有界非阻塞 + deadline（`transport_tcp.h:35,49-51`；
  2026-08-27 CHANGES）；3000 ms 为 Coffee2 配置（`coffee2_app_config.h:49`）。
- 问题：`ulConnectTimeoutMs=0` 保留旧阻塞语义；connect 失败如何回到应用重试循环？

### modbus_port 事务核心

- `xModbusPortClientInit` `:141-162`；`prvBegin` `:732-753`（RTU 帧间静默 + 事务预算 +
  nmbs 超时/目标地址）；`prvWaitFrameSilence` `:756-786`（3.5 字符时间动态计算）；
  `prvFinish/prvMapError`（归一化 + 故障详情）；`xModbusPortServerPoll` `:193+`。
- 回调超时被裁剪到事务剩余预算（`prvGetEffectiveTimeout` `:847-861`）。
- 断点：`modbus_port.c:742`、`:795`。问题：RTU 静默为何要动态读波特率？TCP 为何免静默？

### nanoMODBUS

- v1.23.0（`UPSTREAM_VERSION.md:1-6`）；本地补丁 5 条（`:8-15`：有界接收/固定缓冲
  MBAP 长度/避免 ARMCC VLA/文件记录溢出与 0 长度拒绝/指针组合校验）。
- 配置 `nanomodbus_config.h`：client+server 均启用；Keil 经
  `coffee2_build_config.h` preinclude 保持布局一致（`uvprojx:341`）。

### CommonTargets 与 legacy

- `CommonTargets.h:22-28` 按 `USE_COFFEE2` include `coffee2_manager.h`；只被
  `freertos.c` include（见 L1/主文档 §3.5）。
- legacy `ProtocolStack/Modbus`：目录存在，未进入当前构建（§5）。

## 15. 正常路径

- 日志：Coffee2 源 → app_log ring → C2Log 任务 → transport UART1。
- Modbus 下行：owner → `modbus_port`（begin/send/wait/finish）→ transport → HAL/lwIP。
- Modbus 上行：transport 收流 → nanoMODBUS 解析 → 回调/结果 → owner。
- 崩溃：fault/assert → 汇编入口 → `vAppCrashDiag*` → 文本 → `lAppCrashDiagWrite`
  （Coffee2 强实现，USART1）。

## 16. 错误和超时路径

- 字节/总超时分层：Transport 有单次 IO 超时；`modbus_port` 用总事务预算裁剪回调超时；
  owner 再按设备命令超时封装。
- 错误归一化链：`nmbs_error → ModbusPortResult_e → 设备层结果 → Coffee2 结果/日志`。
- 日志降级：Transport 失败不丢 ring（buffer-only），输出计数累计并可 Watch 读取。
- lwIP 资源耗尽：不改变调用方结果，仅告警（`app_lwip_alert.h:27-30`）。

## 17. 日志位置

公共模块只认 `AppLogSourceId_t` 与 `APP_LOG_LEVEL_*`；Coffee2 的 source 表与 UART1
适配在 L4（`coffee2_log.c:25-45`），崩溃输出介质在 L4（`coffee2_crash_log_port.c`）。
`vCoffee2LogLwipResourceFailure`（`coffee2_log.c:194-198`）转调 `vAppLwipAlertReportFailure`。

## 18. RAM、Flash、栈和 DMA 注意事项

- 环/信号量/StreamBuffer 均静态；崩溃文本 4K、任务登记 16 条。
- UART TX DMA 暂存 256 B 与 RX StreamBuffer 256 B 必须在普通 SRAM（非 CCM）。
- Transport TCP 使用 lwIP Netconn/Socket（MEMP_NETCONN=12 等来自
  `lwipopts.h:64-75`）。
- `MODBUS_PORT_TRACE_LENGTH=260`（`modbus_port_config.h:14`）位于 ModbusPort_t 实例。
