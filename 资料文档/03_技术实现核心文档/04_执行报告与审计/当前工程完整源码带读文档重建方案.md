## 2. 审查结论

原有五份源码带读文档可保留为历史架构审查材料，但不能继续承担“让未读过源码的人学会
当前程序”的主要任务。现有内容缺少：

- 枚举逐值的产生者、处理分支、设备动作和终态；
- 结构体逐字段的初始化、写者、读者、任务上下文和生命周期；
- 函数体从入口校验到状态提交、错误返回的实际执行过程；
- Server、Workflow、Device、Bus、DeviceLibrary、协议栈和 Transport 的完整调用链；
- Coffee2Open 与 Coffee3Close 相似目录中的真实业务差异；
- “源码存在”“进入 Target 构建”“运行时被调用”三种状态的区分。

新源码带读应改成源码教材，由阅读入口、公共层教材、每个 Target 的私有教材、端到端联动
手册和符号索引组成。编号 00 至 22 共 23 份主文档，另附源码覆盖矩阵。正式编写正文前先建立源码覆盖矩阵。

## 5. 每篇文档的固定讲解模板

每篇必须按以下顺序编写，不得只罗列 API：

1. 模块解决的现实问题及所在调用层。
2. 覆盖的 `.c/.h` 和 Coffee2/Coffee3 的 Keil/GCC 纳入状态。
3. 头文件阅读顺序：宏、枚举、结构体、公开 API。
4. 枚举逐值说明：数值、产生者、处理者、设备/协议动作、终态。
5. 结构体逐字段说明：初始化、写者、读者、任务上下文和生命周期。
6. 静态/全局对象：所有权、并发访问、RAM 和 DMA 约束。
7. 初始化和依赖注入路径。
8. 关键函数体按实际顺序分段：校验、准备、下行调用、解析、状态提交、返回。
9. 调用者和被调用者，至少向上、向下各追一层。
10. 正常状态、完成条件、错误出口和恢复路径。
11. RTOS 任务、队列、锁、通知、阻塞时间和超时。
12. 协议地址、功能码、字节序和返回码映射。
13. 正常与异常日志如何对应代码现场。
14. 建议断点、观察变量和“下一步读什么”。

## 6. 类型和函数体的讲解深度

### 6.1 结构体

每个重要结构体建立字段表：

| 字段 | 语义 | 初始化 | 写入者 | 读取者 | 并发/生命周期 |
| --- | --- | --- | --- | --- | --- |

还要明确它属于公共设备上下文、协议对象、私有业务状态还是临时帧缓冲；内部指针由谁保证
有效；能否跨任务保存；是否可能交给 DMA。

### 6.2 枚举

每个重要枚举建立流转表：

| 枚举值 | 数值 | 谁产生 | 谁处理 | 对应动作 | 完成/失败 |
| --- | --- | --- | --- | --- | --- |

Coffee2/Coffee3 的业务动作枚举不得描述成公共设备库能力。

### 6.3 函数体

不能用“发送命令并解析响应”一句带过。设备执行函数至少说明：

- context 从哪个 Target 静态绑定传入；
- 产品动作在哪个私有函数映射为设备动作；
- 参数和状态如何校验；
- 请求 PDU 或原生帧怎样生成；
- 调用哪个 ModbusPort 或 Transport API；
- 超时和取消如何检查；
- 协议结果如何映射为设备结果；
- 成功时提交哪个镜像，失败时是否保留旧值；
- 哪个任务等待并消费最终结果。

复杂函数只摘录理解所需的短代码片段，并结合当前行号逐段解释，不复制整段源码。

## 7. 必须讲通的端到端调用链

1. MCU 复位到 `xAppTaskManagerCreateTasks()`，再到全部产品任务启动。
2. 上位机订单寄存器到 Server 判定、Workflow 接单和状态发布。
3. Workflow 设备步骤到 Device、RTU Bus、DeviceLibrary、ModbusPort、Transport。
4. Coffee2 F200 的动作映射、自有帧、Transport 和设备镜像提交。
5. Coffee3 M50 的动作映射、Modbus 寄存器访问和镜像提交。
6. Robot 动作到私有点位表、公共 Dobot 解析、TCP Modbus 和完成线圈。
7. 周期 IO 刷新到板载 GPIO/Modbus IO、私有镜像和 Server 寄存器。
8. IO 调试到准入、组合位图、写入和读回验证。
9. 设备超时到公共返回码、私有命令终态、Workflow 和日志。
10. OTA 到业务停机、安全输出检查和 Bootloader 联动边界。
11. HardFault 捕获到 Target 私有输出端口。
12. Coffee3 残杯、双储位、出餐门和取餐闭环。

每条链固定写为：

```text
外部事件/任务入口
  -> 文件:函数（输入）
  -> 文件:函数（队列/状态变化）
  -> 文件:函数（协议/设备动作）
  -> 完成条件
  -> 错误出口
  -> 日志、断点和观察变量
```

## 10. 已确认的代表调用链

### 10.1 Target 启动

`freertos.c` -> `CommonTargets.h` -> Coffee2/Coffee3 manager -> Device、RTU、Robot、Workflow、
Server 初始化 -> 产品任务创建。

### 10.2 Coffee3 M50

Workflow -> Device -> `coffee3_rtu_bus.c::prvExecute()` -> `xCoffeeMachineM50Execute()` ->
ModbusPort -> nanoMODBUS -> Transport UART -> `vCoffee3DeviceImageCommitM50()`。

### 10.3 Coffee2 F200

Workflow -> Device -> `coffee2_rtu_bus.c::prvExecute()` -> F200 配方/动作映射 ->
`xCoffeeMachineF200Execute()` -> F200 自行构帧 -> Transport -> 解析 ->
`vCoffee2DeviceImageCommitF200()`。

### 10.4 Server

Target Server callbacks -> `xModbusPortServerInit()` -> `xModbusPortServerPoll()` ->
nanoMODBUS callback -> Target 私有寄存器语义 -> Workflow/IO/调试入口。

### 10.5 Robot

Target 私有点位表 -> `ucDobotRobotResolvePoint()` -> 命令/结果线圈 -> Robot TCP 使用
ModbusPort -> Device phase/ready -> Workflow 等待完成。

### 10.6 IO

Workflow/Server -> Device -> RTU Bus -> 公共 IO DeviceLibrary -> 私有 IO 镜像 -> Server 寄存器。

## 12. 风险和待核项

1. `ProtocolStack/Modbus/modbus_rtu_master.*` 与 `modbus_tcp_client.*` 当前未找到主路径初始化
   调用，应标为 `LEGACY_CANDIDATE`；确认引用和构建状态前不能删除，也不能写成现役主栈。
2. `CommonTargets.h` 的物理目录与语义边界不同，必须明确为启动组合适配器。
3. Coffee2/Coffee3 私有实现虽同构，仍是两个独立产品，不能抽成虚构的公共业务层。
4. 公共设备请求成功不一定表示机械动作完成，完成条件需回到私有 Workflow 分析。
5. Coffee3 已进入双工具链，不能继续描述成未来规划。

## 13. 验收标准

完成后，未读过本工程源码的开发者应能：

1. 从启动入口找到全部产品任务和创建参数；
2. 解释一个业务枚举如何转换为设备动作和协议帧；
3. 指出关键结构体每个字段的写入者、读取者和生命周期；
4. 判断超时发生在 Transport、ProtocolStack、DeviceLibrary 还是 Workflow；
5. 区分 Coffee2Open 与 Coffee3Close 的共同模式和业务差异；
6. 根据 Keil/CMake 判断修改公共文件会影响哪些 Target；
7. 从任一活动源码文件找到主讲章节；
8. 从任一重要公开符号找到定义、调用点和端到端链；
9. 不把 DeviceProtocol、MilkTea、历史日志或未来方案冒充当前实现。
