# 源码注释与学习可读性规范

## 1. 目的

当前源码带读的目标是让读者理解真实代码，而不是让每一行代码都配一句解释。注释应当
回答“这一段代码在流程中负责什么、输入从哪里来、输出交给谁、失败如何处理”，让读者
可以顺着函数体阅读，而不被重复说明淹没。

本规范适用于 `Application/Common`、`Transport`、`ProtocolStack`、`DeviceLibrary` 和各
`Application/UserAPP/<Target>App`。公共层注释不得写入 Coffee2Open 或 Coffee3Close 的业务
语义；Target 私有层可以说明订单、设备绑定、寄存器和业务状态。

## 2. 总体原则

### 2.1 注释解释意图、边界和联动

代码已经表达“怎么做”，注释重点表达：

- 为什么在这里做；
- 这一段处理的是哪个业务或协议阶段；
- 哪个对象拥有数据，谁会继续使用；
- 返回值如何影响上层；
- 哪些条件不能省略。

不要把 `i++` 注释成“索引加一”，也不要把每个 API 名字翻译成中文。

### 2.2 函数内按模块分段

一个函数按执行阶段分成少量逻辑块，每块前写一条段首注释。推荐顺序：

```c
/* Validate the command identity and resolve the device route. */
/* Allocate the command id while keeping the sequence non-zero. */
/* Apply ownership and priority rules before queue submission. */
/* Copy the command into the owner queue and release a failed reservation. */
```

实际项目源码已有中文注释时，可以使用中文说明；新增 C/H/ASM 注释按 Keil V5 规范使用英文、
`/* */`，业务文档另行提供中文解释。一个逻辑块通常 5 至 25 行，函数超过约 50 行时优先在
文档中拆解，只有真实重复或复杂度问题才考虑拆函数。

### 2.3 注释必须紧邻事实

定义处说明类型和字段；函数声明处说明契约；函数体段首说明阶段；调用点只补充该调用在
当前流程中的特殊前提。不要在文件末尾写一大段无法对应具体代码的说明。

## 3. 变量、宏、枚举、结构体和指针的注释要求

### 3.1 变量

变量注释说明语义、单位、有效范围或所有权。只有名称已经足够清楚的局部变量不需要注释。

```c
TickType_t xStartTick; /* Workflow timeout origin, in RTOS ticks. */
uint8_t ucResultValid; /* 1 only when terminal result matches id and epoch. */
```

不要写“定义一个变量”。对于 `old/new`、`index`、`mask`、`timeout` 这类容易误用的变量，
必须写清比较对象、位图方向、单位和是否包含协议等待时间。

### 3.2 宏

宏注释说明地址空间、单位、位意义、适用 Target 或安全限制；不要只重复宏名。

```c
/* Host readable 32-channel IO page; unused channels remain zero. */
#define COFFEE3_REG_LOCAL_INPUT_LOW 0x10F0U
/* Motion budget for the outlet door, excluding unrelated workflow waits. */
#define COFFEE3_DOOR_MOTION_TIMEOUT_MS 5000U
```

涉及寄存器的宏必须同时说明十六进制地址和协议用途。涉及时间的宏必须写单位；涉及位图的
宏必须写 bit0 对应哪一点。Target 私有宏不应放入公共头文件。

### 3.3 枚举

枚举顶部说明“这个枚举描述哪个状态空间”，每个值在值域发生歧义时补充数值和终态含义。
动作枚举要区分产品动作、公共设备动作和协议功能码。

```c
/* Terminal events belong to one device command, not to the whole workflow. */
#define COFFEE3_DEVICE_EVENT_TERMINAL (...)
```

对 `Coffee3Action_e` 等大型枚举，不在每个值后重复句式；使用分组注释说明 1..3、100..126、
200..203 等编号段，并在源码详解索引中列出每个值的产生者、处理者和对应设备。

### 3.4 结构体

结构体顶部说明对象用途、所有者、复制方式和生命周期。字段注释只写会影响理解的语义：
单位、写入者、读取者、并发保护、是否允许 NULL、是否为快照。

```c
/* Value-copied command; owner queue receives the complete 32-byte object. */
typedef struct {
    uint32_t ulCommandId;     /* Exact terminal-result matching key. */
    uint32_t ulOrderEpoch;    /* Cancellation generation; zero for non-order work. */
    uint16_t ausParameter[4]; /* Action-specific values; never a pointer. */
    uint8_t ucDeviceId;       /* Logical device id, later resolved to route/unit. */
} Coffee3Command_t;
```

对于 `Coffee3DeviceStatus_t`，必须说明 `ulLastCommandId + ulLastOrderEpoch` 才能识别一条
终态；对于 `Coffee3IoState_t`，必须说明 `aucModbusValid[]` 区分“有效读取到零”和“尚无样本”。

### 3.5 指针

指针注释必须说明指向对象的所有权、有效期、是否可为 NULL、是否跨任务保存以及是否交给 DMA。

```c
/* Static bus configuration; task stores this pointer for its whole lifetime. */
const Coffee3RtuBusConfig_t *pxConfig;
```

不要仅写“配置指针”。如果函数只借用指针，写 `borrowed`；如果函数复制内容，写 `copied`；
如果调用者必须保持对象有效，写 `caller-owned lifetime`。DMA 缓冲还要注明 SRAM 可达性。

## 4. 函数注释模板

### 4.1 头文件声明

公共或跨文件函数的 Doxygen 注释必须说明：目的、输入、输出、返回值、调用上下文、阻塞/超时、
所有权变化和重要前提。示例：

```c
/**
 * @brief Wait for the terminal result of one exact device command.
 * @param[in] xDeviceId Logical device id, not the Modbus unit id.
 * @param[in] ulOrderEpoch Cancellation generation used for identity matching.
 * @param[in] ulCommandId Non-zero command sequence returned by submit.
 * @param[in] xWaitTicks Maximum wait for this call.
 * @return Terminal event bits; zero means timeout or stale completion.
 * @note Must be called from task context; does not imply physical completion.
 */
```

### 4.2 函数体段落

函数体至少按以下阶段组织注释：

1. 输入和状态校验；
2. 读取/解析配置或查找对象；
3. 准备请求、快照或局部状态；
4. 调用下层接口并说明阻塞/重试；
5. 解析结果和更新拥有者状态；
6. 返回成功、超时、取消或设备错误。

不是每个函数都需要六段；没有实际逻辑的阶段不要硬加空注释。循环内部只有在循环不变量、
退出条件或安全动作容易误读时添加注释。

## 5. 当前代码的推荐注释落点

### 5.1 `coffee3_device.c`

在 `prvSubmit` 前说明“命令按值复制到 route owner 队列”；在设备 ID 查绑定后说明逻辑 ID、
route 和 unit 的区别；在 command ID 临界区说明不能产生零；在 Server 手动分支说明 DEBUG
标志绕过预留、REFRESH 保持普通优先级；在入队失败分支说明释放 reservation。

在 `vCoffee3DeviceCommandStarted` 前说明清理上一终态是为了避免旧事件污染新等待；在
`vCoffee3DeviceCommandCompleted` 前说明它同时更新事件组、最新终态、历史终态和手动预留。
不要只在每个 `xEventGroupSetBits` 后逐行解释。

### 5.2 `coffee3_device.h`

重点注释 `Coffee3Command_t`、`Coffee3DeviceBinding_t`、`Coffee3DeviceStatus_t` 的字段；说明
32 字节编译期断言；标注 `COFFEE3_DEVICE_EVENT_TERMINAL` 仅表示命令终态，不表示机械动作物理
完成；标注 `Coffee3DeviceId_e` 是逻辑设备空间。

### 5.3 `coffee3_io.c/.h`

在 `vCoffee3IoRefreshLocal` 的采样、临界区提交、baseline 和变化日志四个块前分别注释。
明确本机 DI 低电平有效：HAL 读到 RESET 转换为逻辑 1；输出从 ODR 读取，是软件输出状态，
不能当作继电器触点反馈。`ucCoffee3IoApplyLocalDebugMask` 要说明它按 mask 全量写 8 点，
未置位点也会被清零。

在 Modbus image commit 函数前说明输入模块/输出模块分别对应哪一个外部组、何时更新 valid/tick、
NULL 时不提交。`vCoffee3IoGetSnapshot` 注释必须提醒调用者得到的是复制快照，不是内部指针。

### 5.4 `CommonTargets.h`

文件头说明它是启动组合适配器。条件包含 `coffee2_manager.h` 或 `coffee3_manager.h` 的注释
要写清“只允许平台组合根包含”，公共设备库不得通过它获得 Target 业务接口。

## 6. 注释密度控制

推荐密度：

- 文件头：1段，说明职责和边界；
- 公共类型/宏：定义处注释；
- 公开函数：完整契约；
- 复杂函数：每个主要阶段 1条段首注释；
- 简单赋值、递增、显而易见的 API 调用：不注释；
- 关键错误、超时、取消、安全停机：必须注释原因和恢复影响。

判定标准是“删掉注释后，读者是否会误解所有权、单位、状态、优先级或失败出口”。如果不会，
就不需要注释。

## 7. 禁止事项

- 不逐行翻译代码；
- 不在同一函数重复解释同一个变量；
- 不写与源码行为相反的愿望式注释，例如把命令应答写成机械动作完成；
- 不把公共设备库注释成 Coffee2 专用；
- 不把 `DeviceProtocol` 重新描述为当前架构层；
- 不用注释掩盖未确认事实，必须标 `UNKNOWN` 或 `NEEDS_ROOT`；
- 不在 C 源码加入大段中文协议文档，协议完整表格放 Markdown；
- 不使用“后续会”“应该会”等没有源码证据的承诺。

## 8. 落地顺序

1. 先注释公共头文件的核心宏、枚举、结构体和公开 API。
2. 再注释公共实现中的事务、状态提交、错误映射和 DMA/RTOS 边界。
3. 按 Coffee2Open、Coffee3Close 分别注释 manager、Device、RTU、Robot、Workflow、Server、IO 和 OTA。
4. 每修改一个模块，立即更新对应源码详解章节的调用链和字段表。
5. Keil 与 GCC 都检查预处理后符号是否一致；注释不应改变编译结果。
6. 通过代码审查后再统一做拼写、格式和行宽整理。

## 9. 验收标准

- 读者能从函数段首注释判断当前阶段、输入、输出和失败出口；
- 每个重要结构体字段都能找到所有者、单位和生命周期说明；
- 每个枚举分组都能追到实际 `switch` 或比较分支；
- 每个指针都能判断 borrowed、copied、caller-owned 或 DMA buffer；
- 注释没有虚构源码不存在的动作、协议或安全保护；
- Coffee2Open、Coffee3Close 和公共层的注释边界与构建选择一致；
- 注释增加后 Keil/GCC 的行为和产物不应发生改变。

本报告只规定注释方法。本轮不直接批量修改源码，下一步应按上述顺序对源码详解目录中的文件
逐模块实施，并在每个模块完成后做一次代码与文档交叉核对。
