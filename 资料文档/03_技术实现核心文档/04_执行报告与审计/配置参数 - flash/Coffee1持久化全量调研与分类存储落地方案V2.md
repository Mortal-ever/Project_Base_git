# Coffee1 持久化全量调研与分类存储落地方案 V2

日期：2026-09-11。状态：待审批，替代《Coffee3存储位调试拒绝与非OTA持久化规划.md》的方案部分。

本轮只有调研与文档，没有修改固件、擦除 Flash、下载或测试实机。

## 1. 先明确要保证什么

你的“结构体统一管理 → 上电加载到 RAM → 修改后按地址保存”是正确的应用接口。本方案保留这个使用方式，增加其下方的可靠存储和升级恢复机制，不要求业务到处操作 Flash 地址。

但需要区分三件事：

| 情况 | 单结构体、擦原扇区再写 | 本方案 |
| --- | --- | --- |
| 正常更新且供电完整 | 可以保留整个结构中的其他字段，前提是 RAM 快照完整且没有并发覆盖 | 同样支持 |
| 擦除原副本后、写回完成前掉电 | RAM 也消失，唯一有效 Flash 副本已被擦除 | 先保留旧提交记录，在另一个可写位置提交新记录；跨独立扇区轮转 |
| 调试器真正整片擦除主 Flash | 同片参数和同片 A/B 都可能被擦掉 | 正常下载禁止整片擦除；必须整片擦除时先外部备份、验证，再恢复 |

因此，**结构体解决数据组织，不自动解决擦写原子性；片内 A/B 解决更新中断，不解决主 Flash 全片擦除。** 扇区擦除和 Mass erase 是不同操作，硬件依据为 [ST RM0090](https://www.st.com/resource/en/reference_manual/rm0090-stm32f4xx-reference-manual-stmicroelectronics.pdf) 的 Flash 接口定义。本文所称“整片”指用户主 Flash，不将 OTP、系统 ROM、选项字节等混为普通参数区。

### 3.2 OTA类（必须独立列出）

| 数据 | Coffee1位置/字段 | 当前工程 |
| --- | --- | --- |
| OTA元数据 | 0x08004000，ota_config_t：magic、update_flag、firmware_size、crc32；16字节 | 地址保持，遵守现有Bootloader契约，不随程序参数结构扩展 |
| OTA暂存镜像 | 主参考应用flash_if.h声明0x08040000～0x0807FFFF | 当前1MB布局使用0x08060000～0x080BFFFF，不能复制旧地址 |
| 应用固件 | 应用基址0x0800C000 | 当前结束边界0x08060000 |

OTA元数据不是可自由扩展的运行配置结构，Bootloader也会读取。若改它的格式，必须联合升级和兼容判断；本次保持不动。

### 3.3 容易误认为已保存、实际未查到保存链的数据

| 数据 | 事实/边界 |
| --- | --- |
| 订单输入、订单执行状态、完成/取餐握手 | order.c中的静态寄存器/线圈结构，未查到其整体写Flash；静态变量不是掉电保持 |
| IO输入输出状态、传感器占用 | 实时设备状态，不等同于store_cup_valid开放配置 |
| 机器人ready、动作线圈、ACK | 运行状态，不能从旧Flash直接恢复为可信事实 |
| 报警输出、运行日志 | 有打印不等于有Flash日志；本次未发现应用日志持久写入链 |
| IP/MAC等网络参数 | 未查到其通过machine_type或另一NVM写入链保存，不能作为Coffee1已落盘参数列出 |
| 设备内部配方、校准或计数 | 经协议配置设备不等于写MCU Flash；设备自身是否掉电保存需对应协议/设备确认 |

## 4. 你的方式与推荐方式对比

| 项目 | RAM结构体→擦原扇区→整结构写回 | 推荐：RAM结构体→追加提交→双扇区轮转 |
| --- | --- | --- |
| 业务使用 | 简单 | 相同，业务仍只改结构/调用保存 |
| 未修改字段 | 完整RAM快照可以保留 | 同样保留；存储模块保证串行读改写 |
| 写中断电 | 可能全部丢失 | 选择旧的或新的完整提交记录，不能混合半条记录 |
| 擦写次数 | 每次保存都擦扇区 | 用完扇区才擦另一个扇区 |
| 扩展结构 | 直接sizeof容易破坏旧记录解释 | 新增版本，迁移已知旧字段，新增字段加载默认 |
| 真正整片擦除 | 丢失 | 片内也丢失，必须外部备份/恢复 |

不推荐只把当前RAM结构缓存下来就认为安全：掉电后RAM不在；两个任务同时从旧结构改不同字段，也可能最后写入者覆盖前者。因此整个“读取当前快照→修改→验证→提交”必须串行，而不只是给HAL写函数加锁。

## 5. 分类管理：逻辑类别与物理分区分开

### 5.1 分类定稿建议

| 类别 | 内容 | 所有者 | 保存策略 |
| --- | --- | --- | --- |
| OTA | 镜像和启动更新元数据 | 现有公共OTA+Bootloader | 保持原分区与协议 |
| PROGRAM.CONFIG | 开放存储位、未来校准参数等现场配置 | Target私有配置模块 | 同值不写；参数更新成功后保存 |
| PROGRAM.RUNTIME | 机器人下一连接端口预留序号等必须跨重启的少量变量 | Target运行owner，经统一存储 | 在使用前提交；不随恢复业务默认值清零 |
| VOLATILE | IO、动作、ACK、工作流临时变量 | 原任务/设备模块 | RAM，不持久化 |
| DIAGNOSTIC（预留逻辑类别） | 将来若有明确需求的故障快照 | 后续专门设计 | 目前不分配Flash日志环，不在HardFault里直接擦写 |

不需要“每个类别一个物理扇区”，也不需要把OTA塞进巨大AppConfig结构。PROGRAM内部按结构体分类，物理层保存整个小快照，避免本轮引入通用数据库或TLV框架。

### 5.2 本轮可实施的私有结构

```c
typedef struct {
    uint32_t storage_enabled_mask; /* default 0x00000003 */
} Coffee3ProgramConfigV1;

typedef struct {
    uint32_t robot_port_reservation_sequence;
} Coffee3ProgramRuntimeV1;

typedef struct {
    Coffee3ProgramConfigV1 config;
    Coffee3ProgramRuntimeV1 runtime;
} Coffee3ProgramPersistentV1;
```

未来可以扩展成员，如config增加已批准的两路果乳系数，但必须同时补默认值、范围检查、版本迁移和实际算法消费。不能保证“只加一个C成员，旧Flash就自动懂其含义”。建议用显式V1/V2磁盘结构，不直接改变已发布版本布局；旧结构保留用于迁移。

record_generation与端口预留序号分开：保存配置不能意外推进/回退端口。公共层不认识这些成员，Target提供默认值、编码和版本迁移。

### 5.3 文件职责及接口

- `Application/Common/PersistentStore/`：载入最新有效记录、提交快照、校验、两扇区轮转；不依赖Coffee2/3的头文件。
- `Coffee3CloseApp/Config/coffee3_persistent_config.c/.h`：私有结构、默认/校验/迁移、`GetSnapshot`、`SetStorageMask`、`ReserveRobotPort`。
- 公共Flash访问协调与现有OTA协调，只允许一个写入owner；具体分区由固定布局提供，不开放任意地址写接口给业务。
- Coffee2需要接入时提供自己的target_id/schema及私有结构。不同Target不默认互认数据，切换Target前先备份对应配置；本轮不承诺同片无限保存所有Target历史。
- 不新增RTOS任务/动态分配，复用现有任务调用上下文和静态快照；记录未知版本、无有效数据、忙、写失败等明确返回值。

## 6. 物理布局及记录格式

以下为当前1MB布局；启动必须验证Flash容量，不用于512KB器件。

| 物理范围（含末地址） | sector | 用途 |
| --- | --- | --- |
| 0x08000000～0x08003FFF | 0 | Bootloader，保持 |
| 0x08004000～0x08007FFF | 1 | OTA元数据，保持 |
| 0x08008000～0x0800BFFF | 2 | 保留/历史Coffee1配置，不作为新方案唯一副本 |
| 0x0800C000～0x0805FFFF | 3～6 | 当前应用336KB，保持 |
| 0x08060000～0x080BFFFF | 7～9 | 当前OTA暂存384KB，保持 |
| 0x080C0000～0x080DFFFF | 10 | PROGRAM快照日志A，替换当前端口日志A |
| 0x080E0000～0x080FFFFF | 11 | PROGRAM快照日志B，替换当前端口日志B |

不能一边保留旧端口函数的整扇区擦除，一边把新参数放同扇区其他偏移。必须统一所有权。A/B为两个软件副本区，不表示MCU支持Flash硬件双Bank并行运行。

建议首版固定128字节记录（相较上版64字节增加格式扩展余量），精确布局：

| 偏移 | 4字节字段 |
| --- | --- |
| 0x00 | magic |
| 0x04 | record_format_version |
| 0x08 | target_id |
| 0x0C | payload_schema_version |
| 0x10 | payload_length，最大96 |
| 0x14 | record_generation |
| 0x18～0x77 | payload及固定填充，96字节 |
| 0x78 | CRC32，覆盖0x00～0x77 |
| 0x7C | commit，最后单独写入 |

128KB扇区可放1024条记录（不另设扇区头）。明确小端编码、长度、CRC算法参数及字对齐；CRC校验参数需在实施时定稿并用PC/Keil/GCC固定向量共同验证。默认填充固定，禁止未初始化padding参与CRC。C90兼容的编译期尺寸检查+跨工具链序列化测试必须有。

不能仅凭magic选择记录。必须验证版本、target、长度、CRC、commit和字段范围；序号比较处理回绕。未知更新版本只读报错，不擅自写默认值销毁可能可恢复的配置。

## 7. 完整读写与掉电恢复流程

### 7.1 上电

安全输出默认态 → 扫描A/B → 验证记录 → 已知版本迁移 → 建立RAM快照 → 业务初始化 → 开始接收配置和端口请求。所有初始值必须明确赋值。

无有效记录时区分空白Flash与损坏记录。首次出厂可按出厂流程写默认值；存量机器损坏/整片擦除后不能只打印“加载成功”，应记录来源DEFAULT/RESTORED并提示待恢复。若无法区分首次出厂与被全擦，应由上位机/工装显式确认后允许正常营业。

### 7.2 普通提交

1. 取得统一写权限，OTA活跃则返回忙。
2. 从当前已提交快照修改指定字段，整体检查，相同值直接成功。
3. 在全为擦除态的新槽写头和正文，再写CRC，最后写commit。
4. 全记录读回验证成功，才发布新RAM快照并响应“持久化成功”。失败仍保留原快照，失败槽不重复覆盖。
5. 端口预留只有步骤4成功后才能connect；掉电允许跳过一个端口，不允许已使用端口无记录。

### 7.3 扇区轮转

保留含最新有效记录的A → 擦B → 写完整快照到B → commit并校验 → B成为最新。以后需要回收A时才擦A。任意一步复位，扫描必须能找到旧或新的完整快照，不能出现无副本窗口。

有界等待不只看HAL超时：内部Flash操作对取指、实时响应和看门狗的影响需要实测。禁止为了写参数长时间无条件关中断/挂调度器；如果运行期无法承受擦除，应准备空槽并在维护空闲窗口轮转，空间不足明确返回忙，不偷偷中断订单。

磨损用现场保存频度估算：约每1024次快照提交发生一次扇区轮转；两扇区交替。重连频度决定主要写入量，不能宣称无限寿命。若高频到无法满足寿命或延迟，才评估外部EEPROM/FRAM，不为未来假设先引入硬件。

### 7.4 并发和接口响应

PROGRAM保存、端口预留和OTA写入共享Flash控制器，必须统一串行。FC06/FC16参数写入先验证整笔配置，再一次提交，成功响应表示保存成功；若采用异步持久化则必须增加明确完成状态，不能混淆受理与成功。上位机配置失败不得留下已改变的RAM寄存器假象。

## 8. 防整片擦除：必须包含工具链及外部恢复

### 8.1 正常下载：保留而非恢复

- 应用HEX/ELF只含应用地址范围；链接区边界是基础，但链接脚本本身不能约束操作员整片擦除。
- 下载入口预检所有装载段，拒绝覆盖参数/OTA元数据/Bootloader的普通应用镜像。
- 只擦需要写入的应用扇区；禁止常规下载脚本使用mass erase。
- 检查现有 `GCC-ARM/scripts/flash.ps1`：OpenOCD调用`program ... verify reset exit`，STLink调用`-P ... -V -Run`，没有显式整片擦除命令，也没有参数备份/恢复闭环。不能仅据无mass字样就保证所有工具设置下保留参数，需实机前后读回验证。
- Keil的工程Flash设备配置不能代替实际Download擦除策略确认；应记录使用的擦除选项，验证下载前后参数区校验值不变。本次未操作Keil界面，未宣称其当前设置已安全。

### 8.2 确实需要整片擦除

必须通过“维护恢复”入口，流程：

```text
识别设备UID/Target/容量
  → 暂停业务、冻结参数修改和机器人重连
  → 读取最新有效结构 + 原始参数区备份
  → 写PC备份文件并回读校验、确认非唯一RAM副本
  → 才允许维护人员确认整片擦除
  → 下载Bootloader和应用
  → 保持维护模式，不自动启动机器人/营业
  → 校验UID/Target/schema并迁移恢复参数
  → Flash与上位机读回一致
  → 解除维护模式、重新初始化
```

推荐备份包：manifest（UID、target、容量、schema、generation、固件版本、时间、来源）、可读配置JSON、规范payload.bin、原始A/B区镜像及完整性校验。文件名按UID/时间/代次区分，不覆盖唯一备份。CRC只防误码，不等于防篡改；将来若存在不可信恢复来源再加认证。

恢复优先使用已验证、可迁移的语义payload，不盲写未知版本整区镜像。UID不符禁止自动恢复；更换主板必须走显式替换板流程。备份失败、容量/版本不匹配、恢复验证失败应停止流程。

**绝对限制：未备份就被真正全擦，单靠被擦芯片上的C结构体无法找回旧参数。** 默认值是重新配置，不是恢复原值。写保护只能作为防误操作附加层，也会妨碍正常写参数；不能承诺能够抵御外部工具解除保护并全擦。

### 8.3 误擦之后仍要恢复，需要预先同步到外部

最低落地方案：每次校准/开放配置保存后，上位机自动按UID备份配置，并显示备份代次是否落后；维护擦除前必须再做一次完整冻结备份。若上位机离线，明确标记“本机已保存，外部未备份”，不能宣称最新数据全擦可恢复。

PROGRAM.RUNTIME的端口序号更新更频繁，旧PC备份可能导致重复使用端口。不能直接恢复任意旧序号并立即连接机器人。计划内擦除以冻结后的最新快照恢复；意外全擦且只有旧备份时，需确认机器人重启清除端口历史或执行另行设计的外部端口预留协调后再连接。不能靠随机端口声称绝不重复。

如果要求“上位机长期离线、被意外全擦、每一项最新变量仍保证恢复”，现有仅片内Flash硬件无法满足，必须增加独立非易失介质/外部实时保存，并规定其写入成功条件。这是明确需求边界，不是增加几个结构体成员就能解决。

恢复出厂只复位PROGRAM.CONFIG到Target默认值，保留PROGRAM.RUNTIME端口序号；OTA更新状态不能随参数恢复随便重放，旧update_flag不得当业务备份导入。

## 9. 扩展和旧数据迁移

### 9.1 扩展成员的固定步骤

1. 在私有V2结构加入成员，V1定义保留。
2. 提升payload_schema_version，提供完整V2默认值。
3. V1→V2逐字段复制已知合法成员，新成员保持默认；校验旧长度，不能按不可信info_size memcpy。
4. 检查payload≤96；超出时明确发布记录格式升级，不静默溢出。
5. 更新上位机读写/备份表示和真实消费点。
6. 测空白、V1、损坏、未知更高版本、降级，不将“升级到默认”当数据迁移成功。

因此业务开发主要是在结构体中扩字段，但升级协议需要少量配套工作；公共A/B擦写算法和Flash地址不需要随每个字段重构。

### 9.2 当前Coffee3端口记录

旧格式是16字节记录，magic=0x43535054、序号、反码、commit。升级先选最新有效旧序号，保留该旧副本所在扇区，在另一扇区提交新PROGRAM快照；验证后才启用新记录。旧端口函数的独立擦写必须同步停用。断电重入迁移不得重置序号。

Coffee1 sector2记录不自动视为Coffee3参数：机型、设备数量不同。可作为工装显式导入源，逐字段校验映射；不得直接把0x00FF开放掩码导成当前两个物理位以外的能力。新固件降级旧固件也必须先备份，旧固件可能擦除未知记录。

## 10. 存储位功能落地闭环

- 修正0x0031写值21/22的手动映射；根因仍是Server缺分支，不是Flash开放失败。
- 0x001A为开放掩码，C3默认0x0003；仅bit0/1合法。建议0表示禁止新增存储，不能像Coffee1重启后自动变0x00FF。
- 自动找位遵守开放配置和实时空位；手动硬件调试按此前边界支持物理1/2，不无意增加业务掩码门禁。
- 停用位的真实占用仍显示；不能因配置停用就把传感器有杯伪装成无杯。
- 配置要在残杯/订单选位前加载；已开始订单使用冻结配置或修改返回忙，避免目标变化。
- 0x0032发布具体位置，复用现有放存储位协议，不为持久层新增机器人通信抽象。

## 11. 实施阶段与验收标准

| 阶段 | 产物 | 必须通过 |
| --- | --- | --- |
| P1 格式与边界 | 分区常量、记录编码、私有结构、CRC固定向量 | Keil/GCC sizeof/offsetof/编码一致，地址不与OTA重叠 |
| P2 可靠存储 | 载入/提交/轮转、旧端口迁移、错误码 | 注入每个字写失败、CRC损坏、序号回绕、A/B轮转掉电，保留旧或新完整快照 |
| P3 业务接入 | 存储位配置、端口预留、手动21/22 | 配置改动不回退端口；重启保持；不增加重复机器人启动 |
| P4 工装保护 | 普通下载范围预检、备份导出/验证/恢复流程 | 双工具链下载前后参数相同；备份失败禁止维护全擦 |
| P5 外部恢复 | UID绑定备份、维护模式、迁移导入 | 模拟全擦后恢复配置；旧端口备份不能未经处理直接连接 |
| P6 实机故障测试 | 电源中断、看门狗、网络/OTA并发报告 | Flash操作不误控输出；OTA互斥；失败日志能定位类别/阶段/原因 |

不以“编译成功”替代掉电/全擦恢复验收。建议先离线做Flash模型故障注入，再由你确认设备和数据已备份后进行上板擦写测试。

## 12. 推荐审批结论

采用“按类别定义Target私有结构体 + 上电加载RAM + 公共A/B追加提交 + 独立OTA分区 + 上位机备份恢复”。这保留你的维护方式，同时补足掉电、扩展版本、并发覆盖、整片擦除四个缺口。

首批落地PROGRAM.CONFIG的存储开放掩码和PROGRAM.RUNTIME的端口序号；Coffee1其它字段完整列为迁移候选，只有确认当前实际消费后才接入，不能伪造持久化效果。方案落地必须包含P4/P5，否则只能称“更新掉电安全”，不能称“整片擦除可恢复”。
