# 配置参数 Flash 管理最终落地方案

> 已被用户否决其中的追加保存及0～3写入限制。最新实施依据为《上位机可配置参数调研与单地址Flash落地审批方案.md》：固定地址单副本擦除覆盖，0x001A完整接受0x0000～0xFFFF。本文件仅作历史记录。

日期：2026-09-11。待审批实施。本文件替代此前两版报告的实施方案；仅新增配置管理，不合并机器人端口记录，不修改 OTA，不移动 HTTP 网页。本轮未修改固件。

## 1. 配置放在哪里

**选定 sector 2，基址 `0x08008000`，结束地址 `0x0800BFFF`，共16KB，专门存配置。**

| 区域 | 当前地址 | 本次处理 |
| --- | --- | --- |
| Bootloader | 0x08000000～0x08003FFF | 不动 |
| OTA 元数据 | 0x08004000～0x08007FFF | 不动 |
| 新增配置区 | **0x08008000～0x0800BFFF** | **仅使用这一完整扇区** |
| 应用程序，包括 HTTP 网页常量 | 0x0800C000～0x0805FFFF | 不动 |
| OTA 固件暂存区 | 0x08060000～0x080BFFFF | 不动 |
| 越疆机器人端口记录 | 0x080C0000～0x080FFFFF | 不动，不迁移到配置结构 |

核查依据：Coffee2/Coffee3 Keil scatter、GCC `STM32F407XX_COFFEE2_OTA_FLASH.ld`、Coffee3 OTA 地址常量、机器人端口函数及 v4.0 Bootloader 布局。当前工程未发现 sector 2 的配置写入者；旧 Coffee1 曾使用此地址，所以现板可能留有旧数据，首次接入必须识别而不能盲擦。

### HTTP 网页不会被覆盖

`Application/Common/Ota/app_ota_http.c:74` 的 `s_acUploadPage` 是 `static const char[]`，不是动态写进 sector 2 的配置数据。

现有 `MDK-ARM/Objects/Coffee3Close_Lst/Coffee3Close.map` 显示：

- 上传页 `s_acUploadPage`：0x0803E348，261字节。
- 成功页 `s_acSuccessPage`：0x0803E44D。
- 错误页同属 `app_ota_http.o(.constdata)`。

这些是现有构建产物中的地址，重新编译可能变化，但仍受应用链接区约束。新配置模块只允许擦 sector 2、只允许写配置区边界内的地址，不会擦应用网页所在扇区。

## 2. 配置结构是什么

首版只有已明确需要的配置，不把订单状态、端口序号、OTA 标志塞进来：

```c
typedef struct {
    uint32_t storage_enabled_mask; /* 默认0x03：开放存储位1、2 */
} Coffee3ConfigV1;
```

上位机参数含义：

| 值 | 配置含义 |
| --- | --- |
| 0x00 | 不开放存储位用于新增存杯 |
| 0x01 | 只开放存储位1 |
| 0x02 | 只开放存储位2 |
| 0x03 | 开放两个存储位，默认值 |

其他值拒绝，不能开放物理上不存在的位置。建议使用现有协议参数地址 `0x001A`，实施前与最新版上位机文档核对。不要将它与手动位置寄存器 `0x0031`、位置选择 `0x0032` 混淆。

未来新增配置就在新的版本结构中增加成员，例如实际需要的果乳校准值。配套补默认值、范围检查及旧版本转换；Flash地址不变。不能仅改变sizeof后直接把旧Flash解释成新结构。

## 3. 程序怎么用

```text
上电 → 读取配置区 → 校验 → 加载到RAM结构体 → 业务读取RAM配置
上位机修改 → 验证新值 → 保存Flash并读回确认 → 更新RAM配置 → 回复成功
```

- 配置加载必须在残杯检查、自动选存储位之前完成。
- 空白配置区默认加载0x03，首次保存默认配置。
- 业务只调用读取/修改接口，不在Workflow或Server里自己擦Flash。
- 重复写相同值不操作Flash。
- 修改失败，保留旧RAM配置，不能让上位机以为新值已掉电保存。
- 自动选位只选“已开放且传感器确认空”的位置；原始IO仍如实显示，停用配置不能掩盖有杯状态。
- 订单执行期间的配置修改返回忙，避免已经选定的存储目标中途变化。这是配置修改约束，不扩展到一次性调试指令。

## 4. 保存方法：一个独立扇区，追加完整配置记录

仍按你的方式维护RAM结构体，但不每改一次就擦掉唯一副本。每次保存将完整配置写到扇区下一个空位置，上电选择最新完整有效记录。

建议每条记录64字节，sector 2共容纳256条：

| 偏移 | 内容 |
| --- | --- |
| 0x00 | 配置记录标记magic |
| 0x04 | Target标识 |
| 0x08 | 配置版本 |
| 0x0C | 有效配置长度，最大36字节 |
| 0x10 | 保存序号 |
| 0x14～0x37 | 配置内容及确定的填充字节，共36字节 |
| 0x38 | CRC32，覆盖前56字节 |
| 0x3C | 提交标记，最后写 |

先写正文和CRC，再写提交标记，最后完整读回。中途掉电只会留下无效新记录，旧有效记录仍在。失败槽跳过，不能覆盖继续写。公共实现固定字节编码，Keil/GCC保持一致，不保存指针或未初始化结构填充。

### 扇区写满怎么处理

在“不动OTA、不动端口区”的约束下，目前只有一个独立配置扇区，**不能承诺擦除回收过程也具有双副本掉电保护**。

本方案确定：**运行中不自动擦掉满扇区。** 写满返回“配置区已满，需维护整理”，旧配置继续有效。维护工具先导出并验证最新配置，维护状态下擦sector 2，再写回最新配置并校验。维护中掉电可从外部备份恢复。

这是首版明确的使用上限：最多256次实际记录写入，包含默认记录、升级和失败占槽。若现场需要频繁调参或无人值守自动回收，再单独审批第二个独立备份区或外部存储，不能暗中占用端口/OTA区域。

如果选择每次直接“擦sector 2再写结构体”，也能正常工作，但擦完未写完时断电就可能丢配置；因此本方案不采用它作为日常保存方式。

## 5. 代码放在哪里

| 文件/模块 | 责任 |
| --- | --- |
| `Application/Common/ConfigStore/config_store.c/.h`（新增） | 固定配置记录读取、校验、追加、范围限制；不了解存储位业务 |
| `Application/UserAPP/Coffee3CloseApp/Config/coffee3_config.c/.h`（新增） | 私有结构、0x03默认值、配置验证和版本迁移 |
| Coffee3 Server | 配置寄存器读写接入；持久化成功才回复成功 |
| Coffee3 Workflow | 自动选位读取配置，不直接接触Flash |
| Coffee3 初始化入口 | 业务启动前完成加载 |

核心接口只需：初始化/加载、读取快照、设置存储位掩码。不新建任务、文件系统或通用数据库。公共模块可供其他Target复用，但私有配置结构不互相依赖；检测到其他Target或未知版本的有效记录时不自动覆盖，先报需要迁移/维护。

配置写入由一个任务上下文拥有并串行处理。虽不同扇区仍共享Flash控制器，应与现有OTA/端口写入协调执行：OTA期间返回忙，端口写入和配置写入不能并发Unlock/Program/Lock。不改变它们的数据格式、地址或业务行为。具体调度方式实施时结合当前调用线程验证，不能仅靠地址不同就并发擦写。

## 6. 首次安装与升级

- sector 2全空白：按当前Target默认值初始化。
- 有本方案有效记录：加载最新值，不每次上电覆盖默认。
- 有旧Coffee1或未知数据：不直接擦除；先备份、确认板型，再显式初始化或迁移。
- 已知旧配置版本：保留原字段，新字段填默认，追加新记录。
- 未知更高版本或损坏记录：明确报配置错误，不静默将用户值改回0x03。
- 普通固件下载只擦应用扇区，不包含sector 2。整片擦除会清掉配置，维护前应备份；本方案不声称同片数据能抵御整片擦除。

## 7. 同时修复手动放存储位入口

现有日志拒绝的直接原因是Server缺少位置21/22的映射，不是配置掩码未保存。

- `0x0031`写十进制21（0x15）→ `PUT_STORAGE`，参数1。
- `0x0031`写十进制22（0x16）→ `PUT_STORAGE`，参数2。
- 复用现有`vCoffee3ServerSelectStorage()`和机器人动作路径，先发布0x0032，再发动作。
- 单步调试仍遵守此前机器人就绪规则，不因此自动执行整套启动；业务开放掩码用于自动分配，不额外限制已存在的物理位置调试。

## 8. 实施与验收清单

1. 新增配置模块、初始化加载和0x001A读写；补21/22手动映射。
2. Keil/GCC纳入新文件；核对应用链接区仍从0x0800C000开始，网页常量仍在应用区。
3. 在Flash模拟测试中验证：0/1/2/3保存、同值不写、非法值拒绝、记录写中断电、满区拒绝、未知格式拒绝、旧版本扩展。
4. 上板验证重启后配置保持；保存前后网页可访问，OTA行为不变，端口记录不变；故障注入由用户确认板卡并备份后执行。
5. 交付配置源码位置、默认值修改位置、字段扩展步骤及维护导出/整理方式。不把“模块写完”当完整交付，满区维护工具也应可操作。

**最终选择：配置专用sector 2（0x08008000），Target私有配置结构，日常追加保存；OTA、网页和越疆端口存储完全保持原地址与格式。**
