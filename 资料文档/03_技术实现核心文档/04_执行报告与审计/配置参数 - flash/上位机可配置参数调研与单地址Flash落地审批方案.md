# 上位机可配置参数调研与单地址 Flash 落地审批方案

> 后续最终审批已扩展唯一 `Coffee3Config_t`：保留0x001A存储位掩码，并加入0x00AA~0x00AF六路果乳比例系数。结构和标记不做V1/V2并行命名，统一使用 `Coffee3Config_t` 与 `COFFEE3_CONFIG_MARK`。本文件其余“首轮只实现0x001A”的文字作为当时审批历史保留。

本方案供审批后实施。结论：配置固定放在 **0x08008000**，只保留一份结构体，上电读取；上位机修改成功时立即擦除并覆盖保存。不追加、不轮转、不定时保存、不合并端口或OTA。

“低频”仅表示实际配置操作很少，不是软件限频、延迟合并或隔一段时间才写。相同值重复写无需擦除。

## 1. 本次调查依据

- 当前磁盘上的《咖啡售卖机下位机-通信协议.docx》，读取参数表的地址、范围和说明；只读提取，不修改Word文件。Word中尚未保存的内容不在本次读取范围。
- Coffee1 `coffee_close_v2.8.29_IOPage/ControlFlow/machine_type.h/.c` 与 `modbus/tcp_server.c` 的参数赋值、单写/多写保存路径。
- 当前Coffee3的Server、Workflow及配置宏。

必须区分：**协议允许上位机写入，不代表这个值已经被固件保存到Flash，也不代表它属于长期配置。** 当前Coffee3普通寄存器写入多数先复制到RAM，再分发动作；不能据写入成功判断配置已经落盘。

## 4. 0x001A最终语义

**全范围接受、原值保存、原值读回。**

```c
stored_mask = host_value;             /* 0x0000～0xFFFF原样保存 */
effective_mask = stored_mask & 0x0003; /* Coffee3当前实际两个存储位 */
```

| 上位机写入 | Flash/FC03读回 | 当前实际开放 |
| --- | --- | --- |
| 0x0000 | 0x0000 | 无 |
| 0x0001 | 0x0001 | 存储位1 |
| 0x0002 | 0x0002 | 存储位2 |
| 0x0003 | 0x0003 | 两个位置 |
| 0x8000 | 0x8000 | 当前无对应物理位置，不执行额外动作 |
| 0xFFFF | 0xFFFF | 两个位置；高位保留 |

0和0xFFFF都是合法配置，不作为“没有初始化”的判断条件。默认0x03只用于尚未初始化/无效配置恢复，不得每次上电强制改回。

协议0x001A位说明只列到第15位，但字段范围与本次用户要求明确覆盖16位；第16位同样保存，当前不产生物理效果，不以文字漏项拒绝0x8000。

已关闭位置的实际有杯信号仍如实显示；自动分配过滤开放掩码。既有杯子的人工清理/取杯不能简单因为停用就永久无法处理。当前在途订单保持已选位置，配置成功后的新分配使用新值，避免临时切换本单目标。

## 5. 固定地址与结构

地址仍为 **0x08008000，sector 2**。只保存一份，不使用历史记录、64字节槽、A/B或“写满维护”。

```c
typedef struct {
    uint32_t valid_mark;           /* Coffee3配置格式V1的专用有效标记 */
    uint32_t storage_enabled_mask; /* 仅低16位存参数，默认0x0003 */
} Coffee3Config_t;
```

首版8字节：0x08008000为标记，0x08008004为配置值。用专用标记区分空白Flash；检查值的高16位必须为0，低16位任意合法。不能用参数值0xFFFF判断空白。

扩展时增加私有结构成员，并更新格式标记或明确版本，保留已知旧格式的迁移规则。新成员设置默认，已有配置值保留；不直接按新版sizeof读取旧记录后假设新增成员有效。

边界保持：sector1为OTA元数据；应用从0x0800C000开始，HTTP网页为应用只读常量；sector7～9为OTA暂存；sector10/11为越疆端口日志。上述区域、格式和业务不变。配置虽然只有8字节，但sector2擦除粒度为16KB，这个扇区不能混入其他不可重建内容。

## 6. 上电和修改流程

### 上电只加载一次

1. 在业务初始化前读取固定地址。
2. 标记正确且字段合法：加载RAM，发布0x001A读回值，不擦写。
3. 无有效配置：RAM生成0x03，擦sector2，写配置值，最后写有效标记，读回验证。
4. 初始化写失败则明确报错，不宣称配置初始化成功。已知旧格式先转换；未知数据需日志标明恢复默认的原因。

### 上位机写入立即保存

1. FC06写单寄存器或FC16范围覆盖0x001A时，提取对应值；FC16不限制数量必须为1。
2. 先完成请求范围检查，准备新结构。与当前已保存值相同则不擦写。
3. 串行取得Flash操作权限，擦sector2，写完整新配置，标记最后写，读回比较。
4. 成功后更新RAM配置和0x001A镜像，回复成功。配置写本身不触发机器人动作、不触发订单制作。
5. 保存失败返回设备故障异常04并记录原因，保留当前RAM旧值；必须说明Flash旧副本可能已被擦除，不能声称RAM旧值代表已落盘。
6. OTA/另一Flash写正在进行时返回忙06或按现有可兼容的错误路径明确失败；不得两个写入者并发Unlock/Program/Lock。Flash操作不放入中断，不修改nanoMODBUS核心协议栈。

FC16同包有配置和其他可写寄存器时，先检查整包合法性，再保存配置，成功后才发布RAM及分发命令；Flash失败不得先执行包内动作。通信应答表示寄存器受理/保存结果，不等于异步设备动作完成。这只解决配置提交顺序，不扩展为跨设备事务。

没有定时器、等待凑批、主动延迟或软件写次数限制。实际写操作少，所以使用用户指定的单份擦除覆盖。

**接受的限制：擦除后写完前掉电，单副本可能丢失，下次默认恢复0x03；最后写标记不能保证保住旧值。** 不额外增加被否决的历史/双副本机制。整片擦除也会丢配置。

## 8. 验收标准

- 空白配置启动读回0x03；第二次启动不再次擦除。
- FC06、FC16分别验证0、1、2、3、0x8000、0xFFFF；重启后原值保持。
- 0xFFFF只能使用现有两个位置；0x8000不访问不存在的IO或数组索引。
- 同值重复写不擦Flash；不同值每次成功请求立即覆盖。
- 非法地址/跨区请求不改变配置；保存失败不回复成功、不提前执行同包动作。
- 网页仍可访问；OTA与端口记录未被覆盖；更新配置不引起机器人连接/启动流程变化。
- Keil/GCC均编译；写前写后比对扇区边界，掉电恢复默认场景需上板确认后测试。
