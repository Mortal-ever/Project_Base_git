# Coffee3Close RTU Bus 自主轮询与命令优先级架构调研报告

> 调研日期：2026-09-20  
> 复审版本：V3，纳入“放弃后台帧后重发”“IO 服务域快速轮询”和“TCP 明确排除”  
> 调研范围：Coffee3Close 外部 Modbus RTU/串口 Bus、设备状态镜像、C3Server/Workflow 命令投递关系  
> 不适用范围：机器人 Modbus TCP Client、C3Server TCP 会话和其他一连接一目标的 TCP 任务  
> 本报告性质：新架构设计与迁移建议；本次不修改固件源码，不处理制冰流程日志改造

## 1. 结论

用户提出的总体方向正确，建议正式采用：

1. 每个物理 RTU Bus 任务继续作为该串口、协议端口和事务状态的唯一所有者。
2. 周期状态轮询从 Workflow 下沉到对应 Bus 任务，由 Bus 自主调度所属设备。
3. C3Server、Workflow、维护流程只投递前台命令，不再定期投递 `REFRESH` 命令维持设备在线状态。
4. Bus 内部区分前台命令（调试、订单、维护和安全动作）与后台轮询（状态刷新和通信健康检查）。
5. 前台命令优先。只读后台查询在等待响应阶段可被主动放弃；系统保存轮询游标和步骤，完成接收清理后执行前台命令，随后重新发送被放弃的后台查询。
6. 每台设备使用独立的 3000ms 轮询截止时间；同一 Bus 的设备在启动时按 200ms 错相，不能采用“整轮扫描完再固定睡眠 3 秒”。
7. 设备离线由“连续两次实际执行的健康轮询没有获得目标设备有效响应”判定，不由命令等待时间或简单墙钟超时直接判定。
8. 命令洪泛期间允许后台轮询一直暂停；未实际执行的轮询不累计丢帧，也不触发离线。
9. 不为 UART 增加二值信号量或互斥量。用户提出的“单槽执行权”由 Bus 单任务所有权、前台队列和内部执行状态实现。
10. DeviceImage 继续作为 Bus 到 C3Server/Workflow 的状态快照，但需要统一为“私有临时结果完成后一次提交”，避免读到半更新数据。
11. IO 采用专用快速策略：板载 GPIO 状态周期刷新，Bus5 外部输入/输出模块以 100ms 设备槽错相轮询，输入模块连续 3 次实际查询无有效响应后判离线；输出写命令优先。

该方案能降低 Workflow 的周期调度负担，使设备晚上线、短时丢帧、恢复上线均可自愈，同时保持上位机命令和业务命令的响应优先级。

## 2. 当前真实架构

当前工程需要先澄清一个前提：并不是所有设备轮询都由 C3Server 发起。

```text
C3Server                    Workflow
  │ 上位机手动/调试命令        │ 订单动作 + 周期 REFRESH
  └──────────┬───────────────┘
             ↓
       Coffee3Command Queue
             ↓
       对应 RTU Bus 任务
             ↓
       设备驱动/协议收发
             ↓
        DeviceImage 快照
             ↓
 C3Server 映射为上位机状态寄存器
```

代码证据：

- `coffee3_rtu_bus.c` 的 Bus 任务通过 `xQueueReceive()`等待命令，本身尚无设备周期调度器。
- `coffee3_workflow.c` 的 `prvServiceIoRefresh()`负责周期性投递外部设备刷新。
- `coffee3_server.c` 的手动命令通过 `xCoffee3CommandSubmitUrgent()`进入对应 Bus 队列。
- `coffee3_device.c` 对 urgent 命令使用 `xQueueSendToFront()`。
- `coffee3_server.c` 的 `prvRefreshStatusRegisters()`读取各 DeviceImage，再投影到上位机寄存器。

因此本次重构的本质是：

> 将“设备健康轮询调度权”从 Workflow 移交给物理 Bus 所有者；C3Server 保持协议入口和状态发布职责。

### 2.1 当前 Bus 与设备分布

| Bus | 默认波特率 | 当前设备 | 备注 |
| --- | ---: | --- | --- |
| Bus2 | 115200 | M50 咖啡机，Unit 1 | 当前仅一台设备 |
| Bus3 | 9600 | 落杯机 Unit 1、糖浆机 Unit 2、压盖机 Unit 1、电表 Unit 3 | 设备最多、总线最慢，是错相调度重点 |
| Bus4 | 19200 | 制冰机 Unit 1、电子秤 Unit 2 | 制冰机已有 100ms 最小帧间隔 |
| Bus5 | 38400 | IO 输入 Unit 1、IO 输出 Unit 2 | IO 设备已有 20ms 最小帧间隔 |

当前通用 RTU 事务超时为 500ms，Bus 空闲等待为 20ms，前台命令队列长度为 4。新的 3 秒轮询周期应建立在这些现有边界之上，而不是替代驱动超时和设备最小帧间隔。

## 3. 当前职责错位带来的问题

### 3.1 周期监控依赖上层业务任务

设备是否被刷新取决于 Workflow 何时调用 `prvServiceIoRefresh()`。当 Workflow 正在执行长步骤、等待动作结果或进入异常分支时，设备健康轮询可能被延后。设备通信健康属于传输层/设备层责任，不应依赖业务状态机是否空闲。

### 3.2 周期刷新与前台命令共享短队列

当前 `COFFEE3_COMMAND_QUEUE_LENGTH` 为 4。若后台轮询也作为普通命令反复塞入该队列，可能出现后台刷新占用队列槽位、前台动作入队失败、重复刷新积压、过期轮询仍被执行，以及无法区分“设备没有响应”和“轮询根本没有得到执行机会”。

新架构中，后台轮询不应进入前台命令队列，而应由 Bus 内部调度器直接生成一次事务。

### 3.3 在线状态容易被单次错误抖动

RTU 现场可能出现单帧超时、CRC 错误、串口干扰或其他从站帧混入。单次失败立即判离线，会造成 ready 状态频繁升降。

### 3.4 全局镜像存在一致性边界

Bus 写 DeviceImage 与 C3Server 读 DeviceImage 发生在不同任务。对齐的 16/32 位单字段写入通常是原子的，但包含多个字段的完整设备状态并不天然具有快照一致性。若驱动逐字段写全局结构，C3Server 可能读到新旧字段混合状态。

## 4. 目标职责划分

### 4.1 C3Server

C3Server 应负责解析上位机请求、构造设备命令、标记来源和优先级、读取稳定设备快照、投影状态寄存器，以及返回命令结果。

C3Server 不应负责周期调度 RTU 状态查询、判断设备通信在线/离线、解析具体设备协议帧或管理 UART 重试和帧间隔。

“命令队列编辑器”可以作为理解方式，但更准确的定位是：

> C3Server 是上位机命令入口和状态寄存器发布者；真正的命令仲裁发生在对应 Bus 任务内部。

### 4.2 Workflow

Workflow 负责订单与维护业务状态机、投递设备动作、等待命令完成事件，以及根据 DeviceImage、DeviceStatus 和业务条件决定下一步骤。Workflow 不再负责外部设备的周期健康刷新。

### 4.3 RTU Bus

每个 RTU Bus 任务负责：

- 作为 UART 和 ModbusPort/自有协议端口的唯一所有者；
- 串行执行前台命令；
- 自主调度后台健康轮询；
- 执行设备规定的最小帧间隔；
- 维护每台设备的在线状态、连续失败计数和最近成功时间；
- 将完整结果提交到 DeviceImage；
- 发布设备上线、首次丢帧、掉线和恢复事件。

### 4.4 设备驱动

设备驱动负责生成具体协议请求、校验目标设备响应、解析数据为设备语义并返回统一结果码，但不决定全局任务调度优先级。

## 5. 推荐的数据流

```text
                       ┌─────────────────────┐
上位机 ──> C3Server ──>│ 前台命令队列         │
Workflow ─────────────>│ safety/manual/work  │
                       └──────────┬──────────┘
                                  ▼
                  ┌────────────────────────────┐
                  │ 每个 RTU Bus 唯一所有者任务 │
                  │ 1. 检查前台命令            │
                  │ 2. 检查到期后台轮询        │
                  │ 3. 执行一个完整协议事务    │
                  │ 4. 更新健康状态和镜像      │
                  └──────────────┬─────────────┘
                                 │
                ┌────────────────┴────────────────┐
                ▼                                 ▼
        DeviceImage 快照                  DeviceStatus/Event
                └────────────────┬────────────────┘
                                 ▼
                 C3Server 只读映射状态寄存器
```

例如上位机地址 4208（`0x1070`）为制冰机状态区域、4256（`0x10A0`）为果乳状态区域，`0x10F2`起为外部输入状态、`0x10FA`起为外部输出状态。这些寄存器的读取只应取得最近一次稳定快照，不应触发实时串口查询。

### 5.1 TCP 明确排除

本报告的“单槽、后台轮询、主动放弃帧、保存游标和多设备顺序恢复”只用于一条 RTU 串口挂载多个从站的场景。

机器人 Modbus TCP Client 当前是一任务负责一个目标连接，不承担同一任务下多个从站的轮询，也不存在多个 RTU 从站共享半双工链路的问题。TCP 建连、重连、keepalive、请求响应和机器人动作状态继续由机器人 TCP 模块独立处理，不复用本报告的 RTU 抢占调度器。

C3Server 的 TCP 客户端会话管理同样不属于本报告范围。本报告只讨论 C3Server 生成的设备命令如何进入 RTU Bus，不讨论 TCP Server 本身的连接并发。

## 6. 普通 RTU 设备轮询周期设计

本节适用于 Bus2、Bus3、Bus4 的普通设备。Bus5 IO 使用第 11 节的 100ms 专用策略，不套用本节 3 秒周期。

### 6.1 不建议“整轮结束后再等 3 秒”

若一个 Bus 有 3 台设备，使用以下逻辑：

```text
设备1 -> 200ms -> 设备2 -> 200ms -> 设备3 -> 等待3s -> 设备1
```

则每台设备的真实周期为：

```text
3s + 设备间隔 + 每笔事务实际耗时或超时时间
```

当某台设备超时 500ms 时，后续设备的周期都会被拖长，“两次丢帧约 6 秒”的含义也会失真。

### 6.2 推荐“每设备独立截止时间 + 200ms 启动错相”

每台设备维护自己的 `next_poll_tick`：

```text
设备1：t=0ms,    3000ms, 6000ms ...
设备2：t=200ms,  3200ms, 6200ms ...
设备3：t=400ms,  3400ms, 6400ms ...
```

这样每台设备目标周期稳定约 3 秒，多设备不会集中发帧，某台设备超时也不会永久改变其他设备的基准周期。前台命令插入后，逾期轮询可在命令完成后补执行，轮询延迟不被误算成通信丢帧。

### 6.3 200ms 的正确含义

200ms 应定义为后台设备轮询的错相和最早启动间隔，而不是 Bus 任务中的固定阻塞延时。禁止直接使用固定 `vTaskDelay(200ms)`，否则这 200ms 内到达的 urgent 命令也会被无条件延迟。

正确做法是记录下一次允许执行后台轮询的时间，在等待期间用带超时的 `xQueueReceive()`等待前台命令。前台命令可以提前唤醒 Bus，但仍需满足：

- Modbus RTU 3.5 字符静默间隔；
- 当前设备绑定的 `usMinimumIntervalMs`；
- 驱动协议规定的额外间隔。

现有绑定中制冰机、IO 模块已有各自最小帧间隔。普通设备的 200ms 调度参数不能覆盖设备约束，应取实际要求的最大值；Bus5 IO 则使用第 11 节独立的 50ms 错相和专用超时。

## 7. Bus 调度模型

推荐的任务循环如下：

```c
for (;;) {
    now = tick();

    if (has_safety_command()) {
        execute_one_complete_transaction();
        publish_result();
        continue;
    }

    if (has_foreground_command()) {
        execute_one_complete_transaction();
        publish_result();
        continue;
    }

    device = find_due_poll(now);
    if (device != NULL) {
        execute_device_refresh(device);
        commit_device_image(device);
        update_poll_health(device);
        schedule_next_deadline(device);
        continue;
    }

    wait_ticks = time_to_nearest_deadline();
    xQueueReceive(command_queue, &command, wait_ticks);
}
```

任务在没有命令且轮询未到期时必须阻塞在队列上，不能产生忙循环。

### 7.1 后台帧主动放弃与步骤恢复

复审后采纳用户提出的目标：当后台状态查询已经发送、正在等待从机响应时，若前台命令到达，可以主动放弃该后台帧，不等待原超时结束。系统保存当前设备、轮询游标和刷新阶段，优先执行前台命令；前台队列清空后，从被放弃的步骤重新发送完整后台查询。

这里的“恢复”不是继续接收上一帧剩余字节，而是：

```text
后台查询已发送，正在等待响应
              ↓ 前台命令到达
标记当前后台步骤为 PREEMPTED
              ↓
中止本次接收并丢弃已收字节
              ↓
清理 nanoMODBUS/Transport 接收状态
              ↓
等待总线重新静默，隔离可能晚到的旧响应
              ↓
执行前台命令
              ↓ 前台队列清空
重新发送被放弃的后台查询
```

被放弃的后台帧属于本机调度抢占，不是设备丢帧，不增加 `poll_miss_count`，也不改变设备在线状态。

### 7.2 必须解决的旧响应污染问题

Modbus RTU 没有事务 ID。旧后台响应若在前台请求发出后才到达，可能被误认为新命令的响应；当新旧请求属于同一 Unit、相同功能码和相同响应长度时，仅靠响应帧甚至无法可靠区分。

因此不能只设置一个“取消标志”后立即发送前台帧，必须具备完整的安全退出过程：

1. 中止后台等待，返回专用结果 `PREEMPTED`，不能伪装成 TIMEOUT，也不能复用现有 `CANCELED=-9`；用户取消和调度抢占是不同语义。
2. 暂停或重新武装 UART 接收。
3. 清空 Transport StreamBuffer 和 nanoMODBUS 当前消息状态。
4. 丢弃抢占窗口内晚到的旧字节。
5. 检测总线连续静默达到协议要求后，再发送前台请求。
6. 前台结束后，从保存的步骤重新构造并发送后台请求，不复用旧解析缓存。

当前工程已有 `TRANSPORT_CTRL_RX_PAUSE/RX_RESUME/RX_FLUSH`和 nanoMODBUS `flush`基础，但目前一次 `xStreamBufferReceive()`会阻塞至数据到达或超时，前台队列到达本身不能立即打断它。正式实施时还需要增加“可取消接收”能力。

推荐做法是：ModbusPort 接收保持原总超时，但内部使用短时间片等待，例如 5~20ms；每个时间片结束检查 `foreground_pending/preempt_requested`。这样最坏抢占响应由 500ms 降到一个短时间片加清理时间，不需要让其他任务直接操作 UART。

不建议让命令提交者跨任务直接调用 `HAL_UART_AbortReceive()`，否则会破坏 Bus 单所有者原则。命令提交者只负责入队并设置原子抢占请求或任务通知，实际中止、清理和重发仍由 Bus 所有者执行。

抢占仅允许用于只读后台状态轮询。前台写命令、设备动作命令、已经开始产生物理动作的命令不得被另一条普通命令放弃。

还应建立“允许抢占设备白名单”和每类设备的晚响应隔离参数。若某个从站的最坏响应延迟无法测量或无法界定，则不能保证旧响应不会污染下一事务，该设备只能在发送前让出优先级，不能在等待响应期间主动放弃。Bus5 IO 应作为第一批实测和启用对象。

## 8. 命令优先级与后台暂停策略

建议至少划分以下优先级：

1. 安全停止、关闭危险输出；
2. 上位机手动调试命令；
3. Workflow 订单和维护动作；
4. 后台健康轮询。

现有 `xCoffee3CommandSubmitUrgent()`与`xQueueSendToFront()`可继续用于前台优先命令。

本次复审采用用户提出的明确策略：前台命令洪泛期间，后台轮询允许暂停，不设置强制插入轮询的时间上限，也不使用 burst limit 抢占前台命令。

后台调度器只保留一个恢复点：

- 当前 Bus 轮询设备索引；
- 当前设备刷新阶段；
- 本次查询是否已经发送；
- 当前步骤是否因前台命令被主动放弃；
- 恢复后应重发的完整刷新动作。

当前台队列仍有命令时，继续执行前台命令；队列清空后，再重发被放弃的后台步骤并继续原有顺序。暂停期间不推进轮询截止时间、不补算失败次数，也不因为状态快照变旧而直接判离线。可以单独暴露 `stale/age`供诊断，但 `stale`不等于 `offline`。

这种策略主动选择“前台响应优先，后台监控可能长期暂停”，不存在需要解决的后台防饥饿问题。

## 9. 在线状态与两次丢帧判定

### 9.1 推荐状态机

```text
UNKNOWN
   │ 首次有效响应
   ▼
 ONLINE ──首次健康轮询失败──> SUSPECT
   ▲                             │
   │ 下一次有效响应              │ 第二次连续健康轮询失败
   └─────────────────────────────┤
                                 ▼
                              OFFLINE
                                 │
                                 └──任意目标设备有效响应──> ONLINE
```

对外部业务可将 `SUSPECT`暂时仍视为 online，仅在日志中报告第一次 miss；第二次连续失败才发布 offline/lost 事件。

### 9.2 哪些结果推进失败计数

只有“实际执行的周期健康轮询”可以增加连续失败计数：

- 健康轮询超时：`poll_miss_count++`；
- 健康轮询收到坏 CRC、错误长度、错误目标从站响应：`poll_miss_count++`；
- 健康轮询成功：计数清零并置 online；
- 前台命令超时：向调用者返回失败，但不增加健康轮询 miss；
- 前台命令获得目标设备有效响应：可以清零 miss 并恢复 online；
- 轮询因前台命令繁忙而尚未执行：不算丢帧；
- 后台轮询被前台命令主动放弃并标记为 `PREEMPTED`：不算丢帧；
- 队列投递失败：不算设备丢帧，而是本机调度错误。

“有效响应”必须来自目标设备/目标 Unit，帧完整，CRC 或自有协议校验正确，并且请求与响应语义匹配。

Modbus Exception 响应虽然表示命令失败，但能够证明目标设备在线，因此应恢复 online，同时将命令结果返回为协议异常。串口噪声、其他从站帧、坏 CRC 不能证明目标设备在线。

### 9.3 名义约 6 秒，但不是时间判据

若设备最近一次在 `t=0`成功，健康轮询周期为 3 秒：

```text
t=3s：第一次失败，进入 SUSPECT
t=6s：第二次连续失败，进入 OFFLINE
```

因此从最近一次有效响应到判离线约为 6 秒，再加上单次事务超时和调度抖动。

启动阶段若第一轮在 `t=0`立即执行，两次失败可能在约 3 秒后完成。建议启动时使用 `UNKNOWN`语义，并在日志中区分“从未上线”和“已上线后掉线”，不要把两者都打印成 lost。若产品要求启动时也必须等待约 6 秒才报告 offline，可将首轮截止时间安排在 `3000ms + stagger`。

## 10. 前台命令与后台轮询的同设备冲突

由于同一 Bus 只有一个任务执行协议事务，不会发生物理串口并发冲突。

推荐规则：

- 前台命令已到队列时，先执行前台命令；
- 前台命令与到期轮询相同且响应包含完整状态时，可将该响应同时作为本次健康证明，提交镜像并重新安排下次轮询；
- 写命令只有简短 ACK 时，只证明在线，不代表完整状态已刷新；下一次状态轮询仍需执行；
- 前台命令执行期间轮询到期，命令结束后补做轮询，不记为丢帧；
- 不需要把两条相同请求同时发出，可在调度层做“已由前台刷新覆盖”的合并，但这属于优化而非第一阶段必需功能。

## 11. IO 服务域特殊设计

IO 不应直接套用其他 RTU 设备的 3 秒周期。当前 IO 状态包含三类来源：

1. 板载 8 路输入和 8 路输出：直接访问 STM32 GPIO，不经过 Bus5，不存在 Modbus 丢帧；
2. Bus5 外部输入模块：Unit 1，通过 RTU 周期读取输入；
3. Bus5 外部输出模块：Unit 2，通过前台写命令控制，并通过后台回读维护输出镜像和通信健康。

逻辑上可以将三者归入同一个“IO 服务域”，但物理上必须区分本地 GPIO 与 RTU 从站，不能把本地 GPIO 刷新伪装成一条 Bus5 协议帧。

### 11.1 推荐时序

建议精确定义为：

```text
t=0ms    采样板载 GPIO + 查询外部输入 Unit 1
t=50ms                 查询外部输出 Unit 2
t=100ms  采样板载 GPIO + 查询外部输入 Unit 1
t=150ms                查询外部输出 Unit 2
t=200ms  进入下一轮
```

由此得到：

- 板载 GPIO 快照周期：100ms；
- 外部输入模块自身查询周期：100ms；
- 外部输出模块自身回读周期：100ms；
- 两个 RTU 从站之间的启动错相：50ms；
- 上层输出命令到达时，主动放弃当前后台查询，完成接收清理后优先写输出；
- 前台队列清空后，重新发送被放弃的输入查询或输出回读。

若实测表明 50ms 错相不足以覆盖从站最坏响应时间，应增大错相，但仍保持“每设备独立截止时间”，不能退回整轮扫描后统一延时。

### 11.2 IO 独立超时

当前通用 RTU 超时为 500ms。若外部 IO 每台设备都要求 100ms 周期，500ms 超时在某个模块掉线时会连续占用多个轮询槽，因此无法保证上述节拍。

建议为 Bus5 健康查询增加独立短超时：

```text
COFFEE3_IO_POLL_TIMEOUT_MS = 50~100ms，最终值由硬件实测确定
```

输出写命令仍可使用更宽松的业务超时。轮询周期、轮询超时和前台写命令超时必须分开配置，不能继续共用一个数值。

### 11.3 三次丢帧判定

外部输入模块采用连续 3 次实际健康查询无有效响应后判离线：

```text
ONLINE -> miss 1 -> SUSPECT_1 -> miss 2 -> SUSPECT_2 -> miss 3 -> OFFLINE
```

前台命令抢占导致的 `PREEMPTED`、尚未执行的轮询、调度延迟均不计 miss。任意一次有效输入响应立即清零计数并恢复 ONLINE。

外部输出模块也建议使用 3 次后台回读失败作为离线依据。一次输出写失败应立即返回上层“本次写入失败”，但不等同于模块已经离线；后续后台回读继续完成通信健康确认。写命令获得有效 ACK 或有效回读可以恢复模块 ONLINE。

板载 GPIO 没有“通信离线”概念，只维护最近采样时间和快照版本。若采样长期未执行，应报告 `LOCAL_IO_STALE`，不能打印 RTU offline。

### 11.4 本地输出和外部输出的优先级

外部输出必须通过 Bus5 前台命令队列执行，保持 UART 单所有者。

板载输出是直接 GPIO，不应为了形式统一而被外部 RTU 超时阻塞。现有本地输出接口可以继续立即执行，但所有写入点必须通过统一 IO API，并保持门升/门降等互锁检查；不能由多个模块直接操作 GPIO 寄存器。

## 12. 为什么不需要 Mutex 或二值信号量

在推荐架构中，只有 Bus 任务能够调用该串口的发送、接收和协议事务接口，其他任务只能通过队列提交命令，所有事务在单一任务上下文串行执行。

这已经满足 UART 单所有者模型。额外增加 Mutex 会形成重复保护，并可能带来锁顺序复杂、优先级反转、异常路径忘记释放锁，以及诱导其他任务绕过队列直接访问串口等问题。

用户提出的“任何时刻只允许前台或后台一方执掌 Bus”的单槽概念是正确的。只是该槽不需要由二值信号量创建：Bus 任务本身就是唯一执行者，`IDLE/BACKGROUND/FOREGROUND/CLEANUP`执行状态已经能保证单槽互斥。

二值信号量只能表达“有/无”事件，不能保存设备 ID、命令参数、后台游标、被放弃阶段和返回对象。如果把它作为 Bus 所有权锁，还会与单任务所有权重复。

因此建议：

- 跨任务传递命令：Queue；
- 通知 Bus 尽快放弃后台等待：原子 `preempt_requested`配合 Task Notification，或由可取消接收层周期检查；
- UART 完成中断唤醒 Bus：Task Notification 或 Binary Semaphore；
- 状态发布：DeviceImage 原子提交 + Event/Status；
- 禁止其他任务直接访问 Bus 的 ModbusPort/UART 句柄。

只有未来确实出现多个任务必须直接访问同一硬件资源、且无法改为单所有者时，才考虑 Mutex；当前没有必要。

## 13. Modbus 与自有协议的统一轮询抽象

后台调度器不应写死为“发送 Modbus 03 功能码”。正确抽象是：

```text
Bus Scheduler
      ↓
Device Binding / Driver 的 REFRESH 动作
      ↓
具体驱动决定协议
      ├─ Modbus FC03/FC01/组合查询
      ├─ 咖啡机 F200 QUERY 0x10
      └─ 其他厂商自有状态查询帧
```

例如 F200 咖啡机状态查询帧：

```text
7E 1A 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00
00 10 00 00 00 00 2A 7E
```

现有 F200 驱动已经具有 `COFFEE_MACHINE_F200_ACTION_REFRESH`和查询命令抽象，说明统一 `REFRESH`接口可行。Bus 调度器只关心“该设备的刷新动作是否成功并产生完整镜像”，不理解每种设备的帧字段。

## 14. DeviceImage 提交和 C3Server 映射

推荐每次刷新采用以下流程：

```text
驱动在 Bus 私有临时结构中解析完整响应
                ↓
所有校验通过
                ↓
一次性 Commit 到公共 DeviceImage
                ↓
更新 device status / last_success_tick
                ↓
C3Server 在下一次状态发布时读取稳定快照
```

不建议驱动在解析过程中逐字段直接修改公共镜像。

统一 Commit 可选两种实现：

1. 小型结构：在极短临界区内完成结构复制；
2. 较大结构：双缓冲或版本号快照，读者检测版本变化后重读。

应复用当前 Coffee/Cup/Lid 已存在的 Commit helper 思路，并扩展到 Syrup、Ice、Scale、EnergyMeter、IO。临界区内不得进行日志、协议收发或等待。

C3Server 只读取最近一次提交成功的状态；通信失败时保留最后有效值，同时依靠 DeviceStatus 的 online/stale 字段告诉上层该快照是否仍可信，不能在失败时把所有业务字段立即清零。

## 15. 长时间同步驱动的阻塞风险

新的 Bus 自主轮询架构要求一个事务有明确、较短、可界定的占用时间。

当前 M50 咖啡机驱动的部分动作会在驱动内部循环查询并等待较长时间。Bus2 目前只有 M50 一台设备，因此第一阶段可以暂时保留；但这种模式不能复制到 Bus3、Bus4、Bus5 等多设备总线。

多设备 Bus 的长期原则应是：

```text
短事务“启动动作” -> 释放 Bus 调度权 -> Bus 周期查询状态 -> Workflow 根据镜像/事件判断完成
```

不能让驱动内部循环等待几十秒或几分钟，否则整个 Bus 上其他设备和 urgent 命令都会被阻塞。

因此实施前应审计每个设备动作的最长同步占用时间；多设备 Bus 禁止新增长循环等待型驱动。

## 16. 建议的数据结构和配置项

每台可轮询设备建议维护：

```text

bus_id
refresh_action
poll_period_ms
initial_stagger_ms
next_poll_tick
last_attempt_tick
last_success_tick
poll_miss_count
health_state: UNKNOWN / ONLINE / SUSPECT / OFFLINE
image_generation
preemptible
late_response_guard_ms
saved_poll_step
```

建议配置项：

```c
#define COFFEE3_BUS_POLL_PERIOD_MS            3000U
#define COFFEE3_BUS_DEVICE_STAGGER_MS          200U
#define COFFEE3_DEVICE_OFFLINE_MISS_LIMIT        2U
#define COFFEE3_RTU_PREEMPT_CHECK_SLICE_MS       10U /* 候选值，实测范围5..20ms */
#define COFFEE3_IO_LOCAL_SCAN_PERIOD_MS         100U
#define COFFEE3_IO_DEVICE_POLL_PERIOD_MS        100U
#define COFFEE3_IO_DEVICE_STAGGER_MS             50U
#define COFFEE3_IO_OFFLINE_MISS_LIMIT              3U
#define COFFEE3_IO_POLL_TIMEOUT_MS                100U /* 候选值，实测范围50..100ms */
```

设计约束：

- 配置允许单设备覆盖，不强制所有设备完全相同；
- `usMinimumIntervalMs`继续生效；
- 到期计算使用 FreeRTOS Tick 的回绕安全比较方式；
- 不使用动态内存；
- 轮询表根据现有静态设备绑定在初始化时建立；
- 后台轮询不占用长度为 4 的前台命令队列。

## 17. 日志和可观测性建议

状态位掩码可以继续用于上位机协议，但现场日志必须带设备名和 Bus，不能只打印 `ready=0x00C2 lost=0x0600`。

推荐事件日志：

```text
[C3Bus4:Ice] DEVICE_POLL_OK result=0 unit=1 period_ms=3000
[C3Bus4:Ice] DEVICE_POLL_MISS result=-4 unit=1 miss=1 limit=2 state=SUSPECT
[C3Bus4:Ice] DEVICE_OFFLINE result=-4 unit=1 misses=2 last_ok_ms=...
[C3Bus4:Ice] DEVICE_ONLINE result=0 unit=1 recovery=1
[C3Bus4:Ice] DEVICE_IMAGE_COMMITTED result=0 generation=123
[C3Bus4:Ice] DEVICE_POLL_DELAYED result=0 overdue_ms=... reason=FOREGROUND_COMMAND
[C3Bus4:Ice] DEVICE_POLL_PREEMPTED result=PREEMPTED step=... foreground_device=...
[C3Bus4:Ice] DEVICE_POLL_RESUMED result=0 step=... mode=RETRANSMIT
[C3Bus5:IoInput16] DEVICE_POLL_MISS result=-4 unit=1 miss=2 limit=3 state=SUSPECT_2
[C3Bus5:IoInput16] DEVICE_OFFLINE result=-4 unit=1 misses=3
```

前台命令失败与设备掉线必须分开：

```text
COMMAND_FAILED      = 本次动作失败
DEVICE_POLL_MISS    = 一次健康轮询失败
DEVICE_OFFLINE      = 连续健康轮询达到阈值
DEVICE_POLL_PREEMPTED = 后台帧由本机主动放弃，不是通信失败
```

这样使用者能够区分设备离线、命令不支持、设备忙、协议异常和本机队列拥塞。

## 18. 分阶段实施计划

### 第一阶段：职责下沉与 IO 专用调度

1. 在每个 RTU Bus 上建立静态轮询表和独立截止时间。
2. 后台轮询直接由 Bus 生成，不进入前台队列。
3. 保留现有前台命令队列和 urgent 机制。
4. 将 Workflow 的周期 `prvServiceIoRefresh()`停用或缩减为本地非 RTU 状态服务。
5. 普通设备引入 `UNKNOWN/ONLINE/SUSPECT/OFFLINE`和两次 miss 计数。
6. 增加带设备名的上线、丢帧、掉线、恢复日志。
7. Bus5 使用板载 GPIO 100ms、外部输入/输出各 100ms、错相 50ms和三次 miss 的专用策略。
8. 不增加 Mutex、不增加新任务、不修改具体业务动作语义。

### 第二阶段：可取消接收与安全重发

1. 增加前台命令到达时的 `preempt_requested`通知路径。
2. 将 RTU 后台接收改为短时间片检查，同时保留完整事务总超时。
3. 增加 PREEMPTED 结果、RX pause/flush/resume、nanoMODBUS 状态清理。
4. 为允许抢占的设备配置晚响应隔离窗口，并建立可抢占白名单。
5. 保存后台设备、步骤和游标；前台队列清空后完整重发当前步骤。

### 第三阶段：统一镜像提交

1. 为所有设备建立统一 Commit helper。
2. 将驱动解析结果先写 Bus 私有临时镜像。
3. C3Server 使用稳定快照和 generation/stale 信息。
4. 清理逐字段直接写公共镜像的路径。

### 第四阶段：处理长动作和运行监控

1. 审计各驱动最长 Bus 占用时间。
2. 将多设备 Bus 上的长同步动作拆为“启动 + 状态轮询”。
3. 增加轮询暂停时间、主动放弃次数、队列高水位和事务耗时监控。

## 19. 验收测试

### 19.1 周期与错相

1. 一个 Bus 挂 3 台设备，确认目标查询时刻约为 `0/200/400ms`错相。
2. 连续运行至少 10 分钟，确认每台设备平均周期约 3 秒，不因其他设备正常事务持续漂移。
3. 让其中一台设备每次超时，确认其他设备仍按自身截止时间获得调度。

### 19.2 在线状态

1. 已在线设备第一次健康轮询超时，仅进入 SUSPECT，对外仍保持可用。
2. 第二次连续健康轮询超时后进入 OFFLINE，约为最后成功响应后 6 秒加事务误差。
3. 两次失败之间成功一次，miss 计数清零。
4. OFFLINE 设备恢复响应后，无需复位即可进入 ONLINE。
5. 启动从未响应与已上线后掉线使用不同日志语义。

### 19.3 前台命令优先级

1. 后台轮询正在等待响应时到达 urgent 命令：在一个抢占检查时间片内返回 PREEMPTED，清理旧接收状态后执行 urgent。
2. urgent 执行期间轮询到期：命令完成后补做轮询，不计 miss。
3. 前台命令超时：调用者收到失败，但设备健康 miss 不增加。
4. 前台命令获得有效响应：设备可恢复 online。
5. 同一状态查询由前台命令完成时，验证镜像和下次轮询截止时间处理正确。
6. 被放弃的后台查询在前台队列清空后，从保存步骤完整重发，不继续使用旧帧缓存。
7. 构造旧后台响应晚到场景，确认它不会被误配给前台命令。

### 19.4 协议与镜像

1. Modbus FC03 设备和 F200 自有 QUERY 都通过统一 REFRESH 入口执行。
2. C3Server 读取 4208、4256、`0x10F2`、`0x10FA`等 RTU 设备状态区域时不触发串口事务。
3. 高并发读取状态寄存器时，不出现一半新、一半旧的设备镜像。
4. 通信失败后保留最后有效业务数据，同时 online/stale 正确变化。

### 19.5 压力与资源

1. 连续投递前台命令，确认队列不会被后台轮询占满。
2. 连续投递前台命令，确认后台可以暂停且不会累计 miss；停止投递后从保存步骤恢复。
3. 检查每个 Bus 任务栈高水位、命令队列高水位和最坏事务耗时。
4. 验证多设备 Bus 不存在驱动内部长期循环独占。
5. Bus5 验证板载 GPIO 每 100ms 更新、外部输入和输出回读各 100ms，并验证三次实际失败才判离线。

## 20. 风险和必须坚持的边界

1. **不能无清理地丢弃 RTU 帧。** 允许主动放弃只读后台查询，但必须返回 PREEMPTED、清空接收状态、隔离晚到旧响应并重新发送当前步骤。
2. **不能把未执行轮询算作丢帧。** 只有实际发送查询后未获得有效响应才计 miss。
3. **不能让后台轮询占用前台队列。** 否则仍会产生队列竞争和过期命令。
4. **不能让多个任务直接操作同一 UART。** 这会破坏单所有者模型。
5. **不能把所有协议硬编码成 FC03。** 状态刷新必须由设备驱动决定具体查询帧。
6. **不能忽略长同步动作。** 它会让同 Bus 所有设备的监控和命令全部停顿。
7. **不能只用 bitmask 日志。** 位图用于协议，设备名用于诊断。
8. **不能承诺严格 6.000 秒。** 实际时间包含轮询相位、事务超时和前台命令延迟；应以“连续两次实际健康轮询失败”为唯一判据。

## 21. 最终建议

建议批准该架构方向，但按以下修正版落地：

> 每个 RTU Bus 是物理通信唯一所有者和设备健康调度者；C3Server/Workflow 只提交前台命令。普通设备独立按 3 秒截止时间轮询，同 Bus 启动错相 200ms；前台命令到达时可主动放弃正在等待的只读后台帧，完成 RX 清理和旧响应隔离后优先执行，随后重发保存的后台步骤。只有实际健康轮询连续失败才改变在线状态，PREEMPTED 和未执行轮询均不计失败。Bus5 作为 IO 专用域，板载 GPIO 每 100ms 采样，外部输入和输出回读各 100ms、错相 50ms，连续 3 次实际失败才离线。该架构不适用于机器人 Modbus TCP Client。

这比“整轮轮询后等待 3 秒 + 共享队列 + 时间判离线”的方案更稳定、职责更清晰，也更符合当前 Coffee3Close 已存在的 Bus 单所有者结构。
