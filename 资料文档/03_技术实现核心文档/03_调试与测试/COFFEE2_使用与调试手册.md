# Coffee2 使用与调试手册

## 2026-08-12 Robot TCP 恢复调试补充

Robot 所有者任务永久重连，退避时间为 1/2/5/10/30 秒并封顶 30 秒。`ONLINE` 表示 TCP/Modbus 链路可用；`READY` 更严格，还要求上电、使能、运行或空闲有效，并且安全暂停、报警、碰撞、拖拽和恢复信号均为零。手动 Robot 命令只有在已连接、严格就绪、非 BUSY 且非 RECOVERING 时才允许进入队列。

Workflow Robot 动作在 BUSY/RECOVERING 期间保留 command ID 和 order epoch。重连后先检查命令/结果线圈，再进行任何启动清理。结果为 1 时必须写零并读回零；只有连续三次采样一致、目标命令和结果均为零、严格就绪且运行/空闲有效时，才允许最多一次安全重放。信号含义不明确时禁止自动重放；取消会终止恢复，120 秒恢复窗口到期则原命令失败。轮询间隔为 100 ms，但每笔 Modbus 事务使用 1000 ms Robot IO 超时。

每次动作前，FC15 仅清除 3121..3139 共 19 个线圈并读回确认；不清除 3120。链路丢失测试应关注 `ROBOT_READY_RISE/FALL`、`ROBOT_RECOVERY_RECONCILE`、`ROBOT_ACTION_REPLAYED`、`ROBOT_RECOVERY_COMPLETED` 和 `ROBOT_RECOVERY_EXPIRED` 日志。

## 1. 这份手册解决什么问题

Coffee2 的主控是下位机 Modbus TCP Server。上位机只负责连接、下发订单或维护命令、读取状态；Coffee2 负责把命令转换成 Robot TCP 或 RTU 总线命令，并用工作流和设备事件推进流程。

所有调试都遵循同一条闭环：

```text
Modbus TCP 客户端写寄存器
  -> Coffee2 Server 校验/接收
  -> 标准 Coffee2Command_t 命令队列
  -> Robot TCP 任务或 RTU Bus2~Bus5 任务
  -> 设备协议帧
  -> 设备完成/失败
  -> 每设备 EventGroup + 全局状态
  -> 0x1000 状态区、0x1100 监控区、USART1 日志
```

FC06/FC10 返回成功只表示命令被 Server 接收或进入队列，不等于机构动作已经完成。必须继续读状态并保存日志。

## 2. 上电前检查

1. 急停有效，机器人、落杯、落盖、糖浆、制冰和咖啡机处于可安全单步的状态。
2. USART1 接 USB-TTL/安卓屏日志输入，115200 8-N-1。Coffee2 不使用 USART6 做日志，也不创建 Bus1。
3. 主控默认静态地址 `192.168.5.10/24`，网关 `192.168.5.1`。
4. 上位机连接 `192.168.5.10:6001`，Modbus Unit ID 为 `1`。
5. Robot 目标为 `192.168.5.100:502`，Unit ID 为 `1`。
6. 每个 RTU 从站的波特率、地址和总线必须符合下表；RS232/RS485 是电气选择，不是软件总线类型。

## 3. 通讯拓扑和检查点

| 软件任务/总线 | 角色 | STM32 UART | 设备 | Modbus 从站 | 检查方式 |
|---|---|---|---|---:|---|
| C2Log | 日志发送 | USART1 | 安卓屏/串口终端 | 无 | 看启动和状态变化日志 |
| C2Server | Modbus TCP Server | Ethernet | 上位机/调试客户端 | Unit 1 | 监听 6001；0、1、2 个连接测试 |
| C2Robot | Modbus TCP Client | Ethernet | Robot | Unit 1 | 读写 Robot 协议线圈并看重连日志 |
| Bus2 | Modbus RTU Master | USART2 | 咖啡机 | 1 | 单机制作/清洗/取消 |
| Bus3 | Modbus RTU Master | USART3 | 落杯机、糖浆机、落盖机 | 1、2、3 | 分别落杯、出糖浆、落盖 |
| Bus4 | Modbus RTU Master | UART4 | 制冰机、称重模块、电能表 | 1、2、3 | 去皮/读重、制冰、读表 |
| Bus5 | Modbus RTU Master | UART5 | 输入 IO、输出 IO | 1、2 | 读输入、写输出 |

Bus3、Bus4、Bus5 是“一路串口上的小型调度器”。设备 ID、RTU 从站地址和串口由不可变绑定表决定，命令中不重复携带地址，避免上位机绕过绑定表误控设备。

## 4. 上电日志验收

日志格式为：

```text
[Level][Task][Module] EVENT result=... field=value...
```

先保存从 `POWER_ON` 到 `STARTUP_COMPLETE` 的完整日志。正常情况下应能看到：串口重新初始化、网络栈就绪、任务创建、Server 监听、Robot 连接尝试、Bus2~Bus5 启动和工作流启动。网络或设备状态只在变化时输出一次；例如 Robot 离线不会每 5 秒重复刷屏，恢复时再输出一次 `ONLINE`。

重点日志：

```text
[INFO][C2Server][ModbusTcp] SERVER_LISTENING result=0 port=6001
[INFO][C2Server][ModbusTcp] SERVER_CLIENT_CONNECTED result=0 slot=0
[WARNING][C2Server][ModbusTcp] SERVER_CLIENT_DISCONNECTED result=-5 slot=0
[INFO][C2Robot][RobotTcp] ROBOT_CONNECT_BEGIN result=0 attempt=1
[WARNING][C2Robot][RobotTcp] ROBOT_CONNECT_FAILED result=-5 native_error=...
[INFO][C2Robot][RobotTcp] ROBOT_RETRY_SCHEDULED result=0 delay_ms=1000
```

若日志停止，先读取监控区 `0x1138..0x113F` 的任务创建/网络就绪掩码，再看 `0x1100..0x117F` 的堆、设备事件和两个客户端槽。

## 5. Modbus TCP Server 调试方法

### 5.1 客户端槽

Server 固定维护两个可复用槽位。第一个连接可作为实际通讯，第二个连接可作为调试；任意一个槽连接成功即 Server Online。第三个连接会被拒绝。任意槽断开只影响该槽；网络链路或 IPv4 失效时会关闭监听器和两个槽，恢复后重建。

建议先用一个客户端验证业务，再用第二个客户端只读监控。测试项目：

1. 连接一个客户端，读 `0x1100` 开始的监控区，确认 `active_clients=1`。
2. 连接第二个客户端，确认两个槽均为 connected。
3. 尝试第三个连接，确认客户端断开且日志出现 `SERVER_CLIENT_REJECTED`。
4. 断开 slot0，确认 slot1 仍能读写；再重连 slot0，确认槽资源复用。

### 5.2 功能码

- FC03：读保持寄存器，读命令回显区、状态区或监控区。
- FC04：当前回调也映射到只读数据模型，可按客户端工具使用。
- FC06：写一个寄存器，适合单个维护命令。
- FC10：连续写寄存器，适合完整订单参数一次提交。

建议使用 FC10 写入订单参数 `0x0000..0x0006`，再用 FC06 写 `0x0007=1` 表示订单存在，最后写 `0x0008=1` 表示上位机核对通过。订单被接受后会复制到状态区并进入工作流；忙时会记录 `ORDER_REJECTED_BUSY`。

### 5.3 订单和状态寄存器

| 地址 | 写入含义 |
|---:|---|
| `0x0000` | 订单号（建议每次使用不重复的 16 位值） |
| `0x0001` | 咖啡类型 |
| `0x0002` | 是否加盖 |
| `0x0003`/`0x0004` | 糖浆 1/2 参数 |
| `0x0005` | 冰量 |
| `0x0006` | 打印请求 |
| `0x0007=1` | 有新订单 |
| `0x0008=1` | 订单已核对 |
| `0x0009` | 储存取杯选项 |
| `0x000A` | 在线出餐选项 |
| `0x000B` | 取杯确认 |
| `0x000C` | 现场出餐选项 |
| `0x0022=1` | 请求取消当前订单 |

| 地址 | 读取含义 |
|---:|---|
| `0x1008` | 制作状态：0 空闲、1 制作中、2 完成、3 失败 |
| `0x1018` | 当前工作流步骤 |
| `0x1029` | 最近工作流错误 |
| `0x1100..0x117F` | 调试监控：任务、堆、设备事件、命令 ID、Server 槽、RTU 状态 |

协议中被划掉或尚未有确定硬件映射的地址不应自行试写；当前实现会拒绝、忽略或记录 `UNSUPPORTED`，详见工程报告的“仍不能安全完成的项目”。

## 6. 各设备单机调试

每次只打开一个物理动作，确认急停可立即切断。写入后按设备状态区和 `0x1100` 监控区轮询，同时保存 USART1 日志。

### 6.1 Robot TCP

Robot 是 Coffee2 的 TCP Client，不经过 RTU。先确认日志有 `ROBOT_CONNECTED` 或明确的失败/重连记录。维护命令：

- `0x0030=0..7`：启动、停止、暂停、使能、下使能、清报警、进入/退出拖拽。
- `0x0031`：写位置枚举，例如 `0` HOME、`1` 热杯、`2` 冷杯、`3/4` 落盖位、`5/6` 咖啡位、`7` 制冰位、`8` 打印位、`9/10` 出餐位、`0x11..0x14` 出餐储位、`0x15..0x20` 储存位。

基础控制线圈使用 0→1 的上升沿；动作线圈为 Robot 协议的 `3120..3138`，完成线圈为 `3100..3118`。每个位置动作下发前，Coffee2 通过 FC15 清除 `3121..3139` 共 19 个动作命令线圈并读回全零；动作结果为 1 时写零并读回零后才确认完成。3120 不属于清除范围；不要把“写成功”当作“机械臂到位”。

### 6.2 Bus2 咖啡机 RTU

咖啡机使用 USART2、地址 1。单机测试：

1. 写 `0x0040=饮品编号(0..0x28)`，观察是否被接受。
2. 读取 `0x1040` 对应咖啡状态和设备事件；等待 `COMMAND_DONE` 或 `COMMAND_FAILED`。
3. 写 `0x0042=1` 或 `2` 测试冲洗；当前不发送资料中与 X 系列冲突的清洗值。
4. 写 `0x0047=1` 测试取消。

确认日志中出现 RTU 请求结果、从站地址 1、超时/恢复状态。RTU 不使用 TCP 重连机制；故障通过超时、通信故障和下一次成功事务恢复。

### 6.3 Bus3 落杯、糖浆、落盖

三台设备在 USART3 上共享 RTU，总线地址必须严格区分：落杯=1、糖浆=2、落盖=3。

- 落杯：`0x0050=0` 测冰杯，`0x0050=1` 测热杯。
- 落盖：`0x0050=2` 测冰盖，`0x0050=3` 测热盖。
- 糖浆：先写 `0x0061=出液时间`，再写 `0x0060=0..3` 选择通道 A～D；`0x0062` 设置剩余时间，`0x0063=1` 测清洗。

每个动作均应在 `0x1050` 或 `0x1060` 相应状态和 `0x1100` 设备事件中确认地址正确。不要同时驱动同一总线的两个动作，避免人为制造 RTU 帧竞争。

### 6.4 Bus4 制冰、称重、电能表

制冰=地址1，称重=地址2，电能表=地址3，均在 UART4。

- 称重：先执行去皮/清零相关维护命令，连续读三次重量，确认单位和小数位被归一到 0.1 g。
- 制冰—称重联动：写 `0x0071=目标重量(0.1 g)`，再写 `0x0070=1`。程序先去皮、取中值、按 `t=18*weight(g)-300` 估算阀门时间，限制在 200～2000 ms，关阀后等待 1000 ms，再称重并最多补偿两次。该斜率和截距只是首轮标定值，量产前必须重新拟合。
- 电能表：执行刷新/读表命令，确认地址3通讯成功；不要用电能表的读数判断制冰动作完成。

### 6.5 Bus5 输入 IO、输出 IO

输入 IO=地址1，输出 IO=地址2，均在 UART5。工作流会周期提交刷新命令，并把 GPIO 和 RTU 镜像合并到全局 IO 结构；调试时读取 `0x1080` 附近状态和 `0x1100` 设备事件，确认输入变化、输出写入和通信故障。

GPIO 输入/输出属于 MCU 本地资源，不经过 RTU；IO 模块输入/输出才使用 Bus5。从软件视角二者统一进入全局 IO 镜像，但物理故障排查必须区分“GPIO 采样”与“Bus5 从站响应”。

## 7. 完整订单调试

推荐顺序：Robot HOME → 落杯 → Robot 到咖啡位 → 咖啡制作 → 制冰/称重（需要时）→ 糖浆 → 取盖/落盖/压盖 → 打印请求 → 出餐或储存。每一步都必须有一个命令 ID、一个 `WORKFLOW_STEP_START` 和一个终态日志。发生异常时工作流进入失败/取消分支，关闭制冰阀并向咖啡机、Robot 发送取消。

第一次整单使用空杯、最小冰量和可人工介入的位置。确认 `0x1008` 的状态变化顺序为 1→2；任何异常为 3，并保存从 `ORDER_ACCEPTED` 到 `ORDER_COMPLETED/ORDER_FAILED` 的完整日志。

## 8. 取消订单和新订单的安全规则

当前每台设备有独立 EventGroup，命令有全局递增 `ulCommandId`，工作流等待时会比较设备状态中的 `ulLastCommandId`，因此一个已经结束的旧命令通常不会被当前等待直接接受。`ulOrderId` 也随命令传递，便于日志追踪。

但当前 `vCoffee2DeviceCommandCompleted()` 在收到完成回调时没有再次校验“回调命令是否仍是该设备当前命令”，EventGroup 只保存位，不保存订单号。因此异步设备在取消后晚到的完成事件，仍可能短暂置位当前设备的 DONE/FAILED 位。它不会直接造成内存越界或 HardFault，但如果底层任务把晚到结果错误地当成新命令结果，可能导致错误推进、错误报警或错误放行。

现场必须执行以下规则：

1. 取消后等待工作流进入 `CANCELING`，读取所有设备 `BUSY=0`，再提交下一单。
2. 新订单使用新的订单号；不要复用刚取消订单号。
3. 看到 `CANCEL_BARRIER_DONE` 之前，不进行出餐、落盖或再次制冰。
4. 若出现旧命令完成日志带着旧 `order`，保存完整日志，不继续连发新命令。

后续建议的代码加固是：命令增加订单代次/epoch；设备开始时保存 `ulCommandId+ulOrderId`；完成时只接受与当前值完全相同的回调；取消流程等待每个已发命令的取消终态并清理路线队列；EventGroup 只做唤醒，终态从带命令 ID 的结果记录读取。该加固完成前，取消后“等待总线和执行机构静止”是必要的安全屏障。

## 9. 问题定位优先级

1. 先看 USART1 是否有 `TASK_RUNNING`、监听、连接或串口初始化日志。
2. 再读 `0x1100..0x117F`：任务掩码、最小堆、设备事件、命令 ID、Client 槽。
3. TCP 问题看 Server/Robot 的 connect、disconnect、retry；RTU 问题看 bus、unit、timeout、恢复。
4. 有命令无完成：检查目标从站地址、设备协议帧、物理线和波特率。
5. 有完成但工作流不推进：比较日志中的 `command_id`、`order`、`step`，优先排查取消后的陈旧事件。
6. 出现 HardFault：保留崩溃日志、最近一次 `0x1100` 监控读数和最后 100 行 USART1 日志；不要先清除现场状态。
