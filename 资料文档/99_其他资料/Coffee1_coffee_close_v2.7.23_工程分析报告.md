# Coffee1 `coffee_close_v2.7.23` 工程分析报告

> 基线位置：`C:\Users\13193\Documents\工作资料\coffee1\coffee_close_v2.7.23\coffee_close_v2.7.23`  
> 报告用途：作为 Coffee2 协议、设备行为和历史业务流程的追溯基线  
> 评估原则：以旧工程源码和构建 map 为主，说明文档只作辅助，不把历史实现直接等同于 Coffee2 需求

## 1. 工程定位

Coffee1 是一套基于 STM32F407、FreeRTOS 和 LwIP 的咖啡售卖机下位机固件。其主要职责是：

- 通过 Modbus TCP 接收上位机订单和人工调试命令；
- 控制机器人、咖啡机、制冰机、称重模块、落杯/落盖、糖浆/果乳和 IO 模块；
- 按机型和订单参数组织制作顺序；
- 向上位机反馈设备状态、步骤、故障和订单结果；
- 支持历史上的开放式、封闭式 v2.0/v2.1、店中店 v3.0 等多种机型分支。

Coffee1 的价值主要在于它沉淀了较完整的设备协议、边缘业务和现场经验；其局限在于这些知识大量聚集在中心状态机、全局变量和直接驱动调用中，难以安全扩展。

## 2. 硬件与基础软件配置

### 2.1 MCU 与时钟

| 项目 | 配置 |
| --- | --- |
| MCU 系列 | STM32F407，Cortex-M4F |
| 主频 | 168 MHz |
| 片上资源 | 典型 512 KiB Flash、128 KiB SRAM、64 KiB CCM（以具体料号为准） |
| 外设 | Ethernet RMII、多个 UART/USART、GPIO、定时器等 |

### 2.2 软件技术栈

| 层次 | 技术/实现 |
| --- | --- |
| 编译与工程 | Keil MDK、ARM Compiler V5 |
| MCU 驱动 | STM32 HAL / CubeMX 生成框架 |
| 实时操作系统 | FreeRTOS |
| 网络协议 | LwIP raw API，`NO_SYS=1`、`LWIP_NETCONN=0`、`LWIP_SOCKET=0` |
| 上位机接口 | 自定义 Modbus TCP Server，端口 6001 |
| 机器人接口 | Modbus TCP Client，默认目标 `192.168.5.1:502` |
| 串口设备 | RS232/RS485，自定义设备协议与 Modbus RTU 混合 |
| 业务实现 | 轮询式集中状态机、全局订单/设备状态、定时/计数等待 |

### 2.3 网络参数

- 控制器静态地址：`192.168.5.10`
- 子网掩码：`255.255.255.0`
- 网关：`192.168.5.1`
- 上位机连接端口：`6001`
- 机器人地址：`192.168.5.1:502`

地址重叠使用网关与机器人同为 `192.168.5.1` 在同网段内技术上可行，因为同网段通信不经过网关；但生产网络配置应明确记录这一点，避免维护人员误判。

## 3. RTOS 任务模型

Coffee1 的核心任务较少，业务主要集中在 Control 任务中。

| 任务 | 栈（words） | 优先级 | 主要职责 |
| --- | ---: | ---: | --- |
| Log | 256 | +5 | 调试日志输出 |
| Net | 1536 | +4 | LwIP 轮询、TCP 收发和网络状态 |
| Control | 1536 | +3 | 订单解析、设备调度和主业务状态机 |
| LED | 256 | +1 | 指示灯和基础状态显示 |

这种设计在设备数量有限时容易建立，但随着机型、设备和异常分支增加，Control 任务会成为职责和实时负载集中点。网络采用 LwIP raw API 和 `NO_SYS=1`，实际网络栈推进依赖应用主动轮询，和 Coffee2 的 FreeRTOS + LwIP Socket API 模型存在根本差异。

## 4. 程序架构

### 4.1 主要模块

| 模块 | 作用 | 主要特征 |
| --- | --- | --- |
| `ControlFlow/control_flow.c` | 主业务状态机 | 约 7,000 行，约 89 个业务状态，多机型分支集中 |
| `modbus/order.*` | 上位机订单寄存器模型 | 通过结构体/位域映射订单和状态 |
| `modbus/coffee.*` 等 | 设备访问 | 设备协议、状态解析、阻塞等待混合 |
| `Core/Src/usart.c` | 串口底层 | 存在轮询/阻塞式调用和 HAL 直接访问 |
| 网络相关模块 | 上位机 Server、机器人 Client | raw API 轮询与全局连接状态 |

### 4.2 核心编程思想

Coffee1 采用“超级循环/任务内轮询状态机”思路：

1. 上位机写入寄存器形成订单；
2. Control 任务读取全局订单和设备状态；
3. 依据当前状态枚举执行一个动作或等待条件；
4. 动作完成后切换到下一枚举状态；
5. 异常时跳到回收、取消或复位分支；
6. 通过全局寄存器把进度和结果暴露给上位机。

其优势是运行路径直观、现场人员可按状态号定位；不足是状态转移、设备驱动、协议变量和机型差异互相耦合，新增一个设备或顺序变化容易触及大量分支。

## 5. 上下位机通信协议

Coffee1 是《咖啡售卖机下位机-通信协议.docx》的原始实现基线。协议覆盖：

- 订单参数与制作启动；
- 热/冷饮和杯型；
- 咖啡配方；
- 糖浆 1-6、果乳 1-6；
- 打印、落盖、储杯、出餐；
- 设备状态、故障和人工调试命令；
- 软件版本、升级和部分维护寄存器。

订单接收语义的关键点是：上位机先写配方和控制字段，再通过订单有效/制作信号触发执行；下位机在执行期间维护状态与结果。协议字段必须结合源码实际读写位置判断，不能只依据表格中的文字说明。

Coffee2 继承该协议的地址空间和核心语义，但不能据此推断所有历史字段都继续有效。例如 Coffee1 支持糖浆 1-6，Coffee2 当前业务仅执行 1-4。

## 6. 业务模式

### 6.1 单机设备调试模式

Coffee1 通过上位机人工控制寄存器或本地调试分支，允许绕过完整订单，对单台设备执行动作。典型调试对象包括：

- 机器人回零、移动到工位、取放杯、取放盖、出餐和储位动作；
- 咖啡机状态读取、配方制作、取消；
- 落杯器、落盖器动作和状态读取；
- 糖浆/果乳单通道出料；
- 制冰阀、称重去皮和重量读取；
- IO 输入读取、输出点吸合/释放；
- 电表或其他 RTU 设备状态读取。

旧工程中人工调试与订单业务共享大量全局设备状态和底层调用。调试时必须确保订单任务未同时控制同一设备，否则可能出现命令覆盖或状态误判。

### 6.2 订单接收执行模式

典型路径如下：

1. 校验订单字段、设备状态和机型条件；
2. 机器人及关键设备前检；
3. 根据杯型取杯并执行落杯；
4. 冷饮分支通常先执行制冰和称重复核；
5. 机器人将杯移动到咖啡机相关工位；
6. 根据配方执行糖浆/果乳；
7. 执行咖啡制作并等待完成；
8. 可选等待上位机打印；
9. 可选落盖、取盖、压盖；
10. 根据机型将成品送入储杯位或出餐口；
11. 更新订单完成/失败状态并回到待机。

注意：上述是 Coffee1 的概括性主线。不同机型和饮品存在顺序差异。Coffee2 已明确调整为“先咖啡，再制冰，再糖浆”的新顺序，因此不能把 Coffee1 顺序视为新设备的等价需求。

### 6.3 储杯和出餐模式

Coffee1 支持成品暂存、储位取杯和直接出餐等历史分支。状态机需要同时维护目标储位、储位占用、机器人取放动作、出餐口可用性和异常回收。该能力比 Coffee2 当前主线覆盖更广，是迁移时应重点核对的历史业务资产。

## 7. 单设备业务逻辑

### 7.1 机器人

- 通过 Modbus TCP 控制，使用命令线圈/结果线圈完成动作握手。
- 包含上电、启动、回零、各工位移动、取放杯盖、储位和出餐等动作。
- 业务状态机通常写入动作命令，再轮询结果和超时。
- 断线、迟到结果和人工命令与订单命令的协调主要依靠全局状态和分支约定，缺少 Coffee2 的事务对象和订单代际隔离。

### 7.2 咖啡机

- 使用串口设备协议读取状态和下发制作命令。
- 制作前检查在线、空闲和告警条件；按配方启动；轮询完成/失败。
- 存在阻塞式 UART 调用和业务层直接等待，可能拖慢 Control 任务其他设备的调度。

### 7.3 落杯与落盖

- 通过共享 RS485 上的独立从站执行单次动作。
- 动作前后读取状态，结合超时或传感器判定成功。
- 设备卡滞、缺杯/缺盖和通信失败进入异常流程。

### 7.4 糖浆与果乳

- 历史协议覆盖 1-6 路糖浆和 1-6 路果乳。
- 按订单量转换为设备动作或运行时间，各通道依次执行。
- 多配方、多机型逻辑散布在主状态机内，具备较强历史兼容性，但参数语义和量产标定不易集中维护。

### 7.5 制冰与称重

- 冷饮分支打开制冰阀/启动制冰动作，并利用称重模块读取实际重量。
- 状态机结合目标重量、实际重量、超时和补偿逻辑决定继续、完成或异常。
- 称重去皮、稳定等待和采样策略与业务状态耦合，后续迁移应以设备实测为准。

### 7.6 IO 模块与电表

- IO 模块用于读取传感器和控制执行器，部分状态直接影响流程准入和异常判断。
- 电表用于能源/运行数据采集，通常不直接决定单杯制作主链路，但关系维护与统计。

## 8. 异常与恢复逻辑

Coffee1 包含较丰富的现场异常分支，包括设备离线、动作超时、缺料、机器人失败、制冰/称重异常、杯盖异常、订单取消和异常回收。常见处理方式为：

- 设置上位机故障/结果寄存器；
- 跳转到指定取消或回收状态；
- 停止当前设备动作；
- 尝试机器人复位或把杯送到异常位置；
- 清理部分全局订单标志并回到待机。

其风险在于异常清理逻辑分散。若某个分支遗漏状态清零或设备停止，就可能影响下一订单。由于缺少统一的命令身份和取消屏障，迟到的设备完成信号也可能与新流程发生语义混淆。

## 9. 构建与内存质量

现有 Coffee1 map 证据显示：

| 项目 | 数值 |
| --- | ---: |
| Code | 137,672 B |
| RO-data | 5,216 B |
| RW-data | 1,424 B |
| ZI-data | 126,816 B |
| SRAM 使用 | 128,240 / 131,072 B |
| SRAM 余量 | 2,832 B |
| 应用链接基址 | `0x0800C000` |
| 构建诊断 | 0 error、22 warnings |

SRAM 余量约 2.2%，已经非常紧张。新增队列、网络缓冲或任务栈容易造成链接失败或运行期栈/堆冲突。22 个警告中包含隐式声明、非 void 函数缺少 return、不可达代码等类型，这些警告不应视为无害；它们可能导致 ABI 不一致、未定义返回值和失效错误处理。

`0x0800C000` 的链接基址说明 Coffee1 应用预期位于 Bootloader 后方。这是 Coffee1 的部署约束，不应直接复制到 Coffee2，除非新的 Bootloader 和 Flash 分区已经确认。

## 10. 工程优点

- 业务覆盖广，沉淀了多机型、多设备和现场边缘场景。
- 上下位机协议和设备协议已经过历史项目使用，具有重要参考价值。
- 集中状态机便于按状态号追踪单条历史流程。
- 已包含取消、异常回收、储杯/出餐、糖浆/果乳和制冰称重等复杂能力。
- Bootloader 偏移布局和历史发布流程可为 Coffee2 部署方案提供线索。

## 11. 工程问题

- `control_flow.c` 体量过大，状态、协议、设备和机型分支高度耦合。
- 阻塞 UART 和手工等待循环降低实时响应，并放大单设备故障影响。
- 大量全局状态缺少明确所有权，不利于并发安全和测试隔离。
- 设备访问没有统一命令对象、队列、代际和取消屏障。
- 网络 raw API 推进和业务轮询共同依赖少数任务，扩展性受限。
- 内存余量过低，增加功能风险高。
- 构建警告未清零，存在明确的 C 语言正确性风险。
- 自动化测试、故障注入和资源水位证据不足。

## 12. 对 Coffee2 的继承建议

应继承：

- 上位机寄存器地址、字段语义和握手时序中经确认仍有效的部分；
- 各硬件设备协议帧、状态码、动作条件和现场超时经验；
- 历史机型中仍属于 Coffee2 产品需求的业务分支；
- 异常场景、回收策略和生产维护知识。

不应原样继承：

- 中心化超大状态机；
- 业务层直接占用 UART/TCP；
- 阻塞式等待和无界轮询；
- 无所有权的全局状态；
- 依靠清全局标志解决取消和新订单隔离；
- 未经确认的机型、电气接线、设备数量和制作顺序。

## 13. 作为后续佐证时的使用规则

1. Coffee1 是“历史行为证据”，不是 Coffee2 的最终产品需求。
2. 同一行为若与 Coffee2 V2.0 电气图或新业务定义冲突，应提出差异项，由产品/电气/软件共同确认。
3. 设备协议字段可优先复用，但波特率、站号、物理接口和接线必须按 Coffee2 实机重新验证。
4. 迁移业务时应把每个旧状态转换为“前置条件、命令、完成条件、超时、取消、安全状态”，而不是复制状态机代码。
5. 所有历史常量都应重新标定或追溯来源，尤其是时间、重量、流量和动作超时。
