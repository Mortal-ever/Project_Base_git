# 咖啡机与工控机通信数据格式及校验和说明

## 一、通信基本参数

咖啡机与工控机之间采用串口通信，基本参数如下：

| 项目           | 参数                |
| -------------- | ------------------- |
| 物理接口       | RS-232              |
| 波特率         | 115200 bit/s        |
| 通信方式       | 主从问答式通信      |
| 主设备         | 工控机              |
| 从设备         | 咖啡机              |
| 数据包长度     | 固定26字节          |
| 包头           | `0x7E`              |
| 包尾           | `0x7E`              |
| 多字节数据顺序 | 小端模式            |
| 状态查询周期   | 建议每200ms查询一次 |

工控机负责主动发送查询、制作饮品、取消应用等指令；咖啡机收到指令后返回当前机器状态和应用状态。

咖啡机不会主动向工控机上报数据，因此工控机需要通过周期查询获取咖啡机的实时状态。

------

## 二、通信数据帧格式

每个通信数据包固定为26字节，字节位置为 `0～25`。

| 字节位置 | 长度   | 字段名称   | 数据方向      | 说明                         |
| -------- | ------ | ---------- | ------------- | ---------------------------- |
| 0        | 1 Byte | 包头       | 双向          | 固定为 `0x7E`                |
| 1        | 1 Byte | 包长度     | 双向          | 固定为 `0x1A`，十进制为26    |
| 2～9     | 8 Byte | 警告信息   | 咖啡机→工控机 | 64位警告位图，小端模式       |
| 10～17   | 8 Byte | 故障信息   | 咖啡机→工控机 | 64位故障位图，小端模式       |
| 18       | 1 Byte | 咖啡机状态 | 咖啡机→工控机 | 待机、空闲、运行、警告或故障 |
| 19       | 1 Byte | 通信指令   | 工控机→咖啡机 | 查询、制作、取消等指令       |
| 20       | 1 Byte | 应用状态   | 咖啡机→工控机 | 运行、成功、失败、等待等     |
| 21       | 1 Byte | 饮品编号   | 工控机→咖啡机 | 指定需要制作的饮品           |
| 22       | 1 Byte | 应用编号   | 咖啡机→工控机 | 表示当前正在运行的应用       |
| 23       | 1 Byte | 预留字段   | 双向          | 当前固定填写 `0x00`          |
| 24       | 1 Byte | 校验和     | 双向          | 字节1～23的8位累加和         |
| 25       | 1 Byte | 包尾       | 双向          | 固定为 `0x7E`                |

完整数据帧可以表示为：

```text
7E 1A
[警告信息：8字节]
[故障信息：8字节]
[咖啡机状态：1字节]
[通信指令：1字节]
[应用状态：1字节]
[饮品编号：1字节]
[应用编号：1字节]
[预留字段：1字节]
[校验和：1字节]
7E
```

未使用的字段必须填写 `0x00`，不能省略。无论当前指令是否使用全部字段，数据包长度始终保持26字节。

------

## 三、主要字段说明

### 3.1 警告信息

警告信息占8字节，对应一个64位无符号位图。

数据采用小端模式，即低字节先发送。

例如，警告值为：

```text
0x0000000000000001
```

实际发送的8字节为：

```text
01 00 00 00 00 00 00 00
```

警告值为：

```text
0x0000000000000100
```

实际发送的8字节为：

```text
00 01 00 00 00 00 00 00
```

不同警告位可以同时置位。例如存在多个警告时，将相应警告值进行按位或运算后发送。

### 3.2 故障信息

故障信息同样占8字节，为64位故障位图，采用小端模式。

不存在故障时，8字节全部填写 `0x00`。

### 3.3 咖啡机状态

| 状态值 | 状态名称 | 是否接受饮品制作指令 |
| ------ | -------- | -------------------- |
| `0x01` | 待机状态 | 否                   |
| `0x02` | 空闲状态 | 是                   |
| `0x03` | 运行状态 | 否                   |
| `0x04` | 警告状态 | 否                   |
| `0x05` | 故障状态 | 否                   |

工控机只有在咖啡机状态为 `0x02` 时，才能发送饮品制作指令。

### 3.4 主要通信指令

| 指令值 | 指令名称     |
| ------ | ------------ |
| `0x01` | 饮品制作指令 |
| `0x10` | 查询状态指令 |
| `0x11` | 取消应用指令 |

咖啡机回复数据时，通信指令字段通常保持为当前正在响应的指令值。

例如：

- 回复查询状态时填写 `0x10`
- 回复饮品制作指令时填写 `0x01`
- 回复取消应用指令时填写 `0x11`

### 3.5 应用状态

| 状态值 | 状态名称     | 说明                                   |
| ------ | ------------ | -------------------------------------- |
| `0x00` | 应用无状态   | 当前没有运行应用                       |
| `0x01` | 应用运行状态 | 应用正在执行                           |
| `0x02` | 应用阶段成功 | 当前阶段执行成功                       |
| `0x03` | 应用完全成功 | 整个应用执行完成                       |
| `0x04` | 应用失败     | 应用执行失败或指令被拒绝               |
| `0x05` | 应用等待状态 | 咖啡机已收到指令，正在判断是否可以执行 |

------

# 四、校验和算法说明

## 4.1 校验类型

本协议使用的校验方式不是CRC校验，也不是CRC-8、CRC-16、异或校验或补码校验。

本协议使用的是：

> 8位累加和校验，即 Additive Checksum。

它属于协议自定义的简单校验和算法。

计算过程中不需要配置：

- CRC多项式
- CRC初始值
- 输入数据反转
- 输出数据反转
- 结果异或值
- STM32 CRC硬件外设

因此，STM32程序中直接使用普通加法计算即可。

------

## 4.2 校验范围

参与校验和计算的字节范围为：

```text
frame[1] ～ frame[23]
```

即从包长度字段开始，一直累加到预留字段。

| 字段                     | 是否参与校验 |
| ------------------------ | ------------ |
| 包头 `frame[0]`          | 否           |
| 包长度 `frame[1]`        | 是           |
| 警告信息 `frame[2～9]`   | 是           |
| 故障信息 `frame[10～17]` | 是           |
| 咖啡机状态 `frame[18]`   | 是           |
| 通信指令 `frame[19]`     | 是           |
| 应用状态 `frame[20]`     | 是           |
| 饮品编号 `frame[21]`     | 是           |
| 应用编号 `frame[22]`     | 是           |
| 预留字段 `frame[23]`     | 是           |
| 校验和 `frame[24]`       | 否           |
| 包尾 `frame[25]`         | 否           |

需要特别注意：

1. 包长度 `0x1A` 必须参与校验。
2. 包头 `0x7E` 不参与校验。
3. 包尾 `0x7E` 不参与校验。
4. 校验和字段本身不参与校验。
5. 值为 `0x00` 的字段虽然不影响结果，但仍属于校验范围。
6. 警告和故障字段必须按照实际发送的原始字节参与累加。

------

## 4.3 校验公式

校验和计算公式如下：

[
Checksum =
\left(
\sum_{i=1}^{23} Frame[i]
\right)
& 0xFF
]

也可以表示为：

```text
Checksum =
(
    包长度
  + 警告信息的8个字节
  + 故障信息的8个字节
  + 咖啡机状态
  + 通信指令
  + 应用状态
  + 饮品编号
  + 应用编号
  + 预留字段
) & 0xFF
```

`& 0xFF` 表示只保留累加结果的最低8位，高位直接丢弃。

例如，所有字节累加结果为：

```text
0x01A7
```

最终校验和应当填写：

```text
0xA7
```

本协议不对累加结果取反，也不计算二进制补码。

------

## 4.4 查询状态报文校验示例

工控机发送查询状态指令：

```text
7E 1A 00 00 00 00 00 00 00 00
      00 00 00 00 00 00 00 00
      00 10 00 00 00 00 2A 7E
```

各字段为：

| 字段       | 数值   |
| ---------- | ------ |
| 包长度     | `0x1A` |
| 咖啡机状态 | `0x00` |
| 通信指令   | `0x10` |
| 应用状态   | `0x00` |
| 饮品编号   | `0x00` |
| 应用编号   | `0x00` |
| 预留字段   | `0x00` |

警告和故障字段全部为零，因此校验和计算如下：

```text
0x1A + 0x10 = 0x2A
```

最终数据包中的校验和为：

```text
0x2A
```

与协议示例一致。

------

## 4.5 空闲状态回复校验示例

咖啡机回复空闲状态：

```text
7E 1A 00 00 00 00 00 00 00 00
      00 00 00 00 00 00 00 00
      02 10 00 00 00 00 2C 7E
```

非零字段为：

| 字段       | 数值   |
| ---------- | ------ |
| 包长度     | `0x1A` |
| 咖啡机状态 | `0x02` |
| 通信指令   | `0x10` |

校验和计算如下：

```text
0x1A + 0x02 + 0x10 = 0x2C
```

因此校验和为：

```text
0x2C
```

与协议示例一致。

------

## 4.6 饮品制作请求校验示例

工控机发送饮品制作指令，饮品编号为 `0x01`：

```text
7E 1A 00 00 00 00 00 00 00 00
      00 00 00 00 00 00 00 00
      00 01 00 01 00 00 1C 7E
```

非零字段为：

| 字段     | 数值   |
| -------- | ------ |
| 包长度   | `0x1A` |
| 通信指令 | `0x01` |
| 饮品编号 | `0x01` |

校验和计算如下：

```text
0x1A + 0x01 + 0x01 = 0x1C
```

因此校验和为：

```text
0x1C
```

与协议示例一致。

## 4.7 制作中状态回复校验示例

咖啡机正在制作饮品时回复：

```text
7E 1A 00 00 00 00 00 00 00 00
      00 00 00 00 00 00 00 00
      03 10 01 00 01 00 2F 7E
```

非零字段为：

| 字段       | 数值   |
| ---------- | ------ |
| 包长度     | `0x1A` |
| 咖啡机状态 | `0x03` |
| 通信指令   | `0x10` |
| 应用状态   | `0x01` |
| 应用编号   | `0x01` |

```text
0x1A + 0x03 + 0x10 + 0x01 + 0x01

```

```text
0x2F
```

# 五、STM32校验和实现

## 5.1 数据帧索引定义

```c
#define COFFEE_FRAME_LENGTH          26U

#define COFFEE_FRAME_HEAD_INDEX      0U
#define COFFEE_FRAME_LENGTH_INDEX    1U
#define COFFEE_FRAME_STATUS_INDEX    18U
#define COFFEE_FRAME_COMMAND_INDEX   19U
#define COFFEE_FRAME_APP_STATE_INDEX 20U
#define COFFEE_FRAME_DRINK_INDEX     21U
#define COFFEE_FRAME_APP_INDEX       22U
#define COFFEE_FRAME_RESERVED_INDEX  23U
#define COFFEE_FRAME_CHECKSUM_INDEX  24U
#define COFFEE_FRAME_TAIL_INDEX      25U

#define COFFEE_FRAME_HEAD_VALUE      0x7EU
#define COFFEE_FRAME_LENGTH_VALUE    0x1AU
#define COFFEE_FRAME_TAIL_VALUE      0x7EU
```

## 5.2 校验和计算函数

```c
#include <stdint.h>

uint8_t Coffee_CalculateChecksum(const uint8_t *frame)
{
    uint32_t sum = 0U;
    uint8_t index;

    if (frame == NULL)
    {
        return 0U;
    }

    /*
     * 校验范围：
     * frame[1]  包长度
     * 至
     * frame[23] 预留字段
     */
    for (index = 1U; index <= 23U; index++)
    {
        sum += frame[index];
    }

    /* 只保留累加结果的低8位 */
    return (uint8_t)(sum & 0xFFU);
}
```

## 5.3 接收数据校验函数

```c
#include <stdbool.h>
#include <stdint.h>

bool Coffee_ValidateFrame(const uint8_t *frame, uint16_t receivedLength)
{
    uint8_t calculatedChecksum;

    if (frame == NULL)
    {
        return false;
    }

    /* 必须收到完整的26字节 */
    if (receivedLength != COFFEE_FRAME_LENGTH)
    {
        return false;
    }

    /* 检查包头 */
    if (frame[COFFEE_FRAME_HEAD_INDEX] != COFFEE_FRAME_HEAD_VALUE)
    {
        return false;
    }

    /* 检查包长度 */
    if (frame[COFFEE_FRAME_LENGTH_INDEX] != COFFEE_FRAME_LENGTH_VALUE)
    {
        return false;
    }

    /* 检查包尾 */
    if (frame[COFFEE_FRAME_TAIL_INDEX] != COFFEE_FRAME_TAIL_VALUE)
    {
        return false;
    }

    /* 重新计算校验和 */
    calculatedChecksum = Coffee_CalculateChecksum(frame);

    /* 对比接收到的校验和 */
    if (calculatedChecksum != frame[COFFEE_FRAME_CHECKSUM_INDEX])
    {
        return false;
    }

    return true;
}
```

## 5.4 发送数据时填写校验和

在发送数据之前，应先填写包头、长度和所有业务字段，最后计算并填写校验和。

```c
void Coffee_UpdateChecksum(uint8_t *frame)
{
    if (frame == NULL)
    {
        return;
    }

    frame[COFFEE_FRAME_CHECKSUM_INDEX] =
        Coffee_CalculateChecksum(frame);
}
```

正确的组包顺序为：

```text
1. 清空26字节发送缓冲区
2. 填写包头0x7E
3. 填写包长度0x1A
4. 填写警告和故障字段
5. 填写机器状态、指令和应用数据
6. 填写预留字段0x00
7. 计算字节1～23的累加和
8. 将结果写入frame[24]
9. 填写包尾0x7E
10. 发送完整26字节
```

# 六、接收处理建议

接收到串口数据后，建议按照以下顺序处理：

1. 在接收缓冲区中查找包头 `0x7E`。
2. 检查长度字段是否为 `0x1A`。
3. 等待接收完整的26字节。
4. 检查最后一个字节是否为包尾 `0x7E`。
5. 计算字节1～23的累加和。
6. 将计算结果与 `frame[24]` 比较。
7. 校验一致后，再解析警告、故障和状态字段。
8. 校验失败时丢弃当前数据包，并重新查找下一个包头。

不建议在校验通过之前直接执行制作、取消或清洗等控制指令。

------

# 七、常见错误

实现该协议时，应避免以下错误：

1. 使用CRC-8或CRC-16代替累加和。
2. 使用STM32硬件CRC外设计算本协议校验。
3. 将包头 `0x7E` 加入校验。
4. 遗漏包长度 `0x1A`。
5. 将校验和字段自身加入计算。
6. 将包尾 `0x7E` 加入计算。
7. 对累加结果取反或计算补码。
8. 未对累加结果执行 `& 0xFF`。
9. 按64位警告值或故障值进行一次数值相加，而不是累加实际发送的8个字节。
10. 在所有字段填写完成之前提前计算校验和。

------

# 八、校验能力说明

该累加和算法结构简单、计算速度快、资源占用低，适合当前固定长度、短数据帧的串口通信。

但它的检错能力弱于CRC。例如：

- 两个字节发生相反方向的数值变化时，累加结果可能不变。
- 字节顺序交换时，累加结果通常不会改变。
- 不能定位或纠正错误。

因此，该算法只能用于兼容现有协议，不能等同于CRC。

如果后续需要提高通信可靠性，建议在双方同步升级协议版本的前提下改用CRC-16。但在与现有咖啡机对接时，必须继续使用当前的8位累加和算法，不能单方面修改。
